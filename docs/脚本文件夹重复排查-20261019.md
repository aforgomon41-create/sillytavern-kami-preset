# 脚本文件夹内外重复排查（2026-10-19）

结论：已用真实历史成品完整复现一条升级路径。0.92-33 的旧平面更新器升级到带文件夹的新包时，会保留外面的12个旧脚本，再追加包含12个新版脚本的3个文件夹，合计24条、但只有12个不同ID。该结论解释了现象，尚不能代替对反馈用户原版本和更新方式的确认；已询问这两项。

## 原因与影响范围

0.92-32/33没有脚本分类，0.92-34起引入文件夹与共享脚本树合并。旧更新器仅按顶层ID对齐：旧脚本ID不等于新文件夹ID，于是将两者都保留。

更新是在旧预设的脚本中执行的，因此“下载的是最新版”不代表“执行合并的更新器也是最新版”。从旧平面版本直接发起远程更新，即使目标是修复版71，首跳仍会受旧代码影响。只在干净新版中测试，无法复现这条旧升级路径。

本机酒馆助手4.11.3与酒馆1.18.0源码核对：
- importRawPreset将整份JSON交给酒馆savePreset，按预设名保存，不按脚本ID再合并。
- 助手脚本schema没有同一预设内部的ID唯一校验；UI、保存和导出保留脚本数组顺序与文件夹结构。
- 跨全局/角色作用域的ID冲突处理不负责同一预设内部去重。
- 运行时也没有按叶子ID收拢副本，因此重复条目不会仅靠刷新消失。

## 最新版本核对

| 路径 | 结果 |
|---|---|
| 33旧更新器 → 62/69/71 | 都是顶层12条 + 文件夹内12条，共24条 |
| 62/69/71的树合并器处理正常旧平面配置 | 3个文件夹、12个脚本，顶层0条 |
| 干净62 → 69 | 3个文件夹、12个脚本，无重复 |
| 62/69原合并器处理已经重复的配置 | 能收为12条，但后面的新版默认data/开关可能覆盖前面的旧用户设置 |
| 修复版71处理已经重复的配置 | 收为12条，保留首份旧用户设置与开关 |

所以，“新版正常升级不会造重复”与“历史升级用户仍有重复”可以同时成立。也发现并修复了最新版处理既有重复时可能丢失旧设置的问题。

## 修复内容

- 修改唯一共享实现 _script-tree.js，更新与继承设置都复用。
- 同一ID只参与一次合并，按输入顺序取首份记录的enabled/data；早期旧更新器恰好先输出旧顶层记录，后追加新文件夹默认副本。
- 正文仍取新版，匹配脚本仍按新版文件夹归属。不同ID的同名自建脚本不删除。
- 缺少有效ID的异常记录明确停止合并，避免多个无ID脚本被静默折叠；不擅自生成ID或覆盖原配置。
- 更新与继承报告显示按ID收拢的重复数量，继续使用原有先备份再写入的流程。
- 不新增启动时自动改写用户预设，不触碰全局脚本、角色脚本或用户聊天。

该修复处理相同ID的异常副本。若用户曾单独导入脚本、被重新分配ID，无法仅凭同名安全判断哪些是副本；不会为此按名字批量删除。

## 已受影响用户的恢复方式

1. 直接手动导入修复版71，切换到该预设，先取得新更新器。
2. 打开“预设设置 → 关于 → 继承旧预设设置”，选此前使用的旧预设。
3. 完成原有合并审阅。新预设会先备份，再继承旧设置；重复ID收为文件夹内一份，旧预设本身不改。

不要把“旧版本点远程更新”当成上述直接导入。旧更新器的首跳代码不会被下载的JSON提前替换。恢复操作也不会在用户仅打开脚本页面时自动执行。
