# 脚本文件夹重复与无感更新（2026-10-19）

## 当前方案：普通更新后自动整理（80）

用户明确否决另行导入修复包。本轮在既有按钮中转站内联 `_script-upgrade.js`，最终仍为12个官方脚本、3个分类，不增加维护脚本、面板或清理按钮。下文71手动恢复流程仅作为历史，不再是用户升级步骤。

新版入口与基础分类各使用一个稳定的新ID，源码 `legacy_ids` 明确关联旧ID，使旧更新器不能用旧正文覆盖入口，也不能因旧分类关闭而阻止整理启动。后续版本必须维持这两个ID及映射，不得每次发布重新生成。源码别名不输出为助手自定义字段。

仅在当前预设存在已知官方重复/旧ID时整理；健康启动不备份、不写盘、不轮询。新版正文只取自已核对完整的正式分类，共用 `_script-tree.js` 合并。旧入口/旧分类的用户状态优先于新默认记录；保留data、开关、分类名称/图标/颜色，自建脚本按不同ID保留，最终不残留旧入口或空旧分类。

执行顺序是完整保存“自动整理前备份”→保存规范树并等待服务器回执→显式收回旧hub心跳/事件→重建本项目运行实例。实机发现只收拢列表仍会因助手Vue重复key留下旧iframe，因此通过公开树接口短暂暂停官方叶子，立即收回其旧/孤立iframe，再由宿主自身JS栈登记的0ms回调恢复原开关和新版正文。用户自建脚本不暂停，禁用入口/分类继续禁用，备份或目标保存失败时也不重新启用。iframe卸载清宿主任务引用，不新增永久维护脚本。

暂停事务用随机nonce临时标记info，恢复时仅清理同一事务；保留期间最新data、自建脚本和分类。保存方法的短时保护会在助手延迟写盘前剥离精确标记并恢复开关，避免切预设、复制或改名后把暂停状态落盘；无标记的其他保存原样通过。清理计时从宿主恢复回调开始，3秒后释放保护，避免低端设备长时间同步处理提前撤保护。恢复异常最多重试3次；此流程不依赖被销毁的入口iframe，不使用私有Pinia接口、全局reloadAll或整页刷新。复制/改名覆盖为离线回归，实机重点核对0ms恢复前切到另一预设、旧1秒防抖保存及刷新。

保存复用 `getPresetManager('openai').savePreset(name, fullRawPreset, {skipUpdate:true})`，不通过重新导入/切换预设保存，也不用缺省白名单导出。只替换内存scripts子树，保留模型参数、其他扩展和预设变量。保存期间发现修改则重读重试，最多3次；切预设、卸载或任务被替换后，不向另一预设调用运行树替换。

助手自身还有1秒防抖保存，且可能存在已发出的旧请求。因此实机检查同时核对宿主保存收敛后的磁盘和刷新结果；不把内存改变当成唯一持久化证据。宿主并发写入没有事务锁：若用户中途关闭页面且旧请求留下污染树，下次启用仍会自动检查，不要求额外修复步骤。

用户仍经过助手原有的启用脚本确认，拒绝启用时不绕过其选择。全局/角色作用域出现相同官方ID时停止自动接管；重建前和恢复时也重新检查，避免清掉其他作用域实例。缺少新版正文、无ID记录或自建脚本ID冲突时也停止，不按名字猜测删除。

历史数据边界：33直接升级后的旧记录仍在，可以直接保留。干净69升级也保留用户状态。但若先33→69污染，再由69旧树合并器更新，它可能在新版入口运行前就覆盖旧data；新版不能凭空恢复。旧更新器的备份没有记录可验证的来源指针，不能仅凭最新版本、备份后缀或候选唯一自动回填，以免覆盖用户后续修改。

## 以下为71阶段的历史排查与对照

结论：已用真实历史成品完整复现一条升级路径。0.92-33 的旧平面更新器升级到带文件夹的新包时，会保留外面的12个旧脚本，再追加包含12个新版脚本的3个文件夹，合计24条、但只有12个不同ID。该结论解释了现象，尚不能代替对反馈用户原版本和更新方式的确认；已询问这两项。

## 原因与影响范围

0.92-32/33没有脚本分类，0.92-34起引入文件夹与共享脚本树合并。旧更新器仅按顶层ID对齐：旧脚本ID不等于新文件夹ID，于是将两者都保留。

更新是在旧预设的脚本中执行的，因此“下载的是最新版”不代表“执行合并的更新器也是最新版”。从旧平面版本直接发起远程更新，即使目标是修复版71，首跳仍会受旧代码影响。只在干净新版中测试，无法复现这条旧升级路径。

本机酒馆助手4.11.3与酒馆1.18.0源码核对：
- importRawPreset将整份JSON交给酒馆savePreset，按预设名保存，不按脚本ID再合并。
- 助手脚本schema没有同一预设内部的ID唯一校验；UI、保存和导出保留脚本数组顺序与文件夹结构。
- 跨全局/角色作用域的ID冲突处理不负责同一预设内部去重。
- 运行时也没有按叶子ID收拢副本，因此重复条目不会仅靠刷新消失。

## 最新版本核对

| 路径 | 结果 |
|---|---|
| 33旧更新器 → 62/69/71 | 都是顶层12条 + 文件夹内12条，共24条 |
| 62/69/71的树合并器处理正常旧平面配置 | 3个文件夹、12个脚本，顶层0条 |
| 干净62 → 69 | 3个文件夹、12个脚本，无重复 |
| 62/69原合并器处理已经重复的配置 | 能收为12条，但后面的新版默认data/开关可能覆盖前面的旧用户设置 |
| 修复版71处理已经重复的配置 | 收为12条，保留首份旧用户设置与开关 |

所以，“新版正常升级不会造重复”与“历史升级用户仍有重复”可以同时成立。也发现并修复了最新版处理既有重复时可能丢失旧设置的问题。

## 修复内容

- 修改唯一共享实现 _script-tree.js，更新与继承设置都复用。
- 同一ID只参与一次合并，按输入顺序取首份记录的enabled/data；早期旧更新器恰好先输出旧顶层记录，后追加新文件夹默认副本。
- 正文仍取新版，匹配脚本仍按新版文件夹归属。不同ID的同名自建脚本不删除。
- 缺少有效ID的异常记录明确停止合并，避免多个无ID脚本被静默折叠；不擅自生成ID或覆盖原配置。
- 更新与继承报告显示按ID收拢的重复数量，继续使用原有先备份再写入的流程。
- 不新增启动时自动改写用户预设，不触碰全局脚本、角色脚本或用户聊天。

该修复处理相同ID的异常副本。若用户曾单独导入脚本、被重新分配ID，无法仅凭同名安全判断哪些是副本；不会为此按名字批量删除。

## 已受影响用户的恢复方式

1. 直接手动导入修复版71，切换到该预设，先取得新更新器。
2. 打开“预设设置 → 关于 → 继承旧预设设置”，选此前使用的旧预设。
3. 完成原有合并审阅。新预设会先备份，再继承旧设置；重复ID收为文件夹内一份，旧预设本身不改。

不要把“旧版本点远程更新”当成上述直接导入。旧更新器的首跳代码不会被下载的JSON提前替换。恢复操作也不会在用户仅打开脚本页面时自动执行。
