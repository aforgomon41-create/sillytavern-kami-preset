# 📜 压缩：功能说明（大总结 / 超限压缩）

> 对应脚本：`src/scripts/60-压缩.js`（v1.3），按钮「📜 压缩」，全局 API `KamiSummarize`。
> 本文写给用户与后续会话；机制细节以脚本内注释为准。
> v1.3 起摘要请求带结构化输出、账本瘦身成 v3、缺块会自动补 —— 详见第十节。

---

## 一、这个功能解决什么问题

预设原有的滚动压缩（正则「压缩|摘要/设定」把超过深度的楼层替换成只剩摘要）有一个代价：
**楼层数一变，被替换楼层的内容就变，提示词前缀整体变化，缓存命中被破坏**。

超限压缩把思路反过来：

- **平时不压缩**：楼层原样发送，提示词前缀稳定，缓存一直命中；
- **发送量达到上限才动手**：把很久以前的楼层一次性总结成"压缩块"并隐藏原文；
- 压缩块存在**聊天绑定的世界书**里，只在末尾追加、旧块永不改写——
  两次压缩之间，提示词前缀一个字节都不变，缓存保住。

## 二、面板里有什么

面板骨架、手势、兜底皮肤与「🎨 皮肤管理」「🌟 预设设置」完全同源（皮肤零改动）。

标题栏固定两行：第一行是状态点、标题、关闭按钮；第二行是三个手动操作按钮（立即大总结 / 全部取消隐藏 / 清除压缩数据），并列占满宽度。两行都是**纯结构 + 一段只写布局的注入样式**（`LAYOUT_CSS`，先例 = 50 号的 GUIDE_CSS 排版层）：第一行三个元素全是短元素，任何皮肤下都排得下；副标题（世界书名）已撤到「压缩块」区——它曾是爆行根源（flex 开 wrap 后浏览器按自然宽度断行，长世界书名把整行顶爆；rain 又给副标题 order:3 + flex-basis:100%），撤掉后 rain 的规则匹配不到任何元素，不再需要 order/flex 归零去对抗皮肤。

开关卡的高亮（`.is-on`）**吃皮肤规则**：主任务已修好 trpg / rain / nixie 三套皮肤「通电」选择器缺的空格，兜底皮肤也有对应规则；脚本不再注入任何颜色。

| 区块 | 内容 |
|---|---|
| 模式 | 两张开关卡：**滚动压缩** / **超限压缩**。可同时开，但不建议 |
| 滚动压缩参数 | 起始深度（写进正则的 minDepth，0 = 从第一楼起只发摘要） |
| 超限压缩参数 | 触发上限（token）、保留最近楼数、每块楼数；**立即大总结**、**全部取消隐藏**、**清除本聊天压缩数据**（两段式确认） |
| 例外楼层 | 楼层号列表。隐藏时跳过它们；每个块的摘要请求都会带上它们的信息 |
| 压缩块 | 块序号 / 楼层范围 / 注入深度 / 正文（正文直接读世界书条目，你在世界书里改完会自动同步）。区里有「刷新」按钮；缺块或孤儿隐藏楼层时另有提示与按钮 |
| 大总结模型 | 跟随酒馆 / 自定义。跟随酒馆：默认用当前连接，也可直接点选酒馆已存的「连接配置」（不复制，请求时临时套用那套的源格式/地址/模型，跑完还原，密钥走酒馆自己那份）。自定义：多套已存配置（名称、格式、地址、密钥、模型名）随时切换，格式八种，可自动拉模型列表 |
| 摘要提示词 | 头/任务/尾三段编辑：头尾可自由增删条目（角色+内容，各最多 6 条），任务改正文（可恢复默认），材料自动接在任务后；改动即存 |
| 摘要条目状态 | 「🧱 摘要(小总结)」条目的开关 + 手动开关按钮 + 说明 |
| 页脚状态栏 | 滚动状态 ｜ 超限状态 ｜ 上次实测发送量 ｜ 块数与前沿 ｜ 进度/⚠ |

## 三、超限压缩的工作流程

1. **测量**：只读钩子挂在宿主 fetch 上（照反截断的链式规矩，不改请求），
   每次生成后记下"这次实际发送 ≈ N token"（用酒馆当前分词器逐条消息计数）。
2. **触发**：估算值 = 头部开销（实测总数 − 实测楼层和）+ 当前未隐藏楼层 + 新输入。
   达到上限自动触发（挂在 `GENERATION_STARTED`，酒馆会等它跑完才组装提示词，
   所以**当轮就吃到压缩后的上下文**）；也可以随时手动触发。
3. **切块**：范围 = 上一压缩前沿 + 1 ～ 当前楼层 − 保留楼数；已隐藏楼层与例外楼层跳过。
   按每块楼数切块（默认 20 楼一块，**块与块不再合并**，20 楼压成 1 块）。
4. **总结**：每块一次独立请求（`generateRaw` 原始路径，不带预设）。接口二选一：跟随酒馆当前连接，或从「已存配置」里选一套自定义接口（按所选接口格式发请求；地址/密钥/模型名不全会自动回落跟随酒馆）。请求按「头条目 → 任务 → 材料（固定 user）→ 尾条目 → 输出契约」组合，材料 = 之前所有压缩块 + 例外楼层原文 + 本块楼层。
   原始路径**不经过酒馆正则引擎**，拿到的是楼层原文。
   每个块的请求都带上：**之前所有压缩块** + **例外楼层**原文 + 本块楼层。
   请求还带三件东西：占位工具 `kami_noop` + `tool_choice:'none'`（反截断看到这个标记会主动放手，
   这两个标记**必须成对留着**，原因见第九节）、结构化输出的 `json_schema`，
   以及永远压在最后一条的 `OUTPUT_CONTRACT`（第 168 行）。
   `OUTPUT_CONTRACT` 是运行时契约：不管你把自己的「任务正文」改成什么样子，它都会附在请求末尾，
   老用户存在脚本变量里的自定义提示词模板因此照样管用。
   拿到回复交给 `parseSummaryResponse()`（`src/scripts/_summarize-pure.js` 第 249 行）解析，
   只认合法 JSON：剥掉代码围栏、从第一个 `{` 起取**一个完整对象**（字符串里的花括号与转义不算）、
   认常见别名（`plot` / `summary` / `text` / `content` / `本块剧情` 都当正文）、
   拒绝供应商报错文案（`looksLikeProviderError()`，第 114 行）。
   解析不过就**换边重试**一次：带 `json_schema` ↔ 不带 `json_schema`，
   哪边上次走通过下次就先试哪边（`schemaMode`，脚本第 587 行）。
   两边都不如意判该块失败。
5. **落盘**：解析通过的块才写进聊天世界书（见下节），然后才把覆盖到的楼层标记隐藏。
   脚本写盘前会把 JSON 还原成人话 —— 时间线 / 本块剧情 / 关键变化（`assembleBlockText()`，第 235 行），
   **世界书条目里永远不塞 JSON**。
   解析不过就不算成功：**不写盘、不隐藏**，失败块连同后面的楼层原样保留，**下次从断点继续**，
   面板与 toast 会给出接口返回原文的前 200 字（面板上这类块标「⚠ 疑似失败内容」）。
   为什么要这么严：v1.2 及以前只要模型返回非空文本就收下，供应商报错信息也是非空文本，
   于是「当前分组上游负载已饱和」被当成本块剧情写进了世界书。
6. **隐藏**：酒馆原生 `is_hidden`（与 /hide 同一机制）——不进提示词；
   界面上变半透明"幽灵"样式仍可阅读；消息菜单里的「取消隐藏」随时可手动解除，
   脚本绝不重新藏回手动解除过的楼层（重新触发也只处理新范围）。

## 四、压缩块存在哪、怎么进提示词、为什么不怕丢

聊天绑定的世界书里（没有时自动创建并绑定）：

- **📜 压缩块 #N｜楼层 X-Y**：**一个块一个条目**。位置是「@D⚙ 按深度」，
  深度 = 块尾楼层之后的未隐藏楼层数——每个块都锚在**它总结的最后一名"住户"
  的正后方**。块与块、块与例外楼层在提示词里的先后关系因此永远正确；
  同深度的多个块按块序排列。深度按"距末尾"数、保留区大小固定，聊天照常增长
  深度值不用跟着改；只有例外楼层增删、保留楼数改动、手动取消隐藏才需要重算，
  脚本会在这些时机自动同步。条目带 ignoreBudget，不会被世界书预算截断丢弃。
  **条目正文归你**：脚本只读不覆盖，你在世界书里手工改的提要会被面板、被后续
  摘要请求、被注入提示词原样使用（机制见下一节）。
- **📜 压缩状态（勿动）**：关闭状态（**永不进提示词**），是脚本的账本，内容是
  JSON（v3）：压缩前沿、例外楼层清单、我们隐藏过哪些楼（`hiddenByUs`）、
  待重做段（`pending`），以及每个块的档案（楼层范围 from-to + 对应条目 uid）。
  **不再存正文副本**。它是干什么的见下一节。

因为数据住聊天文件、注入靠酒馆原生的世界书机制：

- 切预设 → 回来还在；换预设期间也在（只是那份预设不注入它）；
- 刷新页面 → 脚本重启后世界书照常注入，**不需要脚本做任何"补挂"**；
- 关闭/删除脚本 → 块照常生效（脚本只负责"写"，不负责"注入"）。

唯一会丢数据的操作：删除这些世界书条目、或用「清除本聊天压缩数据」。账本万一
丢/坏，脚本能按块条目名字里的楼层范围"收养"它们继续干活（例外楼层清单会丢）。
**条目正文归用户**：脚本只读不覆盖 —— 名字（`#N｜楼层 X-Y`）与那一行格式头由脚本维护，
正文是你的，改完照旧只读得到你的版本。

## 四点五、「压缩状态（勿动）」到底是干什么的

一句话：**它是脚本的记事本，模型永远看不到它**（条目是关闭状态）。

模型要读的东西在「📜 压缩块 #N」那些条目里；脚本要用的东西在这条账本里。
但有一件事 v1.3 起调了个头：**楼层范围从块条目的名字里解析，正文以块条目为准，
账本只提供结构**。

脚本每次干活都要查三样账：

1. **进度**：已经总结到第几楼（压缩前沿），下次从哪接着切；
2. **档案**：一共有哪几块、各覆盖哪些楼层、对应世界书里哪个条目
   （uid）—— 名字被改过也靠 uid 认得出是哪个块；
3. **例外楼层**，外加**我们隐藏过哪些楼**（`hiddenByUs`）。

为什么现在反过来读条目的名字？因为名字那个格式
「📜 压缩块 #N｜楼层 X-Y」**是脚本自己生成的**：`blockComment()`（脚本第 886 行）
按 `LB_BLOCK_PREFIX + 序号 + '｜楼层 ' + from + '-' + to` 拼出来，
你手改不出这个格式，脚本自己也不会拿你的正文去拼它。既然它和账本一样是脚本产出的结构化数据，
就没有理由再让账本存一份正文副本 —— 两份副本必然不一致。
正文以条目为准，换来的是：你在世界书里改完立刻生效（面板有 400ms 防抖的自动对账，
见下），脚本保存时也**不回写覆盖**你的改动。

为什么账本还留着？因为下面这两样条目推不出来，丢了就真丢了：
例外楼层的完整清单，以及**哪些隐藏楼层是我们藏的**（`hiddenByUs`）。
尤其是后者 —— 下节「缺块会补」敢自动把隐藏楼层的原文读回来重做，全靠名单上
只有我们藏过的楼。

账本万一丢了也不至于罢工：脚本能按条目名字里的楼层范围把它们**收养**回来接着干活
（`reconcileBlocks()`，`src/scripts/_summarize-pure.js` 第 297 行；例外楼层清单会丢）。
只有一种情况救不回来：账本和块条目**一起**没了，这时被隐藏的楼层来路不明，
脚本不敢自动重读（可能是你手动隐藏的），只报警 + 一颗按钮，见下节。

为什么叫"勿动"：改坏这份 JSON，脚本就丢了进度、例外楼层与隐藏名单。
看看没关系；真想重新来过，用面板的「清除本聊天压缩数据」，别手改 JSON。

## 四点半、缺块会补（你把条目删了，脚本替你把剧情找回来）

加载聊天时（打开面板 / 切聊天 / 流水线开跑之前）会对一次账，规则三条：

- 账本档案里的那一段，条目还在（uid 或楼层范围对得上）→ 块活着，
  **正文以条目为准**（你手改后的版本）；
- 账本有档案、条目没了或正文被清空 → 这一段记成**「待重做」（pending）**。
  你的删除动作被理解成"要求这段重来"；
- 下一次大总结**先**重做这些段，再往前推进新楼层（脚本第 1494-1596 行）：
  它会把这段的楼层原文重新读回来 —— **包括已经被隐藏的那些楼**
  （`pendingFloors()`，`_summarize-pure.js` 第 471 行）——
  不读回来这段剧情就永远补不上。

极端情况：**账本也丢了**，而前沿范围内有隐藏楼层、没有任何块盖着它们。
这时脚本无法确定这些楼是不是你手动隐藏的，于是**绝不自动动它们**：
面板给一条警告 + 一颗「重新纳入大总结」按钮，你点了才会把它们记进待重做段
（`repairOrphans()`，脚本第 1699 行）。账本里 `hiddenByUs` 名单上的那些楼不受
这条限制 —— 那是我们自己藏过的，脚本敢自动重读。

面板与账本怎么保持同步：酒馆保存世界书后会发 `worldinfo_updated`，脚本接住它、
400ms 防抖（脚本第 1685-1695 行）后重新对账；拿不到这个事件时，
面板上那颗「刷新」按钮兜底。**两种方式都是重新读一遍世界书**，不是拿内存里的旧副本，
所以你刚在世界书里改完正文、删掉条目，面板立刻跟着变。

对账本身是个纯函数（`reconcileBlocks()`，`_summarize-pure.js` 第 300 行）：
给它世界书条目、账本、隐藏楼层清单，它算出一份新状态。改世界书、删条目、
改正文，走到的都是这同一份逻辑，面板与流水线不会有两套说法。

## 五、默认值与建议

- 触发上限 **400000 token**（按"实测发送量"算）。注意：上限必须**小于模型上下文窗口**，
  否则没触发就先撑爆了。小窗口模型请调小，页脚的"上次实测"就是校准依据。
- 保留最近 **20 楼**、每块 **20 楼**。
- 两个模式**不建议同时开**：共存不打架（被超限压缩隐藏的楼层不进提示词，
  滚动正则只看剩下的楼层），但语义上重复。
- **摘要条目建议常开**：滚动压缩时，哪一楼没生成摘要，那一楼被压缩后就什么都不剩，
  信息直接丢失。只开超限压缩时可以关（大总结读的是楼层原文）。
  面板**任何模式下都不会自动开关它**。

## 六、已知边界

- **删除楼层会让楼层号漂移**：酒馆的删除事件不报被删序号，已有块的"楼层 X-Y"
  从此只是参考值；压缩前沿与例外楼层会做越界收拢。介意的话删楼后
  「清除本聊天压缩数据」重新来一遍。
- 手动隐藏（酒馆消息菜单）过的楼层不参与总结，它的信息不会进任何块。
- **块条目的名字归脚本，正文归你**：名字（`📜 压缩块 #N｜楼层 X-Y`）里的范围是对账与
  收养的依据，改名字会让这一块靠 uid 才认得出；正文随便改，脚本不回写。
- **正文清空 = 这块没了**：把某块条目的正文删成空白，对账会把它当成"缺少的块"，
  那段进待重做，下次大总结重新总结这些楼层（旧正文找不回来，靠楼层原文重写）。
- **重复范围的条目只生效一块**：同楼层范围出现多条（复制条目最容易撞上），
  只保留一条并参与注入，面板给一条提示，脚本**绝不自动删你的条目**，要删自己删。
- **`hiddenByUs` 只在账本里**：账本被清掉之后，前沿范围内那些没有块盖着的隐藏楼层
  来路不明，脚本不敢自动重读，面板上点「重新纳入大总结」才动手
  （手动 /hide 的楼层永远走这条：脚本替你猜不如你自己定）。
- 升级前写进来的旧内容会做一次体检：正文像供应商报错的块（`looksLikeProviderError()`，
  `_summarize-pure.js` 第 112 行）在面板上标「⚠ 疑似失败内容」；脚本只标不删，
  你在世界书里删掉那条、重新大总结即可。
- 长楼层进摘要请求时截断到 12000 字符/楼（例外楼层 4000），防撑爆摘要请求。
- 脚本运行中不重入：一块大总结没跑完，再次触发会提示等待。
- 通知：开始/完成/失败都有 toast；面板按钮「📜 压缩」会显示「·总结中 n/N」与「⚠」。
- 首次为某聊天写入前，面板与状态都是空态，属正常（读到没有压缩数据 ≠ 出错）。

## 六点五、界面纪律（v1.0 起）

- 字段行、开关卡、按钮全部吃契约类（`.kami-field` 三件套 / `span.kami-card-head` / `kami-btn--ghost`），**内联外观清零**；契约没登记类的少数尺寸（宽控件撑满、多行文本框、小标签行、块正文换行）收在脚本的 `LAYOUT_CSS` 一段只写布局的注入样式里（先例 = 50 号 GUIDE_CSS 排版层）。
- 自定义接口的密钥只存本机脚本变量，且 `export_with.data = false`——**导出预设时不会把密钥带走**；换设备导入后需要重新填。
- 删除楼层会让楼层号漂移：酒馆不报被删序号，脚本只把越界的压缩前沿与例外楼层收拢并落盘，已有块的楼层号从此只是参考值。

## 七、控制台 API（排障用）

    KamiSummarize.status()   // 全部状态：模式、实测、块、正则写入次数、错误
    KamiSummarize.inspect()  // 压缩块明细（含全文） + 对账结果
    KamiSummarize.runOnce()  // 手动触发一次大总结（先补待重做段，再往前推进）
    KamiSummarize.refresh()  // 重新读世界书并重新对账（= 面板的「刷新」）
    KamiSummarize.repairOrphans()  // 把来路不明的孤儿隐藏楼层纳入待重做（= 面板的按钮）
    KamiSummarize.setRolling(on, depth?) / .setGrand(on)
    KamiSummarize.addPin(n) / .removePin(n) / .unhideAll() / .clearChatData()
    KamiSummarize.shutdown() // 等价于关闭脚本

`status()` 里 v1.3 新增的字段：`pending` / `orphan` 是楼层范围字符串数组
（`['12-31', …]` 这种），`suspect` 与 `dup` 是条数，`hiddenByUs` 是"我们隐藏过多少楼"
的条数，`schemaMode` 是结构化输出上次走通的哪条路（`'on'` = 带 `json_schema`，
`'off'` = 只剩提示词约束）。
`inspect()` 里对应的：`state.pending` / `state.orphan` / `state.dup` / `state.hiddenByUs`
/ `state.schemaMode`，以及 `state.blocks[]` 每块的 `chars`（正文长度）与
`suspect`（这块的正文像不像接口报错）。

## 八、安全边界（脚本承诺）

- 绝不修改预设文件；正则与条目开关全部走酒馆活设置通道（与 🌟 预设设置同源）。
- 摘要请求不改变主生成的任何状态；测量钩子只读请求体。
- 注销零残留：面板、样式、按钮登记、事件、实测钩子、全局 API 全部收回；
  **压缩成果（世界书条目、隐藏楼层、正则状态）按设计保持原样**。
- 与引导脚本的关系：50-引导.js 的"压缩机制"预留页（RESERVED_STEPS）待本功能真机验证后
  再填文案上线。

## 九、给后续会话的实现要点（踩坑记录）

- 酒馆助手标准生成路径只有**带 tools 时**才把 tool_choice 注入请求体
  （responseGenerator.ts 的 optionsInjector 只认 hasTools||jsonSchema），
  所以摘要请求带占位工具把 `tool_choice:'none'` 送进请求体，反截断才会放手。
- **占位工具 `kami_noop` + `tool_choice:'none'` 必须成对保留**（结构化输出进来之后
  也一样，别以为有了 `json_schema` 就能把占位工具删掉）。取证：
  `responseGenerator.ts:527-542` 里 `data.tool_choice` 是**写在 `if (hasTools)` 分支内**的
  （第 532-533 行），只传 `json_schema` 不传 tools 时请求体里根本没有 `tool_choice`
  这个字段；而反截断只认请求体里的值就放手
  （`src/scripts/20-反截断.js` 第 182-183 行 `if (pinned === 'none') return { skip: '调用方关掉了工具' }`），
  拿不到这个标记它会自己注入函数并把 `tool_choice` 改成 `'auto'`（同文件第 205 行）
  —— 这次摘要请求就被反截断接管了。完整取证在 `.audit/api-facts-压缩JSON.md` 的 E1 节。
- **Claude 源**：服务端把 `json_schema` 变成一个**强制工具**
  （`chat-completions.js:281-290`：追加 jsonTool 并覆盖 `tool_choice`），于是
  `choices[0].message.content` 恒为空串，JSON 落在 `tool_calls[0].function.arguments` 里。
  取值必须走 `responseTextOf()` 那条兜底（脚本第 1281 行起：先认字符串 / `content`，
  再从 `tool_calls` 里挑名字等于 `kami_block_summary` 的那个，拿它的 arguments）。
  只读 `content` 会一路判成"返回内容为空"。
- **Gemini（makersuite / vertexai）**：助手遇到 `tool_choice:'none'` 会把 tools 整个删掉
  （toolCallCompat 的 Google 分支），请求体里既没有 `tools` 也没有 `toolConfig` ——
  反截断因此照样接管这次请求。但 `json_schema` 仍会走 Google 的 `responseSchema`
  （`chat-completions.js:465-476`），且入口的 `flattenSchema` 会替 Google 删掉
  `additionalProperties`、`default`、`exclusiveMinimum`、`propertyNames`（`util.js:1436-1484`），
  所以 schema 仍然生效，只是 `strict` 不参与、也不会被校验。
- `generateRaw` 原始路径对 ordered_prompts 不跑正则引擎（正则只作用于预设路径的
  聊天历史，dataProcessor.ts），所以摘要请求天然拿到楼层原文。
- 酒馆在 `GENERATION_STARTED` 事件上会等所有监听者（script.js:4240 是 await emit），
  这是"总结赶在本轮提示词组装之前"的机制基础；监听者绝不抛异常。
- `getLorebookEntries` 是异步的，漏 await 会拿到 Promise（已踩过，静态断言盯住）。
- 世界书读写走**酒馆原生** `ctx.loadWorldInfo / saveWorldInfo`（getContext 暴露），
  不走酒馆助手的条目接口——后者按自己的字段表重映射后整文件写回，会把酒馆原生
  字段（ignoreBudget、matchPersonaDescription 等）从整个世界书里抹掉。
- 酒馆的世界书有预算（默认上下文的 25%），到顶后 !ignoreBudget 的条目一律跳过
  （world-info.js 第 4942 行）。压缩块条目因此强制 ignoreBudget:true。
- 「一块一条目」的同深度排序：世界书同深度注入按 order 从大到小排在提示词里
  （sortFn = b.order - a.order 再 unshift），所以块的 order 取 1000000-起始楼号，
  先来的块排前面。
- 新建世界书条目必须带**全字段**（镜像 world-info.js 的 newWorldInfoEntryTemplate），
  缺字段就是 undefined。
- 触发上限的估算自带校准：overhead = 上次实测总数 − 上次实测楼层和，随每次生成更新。

## 十、v1.3 修了什么（三个用户反馈）

这三个 bug 都不是"偶发"，是机制层面的洞。下面按「现象 → 根因 → 现在怎么处理」说。

**① 接口报错被当成剧情存了下来。**
现象：压缩块里出现「当前分组上游负载已饱和」这类文案，甚至混在剧情提要里当正文用。
根因：旧版拿到回复只判断"非空就收"。中转站与网关经常把错误正文塞进
`choices[0].message.content` 并回 HTTP 200，所以错误信息也是非空文本 —— 一路写进世界书。
现在：摘要请求带 `json_schema` 结构化输出，末尾再压一条 `OUTPUT_CONTRACT`
（老用户的自定义提示词模板也逃不掉），回复必须过 `parseSummaryResponse()`：
只认合法 JSON，报错文案、纯闲聊、半个 JSON 全部判失败。
解析不过自动换边重试一次，仍不过就判该块失败 —— **不写盘、不隐藏、下次从断点继续**，
面板与 toast 给你接口返回原文的前 200 字。升级前已经写进来的脏内容，
面板会标「⚠ 疑似失败内容」，你删掉那条重新大总结即可。

**② 你在世界书里手改的块正文，面板看不见，保存时还被覆盖回去。**
现象：改完正文回面板还是旧的；下一次大总结一保存，你的修改被脚本用账本里的副本盖掉。
根因：正文存了两份 —— 账本里一份副本、块条目里一份。读的是账本那份，写的时候又把
账本那份写回条目，于是"两份副本必然不一致"的老问题。
现在：**块条目自己就是唯一真相**。面板读条目的正文；保存时只补结构（名字、深度、位置），
正文只在一个块第一次被创建时才由脚本写进去。
账本瘦身成 v3（前沿 / 例外楼层 / `hiddenByUs` / 待重做段 / 每块的档案），**不再存正文**。
世界书保存事件 `worldinfo_updated` 会让面板 400ms 防抖后自动对账，
另有一颗「刷新」按钮兜底 —— 你改完不用做任何操作，面板自己就变了。

**③ 块条目丢了，那段剧情就永远补不上了。**
现象：误删（或清空）一个块条目之后，那一整段楼层还藏着、新块又从不覆盖它们，
于是这段剧情在提示词里彻底消失。
根因：旧版只看压缩前沿往前推进，账本里"这一段有档案"却没去核对条目还在不在。
现在：加载时对账 —— 账本有档案、条目却没了的段记成「待重做」，
下次大总结**先**把这些楼层的原文读回来（包括已被隐藏的那些）重做，再往前推进。
账本也丢了的极端情况（无法确定哪些隐藏楼层是我们藏的）：面板给警告 + 一颗
「重新纳入大总结」按钮，由你决定 —— **绝不自动**动你手动隐藏的楼层。

这三条都有离线测试兜着，不需要开酒馆就能跑：

    node test/harness/summarize-pure.mjs        # 纯逻辑离线自测（解析器 + 对账器，全绿退出码 0）
    node build/verify-summarize-pure.mjs        # 产物内联守卫（默认挑 dist/ 里最新的 kami-*.json）

前者测的是 `src/scripts/_summarize-pure.js`（构建期内联进 `60-压缩.js` 的那份源码），
覆盖「供应商报错的各种形状」「删条目 / 清空正文 / 改名 / 重复范围」「孤儿隐藏楼层的两类分法」
这些场景。后者检查内联真进了预设产物：纯逻辑的函数都在、占位符没残留、
七处关键接线（`summaryJsonSchema()` / `OUTPUT_CONTRACT` / `reconcileBlocks(` /
`parseSummaryResponse(` / `WORLDINFO_UPDATED` / `pendingFloors(` / `repairOrphans`）
都还在被调用，以及账本写的是 v3 结构。少了这道守卫，内联漏掉时构建照样全绿，
只有真机点开面板才会炸 `ReferenceError`。
