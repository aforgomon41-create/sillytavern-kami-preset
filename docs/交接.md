### 分支与发版纪律（2026-10-27 起）

- **只在 `main` 上发版。** 远程更新脚本把任何**非草稿** Release（**含预发布**）都当正式版推给全体用户，镜像清单也只认 `@main`。
  `.audit/publish-release.mjs` 不在 `main` 上会直接拒绝运行。
- **支线上不发 Release（预发布也不行）、不改 `mirror/`、不改 `version.json`。**
- 支线构建的产物名带支线后缀，构建号单独从 1 计数：`kami-v0.93-1-20261027-frontend-rewrite.json`（`build/branch-tag.mjs`；环境变量 `KAMI_BRANCH` 可覆盖）。
  支线测试包启动时**不会自动更新**到正式版（手动检查照常可用），只导入自己的测试酒馆，不分发给用户。
- 支线定期 `git merge origin/main` 跟进（共享分支不要 rebase），完成后开 PR 给作者审。

## 一、这是什么项目

「卡密预设」：一套运行在 **SillyTavern 1.18+** 与 **酒馆助手（Tavern Helper / JS-Slash-Runner）4.11.2+** 上的 AI 角色扮演预设。
交付物是 `dist/` 里的**一个预设 JSON**（约 5.6MB），用户在酒馆里导入；没有独立网站或服务端。

前端由三部分组成：

| 部分 | 跑在哪里 | 源码 |
|---|---|---|
| 四块面板与各脚本界面 | 酒馆主页面（宿主文档） | `src/scripts/NN-*.js` + `_*.js` 共享模块 |
| 正则内嵌前端：思维链 / 行动选项 / 搜索资料 | 每条消息里由正则替换出的 iframe | `src/regex/frontend-*.html` |
| 皮肤 | 宿主页面与各消息 iframe | `src/skins/<id>/skin.{css,json}` |

**作者与用户的验证方式**：下载构建产物 → 导入（手机）酒馆实测。交付时永远写明「下载哪个文件」。

| 原作者的本机环境（Windows） | |
|---|---|
| 工作区 | `D:\SillyTavern\卡密预设制作` |
| 真机酒馆 | http://localhost:11451/（隔离测试实例常用 11452） |
| 酒馆源码参考 | `D:/SillyTavern/SillyTavern-1.18.0`（旧启动器目录已不存在，见 [真机验证备忘](真机验证备忘.md)） |

其他机器（例如 Linux）开发时：

- 装依赖：`npm ci`。锁文件里的地址是 `registry.npmmirror.com`；若 npm 拒绝下载非默认源的包（npm 12 的 `allow-remote` 默认策略），
  用 `npm ci --replace-registry-host=always`（改从官方源取，锁文件与完整性校验不变）。
- 「正文外壳」端到端检查需要酒馆自带的 showdown / DOMPurify：设 `KAMI_ST_ROOT=<目录>`，该目录下要有
  `node_modules/showdown/dist/showdown.min.js` 与 `node_modules/dompurify/dist/purify.min.js`（没有酒馆时单独 `npm install showdown@2.1.0 dompurify@3` 到一个空目录即可）。
- 浏览器检查需要 Chrome：`KAMI_CHROME=<chrome 路径>`；预览台地址用 `KAMI_PREVIEW_ORIGIN`。

1. **酒馆正则引擎不是 native String.replace**（public/scripts/extensions/regex/engine.js:419-445）：

   否则 settings.json 的 preset_settings_openai 与 preset_allowed_regex.openai 不更新，新产物等于没上。切换路径见真机验证备忘。
3. **消息 iframe 的高度**只由酒馆助手的 ResizeObserver(body) 驱动；实测可靠，前端不需要自己 syncHeight。

   登记在 [皮肤契约](https://github.com/aforgomon41-create/sillytavern-kami-preset/blob/main/docs/%E7%9A%AE%E8%82%A4%E5%A5%91%E7%BA%A6.md) §9.5；行动选项前端原先自己挂的那枚 ResizeObserver 属重复劳动，已按此删除。）
   但预览台是同文档内嵌，RO 有时不触发，已加 1 秒重新量高兜底（只重新量、不改被测行为）。
4. **皮肤选择器必须以 html[data-kami-skin=...] 原样开头**（特效写成 …[data-kami-effects~=...]），lint 会拦；

9. **第 5 条的适用范围被实测修正了**（重要）：`write` 工具（harness 的文件写入工具）是**逐字节忠实**的 ——
   本轮用探针逐行验过：`$`、`$$`、`$1`、`$<name>`、`${braces}`、`\s`、`\n`、`\\`、`{{char}}`、`{{//注释}}`、

9b. **PowerShell 的 `-replace` 会把「替换文本」也做 regex 转义**（第四十一轮踩的，把 `meta.json` 直接写坏）：
    写成 `$t -replace [regex]::Escape($a), [regex]::Escape($b)` 时，`$b` 里的空格变成 `\ `、点变成 `\.`，
    这些是 JSON 的**非法转义**，文件当场 parse 失败。而且 `.NET` 的替换串里 `\n` 会变成**真换行**，
    于是换行符被塞进 JSON 字符串里。
    **结论：改 `.json` / `.md` 一律用 node 脚本做字符串手术（字面量 `String.replace`），
    改完立刻 `JSON.parse` 验证；真要抢救已坏的文件，先 `JSON.parse` 定位到行列再看那一带的字符码。**

10. **`params[].unit` 会被拼进 CSS 值，不是纯显示字段**（本轮踩出来的回归，用户真机发现的）：
    `30-皮肤管理.js` 写用户参数时是 `v + (p.unit || '')`，所以单位必须是**合法 CSS 单位**或**空串**。
    文案把 TRPG 骰子的单位从空串改成 `×`、把记事本印章的 `deg` 改成 `°`，两个都是非法 CSS 单位：
    - `calc(... * 1×)` 使 `width`/`height` 整条声明被丢弃 → **d20 宽高归零 → 压住标题、左半边被纸边裁掉**；
    - `rotate(-1.2°)` 使 `transform` 整条变 `none` → **印章既不倾斜、也丢了 1px 错位**（这条用户还没发现）。
    已在 `build/lint-copy.mjs` 加 `checkUnit` 拦住这类值，契约 §3.8 写了警告，契约 §3.7 的禁用令牌清单管另一类。
    **教训**：改皮肤文案之前，先分清每个字段是「纯显示」还是「会参与机制」——本轮 100 来个字段里只有 `unit` 是后者，
    而平台上连它自己都不一致（伪参数「字号缩放」的 `unit: '×'` 是另一条代码写 CSS 的，纯显示）。

33. **★ 用户手动改了预设条目之后，怎么以他改的那份为基础继续构建**（2026-09-22 用户点名问的，答案就是本项目
    一直以来的那条唯一真相链）：

    ```
    酒馆里手动改条目（界面 / 面板 / 直接编辑预设文件）
              ↓  必须回到工作区，否则下一次构建会把它覆盖掉
    src/preset.base.json          ← **构建的唯一真相**（build.mjs 只读它）
              ↓  node build/build.mjs
    dist/kami-v0.90-<N>-<日期>.json
    ```

    - **构建不读酒馆里的预设**，只读 `src/preset.base.json`。所以手动改的那份**必须先回填**进
      `src/preset.base.json`，否则下一次构建出来的产物还是旧内容（改动"白改"，而且不会报错）。
    - **回填的办法（2026-09-23 起：用工具，别再手工比对）**：
      ```
      node build/merge-handedit.mjs --st --list        # 看酒馆数据目录里有哪些预设（可选）
      node build/merge-handedit.mjs --st <预设名>       # 干跑：只比对，出分类差异报告
      node build/merge-handedit.mjs --st <预设名> --apply --build   # 真合并 + 顺手构建
      ```
      也可以 `<文件路径>` / `--url <ferry链接>`（自动 ferry 取回）/ 不给参数（取「收到的文件/」里最新的预设）。
      工具会：备份主干 → 主干 ← 他那份 → 回填 `src/scripts/meta.json` 的脚本开关与 data、
      `src/regex/list.json` 的正则设置 → 跑 `check-copy-updates.mjs` 核对文案表 →（`--build`）构建。
      **合并口径：一律以用户手改的那份为准**（他 2026-09-23 明确要求），包括条目、顺序、
      条目开关与字段、脚本开关与脚本内设置、正则设置、顶层字段、注释文字。
      唯一「构建期接管、不参与合并」的是脚本正文/名字/info/button 与他没有的脚本（那些每次构建都会重建）。
      三个可选开关：`--sync-comments`（把 `comment-updates.json` 的 match 与文案同步成他写的版本）、
      `--keep-runtime`（脚本 data 不回填，保留主干原值 —— 不想把面板位置、上次检查时间、看过标记、
      当前皮肤与模型这类运行时状态写进新用户默认值时用）、`--json`（机器可读，给 agent 用）。
      工具头部的注释就是完整说明书（`node build/merge-handedit.mjs --help`）。
    - **手工回填的老办法**（工具坏了时的兜底）：把酒馆导出的 JSON 或数据目录里那份直接覆盖
      `src/preset.base.json`，再跑 `node build/check-copy-updates.mjs` 与 `node build/build.mjs`。
    - **两个必须知道的后果**（回填等于"用户的手改覆盖了表里的东西"）：
      · 注释是 `{{//}}` 写在条目 content 里的，**用 `design/copy/comment-updates.json` 落地**。
        用户手改过的条目如果带着旧注释，回填后 `check-copy-updates.mjs` 会报「对不上」；
        这时要么加 `--sync-comments` 让工具把表同步成他写的版本，要么手工改表。
      · 酒馆加载预设时会自己重写文件（+55 个标准字段、剔除顶层 `name`），所以回填后 `src/preset.base.json`
        与「刚构建出来的产物」不会逐字节相同 —— **这是正常的，别去"修"它**（§五第 15 条）。
        顶层 `name` 也一样：构建期会被覆盖成产物名，合并时它怎么变都不影响产物。
    - **反过来也成立**：要让用户的手改不丢，最省事的做法是**让他改完之后把预设文件发回工作区**
      （ferry `get`，落在 `收到的文件/`），或者干脆用 `--st` 直接读他酒馆数据目录里那份。

34. **★ 「清掉一块看着冗余的数据」可能反而打开一条破坏通路 —— 空数组在 JS 里是真值**（2026-09-24，SPreset 那轮）：

    背景：本预设的 `extensions.SPreset.RegexBinding.regexes` 与 `extensions.regex_scripts` 是同一份 11 条正则
    （构建期 `build/build.mjs` 镜像同步）。有人会觉得"正则只该有一份真相"，把那块镜像删掉 —— 结果是**反向**的：

    - 第三方 SPreset 脚本里有个处理器是 `if (SPresetSettings.RegexBinding.regexes) syncToST(); else syncFromST();`
      （`收到的文件/regex_bind_inject.js:4099-4105`）。**`[]` 是真值**，所以"清空"走的是 `syncToST()` 那条，
      而 `syncToST()` 写回的是它在**加载时**算好的常量 `presetRegexes`（`:3700`，那一刻 RegexBinding 是空的）
      → 把 `extensions.regex_scripts` 覆盖成空表 → **本预设 11 条正则（含两个前端载荷）整表清空**。
    - 反过来，块里保持与 `regex_scripts` **逐条一致**时，那次写入是等值覆盖＝空操作 —— 这才是安全态。
    - **通用教训**：判断"这块数据是不是冗余"之前，先看**谁会读它、以及读的时候怎么判空**
      （`if (arr)` 与 `if (arr && arr.length)` 在 JS 里是两种命运）。第三方脚本尤其如此：
      它的代码不在我们仓库里，一旦被它接管，清数据比留数据危险。
    - 同轮另一条：`build/merge-handedit.mjs` 的合并口径是「一律以用户手改的那份为准」，但
      **运行时状态**（面板位置、`lastCheckAt`、`seen`、当前皮肤与模型）也会跟着进默认值；
      不想带上就用 `--keep-runtime`。

36. **★ 想靠"标签"定位内容时，先查酒馆的清洗白名单**（2026-09-26，正文美化 v2 踩出来的）：

    `<content>` 之所以能当判据，是因为**酒馆自带 DOMPurify 的默认白名单里字面就有 `content` 这个名字** → 它会作为真元素
    活到 `.mes_text`，我们在 DOM 里找得到它。而白名单外的名字（例如 `<正文>`、`<narr>`）会被 showdown 转义或被剥掉只留内容，
    **DOM 里根本认不出边界**。所以任何"按标签定位"的设计，第一步都是查白名单；白名单外的只能退回**原始文本指纹对位**，
    并且必须做"**对不上就一个节点都不动**"的保险。另外：**用户输入的标签名永远不要拼进 CSS 选择器**（用
    `getElementsByTagName` 之类的接口），否则一个引号或空格就能把选择器拼坏。

37. **★ 用户的自定义 CSS 与我们的全局层：同特异性下「后注入者赢」**（2026-09-26，酒馆消息区美化）：

    酒馆把用户主题 CSS 通过 `power-user.js` **运行时**追加到 head，所以它可能排在我们注入的 `<style>` 之后 ——
    同特异性下**用户赢**。结论：**不要去打 `!important` 战争**，只挑用户通常不设的属性下手（例如圆角与间距），
    并把冲突点列成清单交用户定；两级都要能看：用户赢时用他自洽那套，我们赢时用皮肤配套的底色+字色，
    避免"底翻了字没翻"。

38. **★ 正文包裹层禁写 `overflow` / `position` / `pointer-events` / `z-index`**（2026-09-26，已入契约 §9.7）：

    正文里**并排着**插件插进来的按钮、HTML 美化条目的卡片、两个既有前端的 iframe。包裹层一写 `overflow:hidden`

    （间距、块级、`overflow-wrap`），颜色归皮肤。**回归时必须含「模拟插件按钮真点击回调 0→1」这一条。**

39. **★ 碰酒馆助手（或任何插件）的正则 API：先确认「返回的对象是什么形态」，别照预设文件的字段名写**
    （2026-09-26，正文前端那轮踩的，差点以「功能做好了」交付）：

    同一份酒馆正则，**两个地方两个形态**：
    · **预设文件里**（`src/preset.base.json` / `src/regex/list.json`，也就是我们写的那些）是酒馆原生形态 ——
      `scriptName` / `disabled` / `findRegex` / `replaceString` / `placement` / `markdownOnly`；
    · **酒馆助手 `getTavernRegexes()` 返回的**是**归一化形态** —— `script_name` / `enabled` /
      `find_regex` / `replace_string` / `source` / `destination`。
    按 `scriptName` 去匹配 → **一条都匹配不上**；按 `disabled` 去比对 → `!!undefined === false`
    正好等于「已一致」，于是**提前返回、一个字节都不写**，而日志还会打印「已设为启用」——
    **功能全废但看起来一切正常**。第三个坑：`replaceTavernRegexes(regexes, option)` 的
    `option` 是**必填**（`{ type: 'preset', name: 'in_use' }`），不带会写到**全局正则表**去。
    两条规矩：**①读回来的对象先看字段名再用；②只动对象上本来就有的那个键**（有 `enabled` 写 `enabled`，
    有 `disabled` 才写 `disabled`），绝不凭空造字段 —— 这样两种形态都能用。
    另外**任何「开关」类功能，验收时必须有一条「开关位置 ↔ 真实位」的并排读数**（本项目做法见
    `preview.html` 的 `正文前端探针|`，以及 `.audit/check-bodyfront-artifact.mjs` 那种产物侧守卫）。
    同一类坑还有一枚：**界面选中态是拿字符串比出来的**（`String(state[key]) === '1'`），
    默认值写成布尔 `true` 就会显示成「关」—— 默认值一律写**字符串**。

40. **★ iframe 对「扫 DOM 的第三方插件」是不透明的 —— 而且它们多半还打偏**（2026-09-26，文生图那轮查出来的）：

    我们的正文前端把正文烤进 `iframe[srcdoc]`。对扫 DOM 的插件来说，这一层是**看不见**的：
    · **TreeWalker / textContent 这类扫描不会跨文档边界** → 拼出来的文本里**没有** iframe 里的字。
      实测（`.audit/文生图-探针.html` 是可重跑的探针）：同样一楼，前端接管后智能扫描读到 **16 字**
      （只剩楼层的散字），没接管时读到 **41 字**且含标签。
    · **`innerHTML` 序列化会把 `srcdoc` 的属性值一起吐出来** → 「拿 innerHTML 做字符串替换」那种插件
      **会命中**（`includes` 为真），但替换落在**属性值内部**：占位符不会被解析成元素（**按钮不出现**），
      而 `srcdoc` 被改坏之后浏览器会**重新解析**它 → **前端里那行字直接没了**（实测 46 字 → 22 字）。
      也就是说：这种模式下不只是「不支持」，是**会把正文内容吃掉一段**。
    · **宿主还可能不是你以为的那个**：RBQ 的 `Tn()` 是 `mes.querySelector('.mes_text, …, .mes_block, …')`
      —— 选择器列表按**文档顺序**取第一个命中的元素，而 `.mes_block` 是 `.mes_text` 的祖先，
      所以它拿到的是 **`.mes_block`（整块消息）**。实测两次都是 `div.mes_block`。后果：插件兜底
      `container.append(card)` 时卡片落在**整块消息的末尾**，永远在正文前端**下面**，跟正文没有位置关系。
    · 反向也确认过：**标签确实活在 iframe 里**（没被碰过的那一组读得到，46 字），只是父文档侧一个都看不见。
    ⚠️ 还有一条通用教训：**卡片的点击事件委托挂在父文档上**，所以「把卡片塞进 iframe 里」这条路
    一定是死键 —— 卡片必须活在父文档。
    完整调研（插件逐个机制 + 六种接法对比 + 诚实清单）：`.audit/文生图兼容调研.md`。
    可重跑的工具：`.audit/文生图-探针.html`（浏览器探针）、`.audit/slice-rbq.mjs` / `find-rbq.mjs`

## 六、新会话的第一件事

1. 按 [docs/README.md](README.md) 的顺序读文档；先看本文第〇节，确认当前分支（`git branch --show-current`）和分支纪律。
2. **确认基线**：`npm ci` → `node build/build-runtime.mjs --check`（应报「已是最新」）→ `node build/build.mjs --dry`（全部测试与守卫通过）。
3. **动手前**：新增任何界面先查 [功能复用](功能复用.md)；在本支线改皮肤、前端、面板先读 [前端契约](前端契约.md)（旧系统才看 [前端技术栈](前端技术栈.md) 与 main 上的皮肤契约）；
   新界面或改版先在 `design/previews/` 出预览，用户（前端负责人）明确认可后才正式实现（记录在 [frontend-design.md](frontend-design.md)）。
   支线上的快速验证：`node build/frontend/build-preview.mjs`（重建预览）、`node build/run-ts-tests.mjs`（单测）、`npx tsc -p tsconfig.json --noEmit`、
   `node test/frontend/browser/{touch,panel,ds-audit}.mjs`（触屏 / 面板 / 渲染对比度审计）。
4. **改完**：`node build/build.mjs`（完整构建，需 `KAMI_ST_ROOT`）；涉及界面再起预览台用浏览器检查；要碰真机先读 [真机验证备忘](真机验证备忘.md)。
5. **交付**：写明下载哪个文件；作者点头后才在 `main` 上发版（`node .audit/publish-release.mjs <构建号> <公告文件>`，公告由作者逐字审阅），
   发完盯 jsDelivr 清单换到新版为止。
6. **收尾**：刷新本文第〇节；新知识按 [docs/README.md](README.md) 的「维护约定」写进对应文档，不开新的散文档。
