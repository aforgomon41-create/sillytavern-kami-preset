# 卡密预设 · 前端契约 v1.0（草案）

> 2026-10-27 起草，适用于 `frontend-rewrite` 支线的新前端。取代旧的《皮肤契约 v0.3》（仍描述 main 上的旧系统，本支线已删除）。
> 本契约管理**所有前端**：面板与对话框、消息里的前端（思维链 / 行动选项 / 搜索资料 / 正文外壳）、原生思维链块的增强、提示与悬浮球、装饰模块，以及皮肤。
> 状态：**草案**。标「待验证」的条目要在真实酒馆里验证后才定稿；每次修改契约都要更新文末的变更记录。
>
> **本契约是先验方案，不是教条。** 它是在还没做出任何皮肤之前，根据旧系统的教训推出来的。做皮肤时如果发现某条规则挡住了合理的设计，
> **以皮肤的需要为准修订契约**：在变更记录里写清是哪套皮肤、想做什么、被哪条规则挡住、怎么改，再升版本。
> 能放宽的是表达能力（新增钩子、装饰槽、令牌、允许的 CSS 属性……）；守住的是第 0 节的目标（可读、可操作、不与酒馆互相干扰、可机器验收）。

## 0. 设计目标

1. **皮肤只给少量输入也一定可读**：任何皮肤、任何组件状态，文字与背景都成对且达标，不靠逐个组件打补丁。
2. **魔改不受限，兜底不失效**：皮肤可以从「只换几个颜色」一路改到「整套外观重画」，越深入检查越严，但平台的结构、可读性、可操作性始终有保障。
3. **与酒馆互不干扰**：酒馆和第三方插件的全局 CSS 进不来，我们的样式也不漏出去。
4. **所有前端一套体系**：同一套组件、同一套令牌、同一个皮肤分发入口，不再有「面板一套、消息前端一套」。
5. **可机器验收**：契约里能判定的规则都有自动检查，皮肤不过检查就不能构建。

## 1. 架构

| 部分 | 职责 | 不负责 |
|---|---|---|
| **运行库**（`KamiRuntime`） | React 18、Radix、设计系统组件、皮肤引擎、挂载服务；全预设只有一份，挂在酒馆主页面 window 上 | 具体功能的业务逻辑 |
| **功能脚本** | 业务逻辑（压缩、搜索、预设解析、更新……）+ 自己的界面模块（TSX），界面只用设计系统组件 | 配色、几何、跨功能的组件实现 |
| **皮肤脚本**（皮肤管理） | **唯一的皮肤分发者**：加载皮肤包、合成令牌、校验与校正、下发到所有渲染面；皮肤管理面板 | 组件结构与行为 |
| **皮肤包** | 种子、令牌覆盖、部件 CSS、装饰、素材、特效与参数（纯数据 + CSS，不含 JS） | 布局几何、交互逻辑、功能文案 |

### 1.1 渲染面

| 渲染面 | 用于 | 挂载方式 |
|---|---|---|
| **S1 宿主浮层** | 面板、对话框、贴底抽屉、提示、悬浮球，以及所有弹层（下拉、菜单、提示框） | 酒馆 `body` 下**唯一一个** Shadow DOM 宿主 `<kami-layer>`；所有 Radix 弹层 portal 进它内部 |
| **S2 消息挂载** | 思维链、行动选项、搜索资料、正文外壳等消息内前端 | 正则把模型输出替换成**挂载标记**；我们的脚本（借助酒馆助手对酒馆页面的访问能力）在消息 DOM 里给每个标记挂一个 Shadow DOM 并渲染。酒馆助手的消息 iframe 渲染作为备选通道（8.3） |
| **S3 原生增强** | 酒馆自己的元素（例如原生思维链块 `details.mes_reasoning_details`） | 在酒馆元素内部放一个 Shadow DOM 宿主承载我们的界面；不移动、不删除、不接管酒馆自己的控件 |

依据见附录 A：Radix 在 Shadow DOM 里经两处构建期修补后鼠标、键盘、触屏全部正常；跨文档渲染进 iframe 不可行。

### 1.2 预设相关界面由预设本体生成

预设设置、引导等与预设条目有关的界面，**页签、分组、选项一律由解析当前预设得来**（`test/harness/preset-parse.mjs`），界面代码只按「类型」渲染（模型页、变量、单选组、多选组、独立条目），
**不写死任何分类名、分组名或选项数量**。预设里加减条目、改名、给运行模式加一种，都不需要改界面代码。
排序等规则也只看类型（例如「模型页最前、含变量的页签其次、其余按预设顺序」）。平台固定的页签（如「关于」）明确标出，不混进解析结果。

## 2. 技术栈与工程约定

- **TypeScript（strict）+ TSX**，esbuild 打包。功能脚本把 `react`、`react-dom`、Radix 与设计系统标记为外部依赖，运行时从 `KamiRuntime` 取，不重复打包。
- **样式用原生 CSS**：写成 `.css` 文件，构建时作为文本打包；**不用 CSS-in-JS**。组件里不写内联样式，动态几何值通过 CSS 变量传入（如 `style={{ '--k-x': x + 'px' }}`）。
- **Radix 版本精确锁定**，并在打包时打两处修补（附录 A）。修补插件会核对修补点数量，Radix 一变就构建失败；升级 Radix 必须重跑隔离验证。
- **浏览器下限**：Chrome / Android WebView 108+、Safari / iOS 16.4+、Firefox 110+。依赖的能力：Shadow DOM、可构造样式表（不支持时回退为每个根一份 `<style>`）、容器查询、`dvh`。
- 新前端目录（建议）：

      src/frontend/
        runtime/        运行库入口、挂载服务、Radix 修补
        ds/             设计系统：组件、部件清单、基础样式
        skin-engine/    令牌合成、对比度校正、皮肤包校验
        surfaces/       S1 / S2 / S3 三种渲染面
        features/<名>/  各功能的界面模块（TSX）与文案
      src/skins/<id>/   皮肤包

## 3. 层叠顺序与样式所有权

每个 Shadow DOM 根里的样式按这个顺序分层，**全部分层，没有不分层的规则**：

```css
@layer k.reset, k.tokens, k.base, k.components, k.skin, k.lock;
```

| 层 | 内容 | 谁写 |
|---|---|---|
| `k.reset` | `:host { all: initial }` 等根重置 | 平台 |
| `k.tokens` | 皮肤引擎合成的令牌值 | 皮肤引擎生成 |
| `k.base` / `k.components` | 设计系统的基础样式与组件默认外观 | 平台 |
| `k.skin` | 皮肤 CSS（皮肤作者**只**写这一层，引擎自动包进来） | 皮肤 |
| `k.lock` | 结构不变量：渲染面定位、贴底抽屉、滚动容器、页签单行、`hidden` 语义、焦点环最低可见度、装饰层不拦截点击 | 平台 |

- `k.lock` 在最后，普通声明天然压过皮肤，**平台不需要 `!important`**；皮肤 CSS **禁止 `!important`**（静态检查拦截）。
- 隔离：Shadow DOM 挡住酒馆的全局 CSS（包括 `!important`）；`:host { all: initial }` 切断继承下来的字体、颜色等属性。

## 4. 组件与部件协议

皮肤只能通过**公开钩子**选中元素；内部类名是私有的，随时可能改。

| 钩子 | 写法 | 例 |
|---|---|---|
| 组件 | `[data-k="<组件>"]` | `[data-k="button"]` |
| 部件 | `[data-k-part="<部件>"]`（在组件内部） | `[data-k="switch"] [data-k-part="thumb"]` |
| 变体 | `data-variant` / `data-tone` / `data-size` | `[data-k="button"][data-variant="primary"]` |
| 状态 | Radix 的 `data-state`、`data-disabled`、`data-highlighted`，以及 `aria-*` | `[data-state="checked"]` |
| 卡片角色 | `data-role="container"/"choice"/"collapse"` | 只有 choice 有选中态 |
| 表面层级 | `data-k-level="bg"/"surface-1..3"/"sunken"/"inverse"`（通用属性：表面、卡片、面板、对话框、弹层都会带） | 带它的元素铺本层底色，并把上下文变量指向本层配对；层级自动嵌套（画布里的卡片是 surface-1，卡片里的卡片是 surface-2） |
| 装饰槽 | `data-k-ornament="<槽名>"` | 见 6.4 |
| 渲染面根 | `[data-k-surface="layer"/"message"/"native"]`，上面带 `data-k-skin`、`data-k-scheme`、`data-k-density`、`data-k-motion`、`data-k-effects` | |

- **由多块组成、且有部分会 portal 出去的组件**（下拉、对话框、提示），每一块的根上同时带 `data-k` 与 `data-k-part`，例如 `[data-k="select"][data-k-part="content"]`。portal 出去的那块不在组件根元素里面，只能这样选中。
- 组件、部件、变体、表面层级、装饰槽的**机器可读清单**在 `src/frontend/ds/parts.ts`；皮肤检查据此拒绝引用不存在的钩子（写错名字的规则会静默失效）。
- **容器组件（面板、对话框、卡片、设置分组、设置行）的部件必须用直接子元素选择器 `>`**，例如 `[data-k="panel"] > [data-k-part="head"] > [data-k-part="title"]`。
  写成后代选择器（`[data-k="panel"] [data-k-part="title"]`）会误伤嵌套在里面的其他组件的同名部件——这正是旧系统 `.kami-card` 的老问题。平台 CSS 遵守，皮肤 CSS 检查强制。
- **选中、勾选、当前页**不能只靠颜色区分，必须同时有形状、边线、字重或图标的变化。
- 初始组件清单（以 `parts.json` 为准）：Button、IconButton、Toggle、Segmented、Tabs、Switch、Checkbox、Radio、Select、TextField、TextArea、NumberField、Slider、Field（标签 / 说明 / 错误）、Card（三种角色）、Collapsible、Accordion、Dialog、Sheet（贴底抽屉）、Panel（浮动窗）、Popover、Menu、Tooltip、Toast、Progress、Spinner、Badge、Status、Alert、Empty、List、Table、Steps、Markdown、Code、Divider、ScrollArea。

## 5. 令牌模型（核心）

### 5.1 三层

```
种子（皮肤给）──推导──▶ 语义令牌（成对，引擎生成）──引用──▶ 组件令牌（组件只用成对的语义令牌）
```

### 5.2 种子

每个配色方案（`light` / `dark`，皮肤可以只给一种）提供：

| 种子 | 含义 | 必填 |
|---|---|---|
| `neutral` | 表面的基调色（决定底色的色相与饱和度） | ✅ |
| `accent` | 主强调色 | ✅ |
| `accent2` | 第二强调色 | 否（由 accent 推导） |
| `danger` / `warning` / `success` / `info` | 状态色 | 否（有默认值，按方案自动调到可读） |
| `radius` | 圆角基准 | 否 |
| `font` | `body` / `heading` / `mono` 字体栈（只用系统字体或皮肤素材里打包的字体） | 否 |
| `elevation` | 层次风格：`flat` / `shadow` / `glow` / `outline` | 否 |
| `contrast` | 目标对比度档位：`standard` / `high` | 否 |

### 5.3 语义令牌：成对规则

**每一个背景令牌都有配套的前景令牌，组件只能把一个背景和它自己的前景放在一起用。** 这条叫配对规则，是消除撞色的根本。

| 背景 | 配套前景 |
|---|---|
| `--k-bg`（画布）、`--k-surface-1..3`（逐级抬高）、`--k-sunken`、`--k-inverse` | `--k-on-<背景>`（正文）、`--k-on-<背景>-muted`（次要）、`--k-on-<背景>-subtle`（弱提示 / 占位）、`--k-border-<背景>`（控件轮廓）、`--k-divider-<背景>`（装饰性分隔线）、`--k-link-<背景>`、`--k-focus-ring-<背景>` |
| `--k-control`（控件默认底）及 `-hover` / `-active` | `--k-on-control`、`--k-border-control` |
| `--k-accent` 及 `-hover` / `-active` | `--k-on-accent` |
| `--k-accent-soft` | `--k-on-accent-soft` |
| `--k-selected` | `--k-on-selected` |
| `--k-danger` / `-warning` / `-success` / `-info` 及各自 `-soft` | 各自的 `--k-on-…` |
| 遮罩 | `--k-scrim`（半透明，不参与配对） |

**表面上下文**：链接色和焦点环**每个表面各有一份**。一个全局颜色不可能同时在深底和浅底上都清楚（例如深色主题里放一张浅色卡片）。
渲染表面的组件（面板、卡片、抽屉……）在自己的根上把上下文变量指向本表面的那一份：

```css
[data-k-surface-level="surface-1"] {
  --k-on: var(--k-on-surface-1); --k-on-muted: var(--k-on-surface-1-muted); --k-on-subtle: var(--k-on-surface-1-subtle);
  --k-border: var(--k-border-surface-1); --k-divider: var(--k-divider-surface-1);
  --k-link: var(--k-link-surface-1); --k-focus-ring: var(--k-focus-ring-surface-1);
}
```

表面里的文字、链接、焦点环一律用上下文变量（`--k-on`、`--k-link` …），这样同一个组件放在任何表面上都自动配对。

### 5.4 对比度门槛

| 配对 | 最低对比度 |
|---|---|
| 正文、次要文字（`on-X`、`on-X-muted`）对其背景 | 4.5 : 1（`contrast: high` 时 7 : 1） |
| 弱提示、占位文字（`on-X-subtle`） | 3 : 1 |
| 控件轮廓 `border-X`、焦点环 `focus-ring-X` 对所在表面 | 3 : 1 |
| 装饰性分隔线 `divider-X` | 1.35 : 1（只求看得见，不能当控件边界用） |
| 选中与未选中 | 除颜色外必须有非颜色差异（见第 4 节） |
| 禁用态 | 不设门槛，但必须同时有非颜色提示（光标、透明度之外的标记） |

强调色作为按钮底色，**不强制**对所在表面达到 3 : 1：品牌色不被引擎强行改深，按钮靠按钮上的文字（`on-accent` 必须达标）和可选的描边来识别。

### 5.5 推导与校正（皮肤引擎）

实现：`src/frontend/skin-engine/`（`color.ts` 色彩与对比度、`tokens.ts` 推导与校正），单测 `test/frontend/`。

1. 在 OKLCH 色彩空间里由 `neutral`（取色相与饱和度）、`accent` 按明暗方案推导各语义令牌。
2. **引擎自己推导的颜色**直接解出达标的值：只调明度（保持色相、饱和度），朝能拉开对比度的方向找改动最小的明度；彩色调到头仍不够就退到纯黑或纯白。这不算「校正」。
3. **皮肤给出的颜色**（原样使用的种子，如 `accent`、给了的状态色；以及 L2 覆盖的令牌）不达标时：先调前景；前景调到黑白都不够（例如 7 : 1 档遇上中等明度的强调色）就调背景。每次调整都记一条**校正**（令牌、原值、新值、对比度前后）。
4. 强调色的悬停 / 按下状态朝「远离 `on-accent`」的方向变化，保证同一个字色在三种状态上都达标。
5. 皮肤覆盖了背景时，引擎推导的前景按新背景重新解（不算校正）。
6. 校正的用途：开发时打到控制台，皮肤管理面板显示「本皮肤有 N 处自动校正」。**内置皮肤不允许出现任何校正**（构建时检查）；运行时校正是给用户调参和将来的用户皮肤兜底。
7. 输出为具体颜色值写进 `k.tokens` 层，不依赖 `color-mix()`、相对颜色语法等较新的 CSS 特性。

压力测试（2026-10-27）：随机种子 × 明暗、高对比档、随机覆盖任意颜色令牌，共 20,000 个方案，**不达标 0 个**；单个方案平均 0.48 毫秒，可以在运行时实时计算（例如用户拖动强调色取色器）。

### 5.6 组件令牌

- 组件只引用语义令牌，例如按钮默认 `background: var(--k-control); color: var(--k-on-control)`。
- 皮肤改组件配色**按对改**：在 `skin.json` 里写 `"components": { "button": { "tone": "accent-soft" } }`，引擎同时设好背景和前景。
- 要在组件上写具体颜色值只能在部件 CSS（L3）里写，并且要过第 14 节的实际渲染对比度检查。

### 5.7 非颜色令牌

圆角阶梯、间距阶梯（随密度变化）、字号阶梯（乘以用户字号缩放）、行高、边框宽度、阴影 / 辉光层级、动效时长与缓动（随动效设置变化）。层级（z-index）由平台管理，不是令牌。

**分设备的排版与间距**（电脑与手机的最佳排版不同，不是简单缩放；以酒馆单栏断点 1000px 为界）：

| 令牌 | 电脑 | 手机 | 用途 |
|---|---|---|---|
| `--k-read-size` / `-lh` / `-measure` / `-para` | 16px / 1.8 / 42em / 0.9em | 16.5px / 1.75 / 100% / 0.75em | 正文阅读：字号、行高、行长、段距 |
| `--k-gap-section` / `-group` / `-item` | 28 / 16 / 10px | 16 / 12 / 8px | 分节、分组、条目间距 |
| `--k-pad-panel` / `-card` | 24 / 16px | 16 / 14px | 面板与卡片内边距 |

皮肤在 `skin.css` 里覆盖这些变量即可（放进 `@media (max-width: 1000px)` 就只改手机）。

### 5.8 用户设置

明暗（浅 / 深 / 跟随系统）、密度（紧凑 / 适中 / 宽松）、动效（完整 / 平静 / 关闭，并尊重系统「减少动态效果」）、字号缩放、特效开关、皮肤参数。设置按皮肤分别保存，切换皮肤时恢复该皮肤自己的值。

## 6. 皮肤包

```
src/skins/<id>/
  skin.json     清单（必需）
  skin.css      部件 CSS（可选，L3）
  assets/       静态图片（可选，L4）
```

### 6.1 四级定制

| 级别 | 能做什么 | 写在哪 | 检查 |
|---|---|---|---|
| L1 种子 | 换基调色、强调色、圆角、字体、层次风格 | `skin.json` → `schemes.<方案>.seeds` | 令牌对比度 |
| L2 令牌覆盖 | 直接指定某个语义令牌或某个组件的配色对 | `skin.json` → `schemes.<方案>.tokens` / `components` | 同上（覆盖后的对也要达标） |
| L3 部件 CSS | 针对公开钩子重画外观：形状、边框、材质、纹理、动效 | `skin.css` | 钩子与属性白名单 + 实际渲染对比度矩阵 |
| L4 装饰与素材 | 在装饰槽里画图形、挂图片、启用装饰模块 | `skin.json` → `ornaments` / `assets` + `skin.css` | 装饰不挡字、不拦截点击、可关闭 |

### 6.2 `skin.json` 字段

| 字段 | 说明 |
|---|---|
| `id` / `name` / `version` / `contract` | 标识、显示名、皮肤版本、遵循的契约版本（如 `"1.0"`） |
| `description` / `author` / `credits` | 介绍、作者、素材来源与授权 |
| `schemes` | **必须同时有 `light`（浅色）与 `dark`（深色）**，可以再加更多（键名为配色 id，例如 `reading`，须写 `base`（基于哪一档推导）与 `name`）；每个含 `seeds`、可选 `tokens`、`components`。渲染面根上 `data-k-scheme` 是配色 id，`data-k-mode` 是明暗 |
| `defaultScheme` | 默认配色方案 |
| `effects` | 可开关的特效：`id`、名称、说明、分组、默认值；开启后渲染面根的 `data-k-effects` 里带上该 id |
| `params` | 可调参数：类型（`color` / `number` / `enum`）、范围、默认值、绑定的令牌或 CSS 变量；`color` 类参数同样过对比度引擎 |
| `assets` | 图片表：`file` 是包内 PNG / WebP（必需，有单张与总量预算），可选 `url` 是 https 外链（6.6）；以 `--k-asset-<名>` 提供 |
| `fonts` | 外链字体（6.6）：`family`、`src`（一个或多个 https 地址）、可选 `weight` / `style` / `unicodeRange` |
| `ornaments` | 使用哪些装饰槽 |
| `modules` | 启用哪些**平台动效模块**（6.5），例如 `["fracture"]`；皮肤定义了同名特效时，由该特效开关控制 |
| `icons` | emoji → 图标映射（6.7） |
| `flavor` | 风格文案：只能填功能方声明过的风格槽位（第 11 节） |

### 6.3 `skin.css` 规则

- 引擎自动包进 `@layer k.skin`，作者不写 `@layer`。
- 选择器必须从公开钩子出发（第 4 节）；不能选中酒馆的元素（也选不到：在 Shadow DOM 里）。
- **禁止**：`!important`、`@import`、`@font-face`（Shadow DOM 里不生效；外链字体在清单 `fonts` 里声明）、`@layer`、在 CSS 里直接写外部 URL（只允许 `data:` 的 SVG / PNG / WebP；外链图片在清单 `assets` 里声明，用 `var(--k-asset-*)`）。
- 结构属性（`position` / `inset` / `top` 等 / `z-index` / `display` / `overflow` / `pointer-events` / `visibility` / `float` / `contain`）**只能写在装饰槽或 `::before` / `::after` 上**；渲染面与面板类组件（面板、对话框、抽屉、弹层）不许 `transform`。
- 实现：`src/frontend/skin-engine/lint-css.ts`（构建期）。
- 颜色属性可以写，但会进实际渲染的对比度检查（第 14 节）。

### 6.4 装饰槽

平台在固定位置提供装饰槽 `[data-k-ornament="<槽名>"]`：不可交互、`aria-hidden`、`pointer-events: none`、限制在所属组件的边界内。初始槽位：面板头部左右、卡片角、空状态插图、背景、分隔线、骰子位。槽位清单以 `parts.json` 为准。JS 装饰模块（骰子）由平台注册和管理生命周期，皮肤只声明启用。

### 6.5 平台动效模块

有些动效靠 CSS 做不出来（需要许多各自运动的元素），由平台用 JS 实现成模块，**皮肤只声明启用、用 CSS 变量调参**，皮肤本身仍然不含 JS。
模块由平台负责性能与生命周期：挂在每个渲染面的 Shadow DOM 上（事件委托），随渲染面销毁。

| 模块 | 效果 | 参数（CSS 变量） | 给皮肤的状态钩子 |
|---|---|---|---|
| `fracture` 碎裂溢光 | 按下（按钮、开关、复选框、选择卡、下拉触发器；**触屏上是真正点按才算**：手指移动超过 10px、按太久或被判定为滚动都不触发）以及展开 / 收起、弹出（折叠卡、对话框、下拉弹层、面板）时，组件边缘碎成方块，先在边缘停一瞬再飞散，碎块背后透出光 | `--k-fx-size` 碎块边长、`--k-fx-glow` 溢光色、`--k-fx-strength` 强度 0~1、`--k-fx-spread` 飞散距离 | 爆裂进行中组件带 `data-k-fx="active"`（皮肤可借此隐去边线，让「碎掉的边」由碎块接替） |

性能约束（必须满足，`test/frontend/browser/fx-perf.mjs` 实测）：碎块来自预先建好的对象池并复用；只动 `transform` 与 `opacity`（Web Animations，合成器线程）；
一次爆裂的碎块数有上限、手机上更少更大；同一元素 120ms 内不重复触发、同时进行的爆裂有上限；动效「平静」只留溢光、「关闭」与系统减少动态效果时完全不播。

### 6.6 外链资源（字体、图片）

允许外链，**但必须有失效时的兜底**，并由平台加载（`src/frontend/runtime/remote.ts`，测试 `test/frontend/browser/remote.mjs`）：

| 资源 | 怎么声明 | 兜底 | 平台怎么加载 |
|---|---|---|---|
| 字体 | 清单 `fonts`；在 `seeds.font` 的字体栈里引用它的 `family` | 字体栈**必须以通用字体族结尾**（`serif` / `sans-serif` / `monospace` / `system-ui` …），清单校验强制 | 用宿主文档的 `FontFace` 在酒馆主页面注册（Shadow DOM 里的 `@font-face` 不生效）；先显示系统字体，加载成功才替换；失败或超时（4 秒）就一直用系统字体 |
| 图片 | 清单 `assets.<名>.url` | 同一项的 `file`（包内文件，必需） | 先用包内文件立刻显示；后台试外链，成功且期间没换皮肤才换上 |

- 外链一律 https；同一资源一次会话只请求一次。**外链不能阻塞界面、不能让文字消失。**
- 建议：优先选国内可达的 CDN；中文字体体积大，用 `unicodeRange` 分片（例如常用字一片、其余一片）；在 `credits` 里写明字体授权（必须允许网页嵌入）。
- 注意隐私：外链请求会把用户 IP 暴露给资源所在的服务器，皮肤说明里应写明用了哪些外链。

### 6.7 emoji → 图标映射

预设条目名只能写 emoji（编辑预设时输入不了图标），所以由皮肤决定怎么显示：

- 平台扫描预设条目名，列出全部 emoji 与举例条目：`src/frontend/ds/icons/preset-emojis.json`（`node build/frontend/scan-emojis.mjs`，改了条目名后重跑）。
- 皮肤在清单 `icons` 里给映射：值是**平台图标名**（`src/frontend/ds/icons/registry.ts`，Lucide 精选，ISC 许可），或 **`data:image/svg+xml` 的 SVG**（用遮罩画，跟随 `currentColor`，配色仍由令牌决定）。
- 条目名里**任何位置**的 emoji 都按映射显示（开头的是前置图标，中间 / 结尾的画成行内小图标并和前一个字一起换行）。
- 没映射的照常显示 emoji；原 emoji 保留在悬停提示里。构建时报告内置皮肤还没映射的 emoji（只提示不拦）。
- 平台界面自己的标签（面板分类等）直接用图标，不走映射。

## 7. 皮肤分发协议

1. 皮肤脚本是唯一写入者：根据当前皮肤、配色方案、用户设置合成「令牌 CSS + 皮肤 CSS + 素材 CSS」。
2. 每个文档只建一份可构造样式表，被该文档里所有 Shadow DOM 根共享（不支持时回退为每个根一份 `<style>`）。
3. 渲染面挂载时向运行库登记；皮肤变化时运行库广播 `kami:skin-changed`（带修订号），所有根同步更新属性与样式表。
4. **兜底**：运行库内置默认皮肤。皮肤脚本没开或出错时，所有前端仍按默认皮肤显示，不会出现无样式的界面。
5. 旧系统的皮肤选择与设置不迁移，升级后统一落到新的默认皮肤。

## 8. 挂载与生命周期

### 8.1 通用

- 每次挂载都返回一个销毁函数；脚本卸载、聊天切换、消息被删除时必须销毁，不留监听、定时器、观察器或节点。
- 运行库对外暴露带语义化版本的 API；功能脚本声明需要的版本范围，不匹配时给出可读的错误提示，不白屏。

### 8.2 S1 宿主浮层

- 只有一个 `<kami-layer>`；面板、对话框、提示都通过运行库打开，弹层统一 portal 进它内部。
- 面板几何由平台决定：宽屏是可拖动、可缩放的浮动窗；**窄屏（与酒馆自己的单栏断点一致，≤1000px）是贴底抽屉**。规则在 `k.lock`。
  - 浮动窗：标题栏拖动、右下角拖动或方向键缩放；拖出视口、窗口变小时自动收回（标题栏始终可见）；几何由使用方保存（`onGeometryChange`）。
  - 抽屉：从标题栏下拉、或内容区**滚到顶后**从内容区下拉，超过高度的 1/4 或快速下甩即关闭，否则回弹；内容没滚到顶时下拉只滚内容。关闭按钮始终可用。
  - 触屏手势（`ds/gestures.ts`，沿用旧版 `_panel-gestures.js` 的做法）：只挂 touch 事件，不用 pointer 事件（浏览器判定滚动后会发 pointercancel）；先判方向，横向才 `preventDefault`。
    面板里开了 `swipe` 的页签：内容区左右滑翻页（到头停住），页签条随之把当前页签滚进视野；起点在页签条、输入控件、`data-k-swipe="off"` 区域上不接管。鼠标不接管任何手势。
  - 面板是非模态的（酒馆照常可用）；`Esc` 关闭。拖动不用 `setPointerCapture`（它会吃掉后续点击的目标）。
  - 实现：`src/frontend/ds/components/panel.tsx`、`ds/geometry.ts`；交互测试 `test/frontend/browser/panel.mjs`（鼠标 / 键盘）与 `touch.mjs`（触屏）。

### 8.3 S2 消息挂载

依据：2026-10-27 在本机测试酒馆（SillyTavern 1.18.0 + 酒馆助手 4.11.3）实测，见附录 C。

- **标记**：正则把 `<标签>…</标签>` 替换成 `<div data-kami-mount="<种类>" data-kami-v="1">$1</div>`。`$1` 只作**兜底显示**（运行库不可用时用户仍能看到原文）。
  - 标记只用 `data-*` 属性识别，**不依赖 class**（酒馆会把 class 改名，例如 `kami-mount` → `custom-kami-mount`）。
  - 不用自定义标签、`<script>`、`<summary>`（都会被清洗掉）。
- **载荷只从聊天原始数据读**：挂载服务由标记找到所在消息（`.mes[mesid]`），读 `chat[mesid].mes` 原文，取同种标签的第 n 次出现。
  **绝不从渲染后的 DOM 文本取载荷**：消息文本会经过 Markdown 处理（例如双引号被包成 `<q>`），JSON 等结构化内容会被破坏。
- **挂载**：在标记上 `attachShadow` 后渲染；Shadow DOM 不带插槽，标记里原有的兜底文字自动不再显示，不需要另外隐藏。
- **重绘自动重挂**：酒馆整段重载聊天、单条消息重绘（编辑、`updateMessageBlock`）都会换掉标记节点。挂载服务用 `MutationObserver` 观察聊天区，
  按「消息 ID + 序号」**幂等**挂载，新节点出现就重挂；旧节点上的 React 根必须卸载。
- **流式生成**：~~生成期间只显示轻量占位，生成结束后一次性挂载~~ → **用户拍板 E：生成期间就用我们的排版逐步渲染**。
  解析器容忍未闭合的标签 / 对白 / JSON（`src/frontend/message/parse.ts`），视图按「这条消息的当前原文」随时重画。
  真实酒馆里怎么拿到生成中的原文、怎么在酒馆每次重绘消息时不重建 React 根，**待在测试酒馆实测定稿**（预览里是模拟的流）。
- 还要验证：切换回复（swipe）、删除消息时的清理、长聊天（上百个挂载点）的性能。

**关于酒馆助手**：上面的清洗规则只约束「正则输出的那段 HTML」。酒馆助手本身能绕过酒馆的限制，社区生态就建立在它之上：

| 酒馆助手的能力 | 说明 | 本契约怎么用 |
|---|---|---|
| 脚本访问酒馆页面 | 脚本跑在隐藏 iframe 里，但能直接读写酒馆主页面的 DOM、调用酒馆与酒馆助手的 API | **默认通道**：挂载服务就是这样给消息里的标记挂 Shadow DOM 的 |
| 消息 iframe 渲染 | 消息里的 html 代码块被渲染成完整 iframe（任意 HTML / CSS / JS、自动调高度、流式生成时也能渲染）；旧版卡密前端与社区「前端卡」都用它 | **备选通道**：需要流式实时渲染、或要与社区前端卡共存时考虑。代价：每个 iframe 是独立文档，Radix 无法从父页面跨文档渲染（附录 A），iframe 里要么自带一份运行库（体积与解析成本按消息数放大），要么只做不依赖 Radix 的轻量界面 |

选哪个通道按实际需要定；如果默认通道挡住了皮肤或功能的设计，按本契约开头的原则修订。

### 8.4 S3 原生增强

不移动、不删除、不改写酒馆自己的控件和交互语义（例如原生思维链块的折叠仍由酒馆的 `details` 负责）；我们的界面放在内部的 Shadow DOM 宿主里。

## 9. 布局与响应式

- 断点只有一处定义（与酒馆单栏断点一致）；组件内部排版用**容器查询**（按面板宽度，不按视口）。
- 最小支持 320px 宽，不出现整页横向滚动；窄屏触控目标至少 40px（推荐 44px）；处理安全区与 `dvh`。
- 字号放大后布局仍可用。

## 10. 交互与无障碍

- 所有操作都能用键盘完成；焦点环清晰可见（对比度 ≥ 3 : 1）；对话框锁定焦点、关闭后焦点回到触发处；`Escape` 关闭。
- 手势（例如下拉关闭抽屉）一定有等价的按钮。
- 异步状态用实时播报区域；动效遵守动效设置与系统「减少动态效果」。

## 11. 文案归属

- 功能文案（按钮、提示、错误、空状态、计数）归功能模块，放在各功能的 `copy.ts`，皮肤不能改。
- 功能模块可以声明**风格槽位**（例如思维链标题），皮肤在 `flavor` 里填写；没填就用默认文案。

## 12. 安全

- 皮肤不含 JS。外部资源只能经清单声明、由平台加载，并且必须有包内或系统兜底（6.6）；包内素材受体积预算限制。
- 模型输出与载荷一律按文本渲染；Markdown 经过净化后才渲染；链接只允许 http(s)，新窗口打开时带 `rel="noopener"`。
- 除了净化后的 Markdown，不使用 `innerHTML`。

## 13. 性能预算

- 运行库与整份预设的体积有预算（数值在第一版设计系统完成后确定）。
- 每个文档只有一份共享样式表；消息挂载要轻（长聊天里可能有上百个挂载点），屏幕外的装饰动画暂停。
- 除了登记过的装饰模块，不跑逐帧 JS 动画。

## 14. 验收与自动化

| 检查 | 时机 | 内容 |
|---|---|---|
| 类型检查 | 构建 | `tsc --noEmit` |
| 皮肤清单与 CSS 检查 | 构建 | 清单结构、钩子存在、禁用属性、`!important`、外部资源 |
| 令牌对比度 | 构建 | 每套皮肤 × 每个配色方案的全部配对；内置皮肤不允许任何自动校正 |
| 实际渲染对比度矩阵 | 浏览器（Playwright） | 每套皮肤 × 明暗 × {320, 390, 1440}px × 每个组件的每种状态：读计算样式，按实际叠加后的背景算对比度 |
| 交互与隔离 | 浏览器 | 鼠标、键盘、触屏冒烟；敌意宿主样式下的隔离（沿用 `spikes/radix-isolation`） |
| Radix 修补守卫 | 构建 | 修补点数量核对；升级 Radix 必须重跑隔离验证 |
| 真机清单 | 交付前 | 手机上逐项确认（清单随功能补充） |

## 附录 A：技术验证结论（2026-10-27）

代码与运行方法见 `spikes/radix-isolation/`。宿主页模拟酒馆与用户自定义 CSS 的强硬全局样式（`button`、`*` 字体、弹层角色都带 `!important`）。

| 场景 | 结果 |
|---|---|
| 宿主页 Shadow DOM，无修补 | 样式完全隔离；鼠标正常；**键盘焦点失灵**（对话框焦点陷阱、菜单键盘稳定失败，下拉键盘间歇失败） |
| 宿主页 Shadow DOM，两处修补 | **20 / 20，连续 5 次稳定**；手机触屏 7 / 7；修补对普通 DOM 无回归 |
| 父页面 React 渲染进同源 iframe | **不可行**：下拉一点开就关，后续卡死（Radix 依赖全局 window / document） |

两处修补：① 打包产物里的 `document.activeElement` 换成钻进 Shadow DOM 取真实焦点的读取器；② FocusScope 的 `focusin` / `focusout` 监听从 `document` 改到容器所在的根节点。
