# 卡密预设 · 皮肤契约 v0.1

> 本文件是「皮肤管理脚本」、所有前端、以及所有皮肤设计/实现的**唯一接口规范**。
> 冻结后改动需要同步：皮肤管理脚本、两个正则前端、预设设置面板、引导面板、以及全部皮肤包。
>
> 想加新东西之前，先看 [功能复用](功能复用.md)：那里登记了**已经有一份实现**的零件与扩展检查清单。
> 本文件管「接口长什么样」，那份管「东西在哪、该复用谁」。

---

## 0. 一句话架构

```
前端(HTML结构 + 行为 + 类名)    ← 固定，不含任何外观数值
        ×
皮肤(一整份组件 CSS + 令牌值)   ← 唯一的外观来源，可整体替换
        ↓
皮肤管理脚本(把选中的皮肤 CSS 下发到酒馆页面 + 每个消息 iframe)
```

**硬规则：前端不写任何 color/background/border/font/尺寸/动画 规则；皮肤写全部外观。**
前端只负责：DOM 结构、类名、状态属性、事件、以及把动态数据写成属性或 CSS 变量。
**这条硬规则有登记在案的例外**（前端不得不写的那几行：宿主要素重置、定位包含块、去 UA 默认外观、高度自保）——
全在 **§9 例外清单**里，动手改前端或写审计报告之前先读那一节。

## 1. 生效与兜底（两条互斥的作用域）

皮肤管理脚本会在酒馆页面与每个消息 iframe 的 `<html>` 上设置：

| 属性 | 取值 | 含义 |
|---|---|---|
| `data-kami-skin` | 皮肤 id，如 `trpg` / `rain` / `nixie` | 当前皮肤；**不存在 = 皮肤管理未运行** |
| `data-kami-scheme` | `dark` / `light` | 明暗方案（皮肤可据此换配色，也可忽略） |
| `data-kami-effects` | 空格分隔的特效 id，如 `scanline grain` | 已开启的特效 |
| `data-kami-motion` | `full` / `calm` / `off` | 动效档位（用户在面板里调） |
| `data-kami-density` | `compact` / `cozy` / `roomy` | 密度档位（用户在面板里调） |

- **兜底皮肤**：写在每个前端自己的 `<style>` 里，作用域 **`html:not([data-kami-skin]) .kami-root { … }`**。
  皮肤管理脚本一运行（`<html data-kami-skin>` 出现），兜底 CSS **立即整体失效**，由皮肤 CSS 完全接管。
- **皮肤 CSS**：作用域 **`html[data-kami-skin="<id>"] .kami-root { … }`**（组件规则可以更具体）。
- 所以：同一份皮肤 CSS 必须**同时**能用在「酒馆页面里的脚本面板」和「消息 iframe 里的内嵌前端」，不得依赖任何只在其中一边存在的上下文。

- **~~全局层（第三种作用域）~~ —— 已整体退役（2026-09-26，用户裁定「连外壳层美化也不需要，我们不动酒馆本身了」）**：
  曾经有一份 `src/skin/tavern.css`，作用域是 `html[data-kami-skin]`（不带 `.kami-root`），
  只作用于**酒馆自身 UI**（聊天消息区 `#sheld` / `#chat` / `.mes` / `.mes_text` 的底色、圆角、间距、字体），
  由 30-皮肤管理.js 注入 `<style id="kami-tavern">`。
  这条线走了四轮（通用底 → 面与特效镜像 → 只留外壳 → 连外壳也删），**两轮效果被用户否**，
  最终**整个文件删除、注入与收回代码删除**。现在：
  - **全项目没有任何规则碰酒馆 UI**：所有选择器都落在 `.kami-root` 里（面板 / 引导 / 三个嵌入式前端）。
  - 产物里搜 `kami-tavern` / `TAVERN_CSS` / `#chat {` / `.mes_text {` 全是 **0 次**。
  - **教训**：用户要的是「我们自己的东西（面板 / 引导 / 前端组件）由皮肤管」，不是「把酒馆改造成皮肤」。
    以后要动酒馆自身 UI，先问。
  - ⚠️ 但**令牌上提保留着**（见 §3）：它是结构性的（皮肤把组件面专用令牌的重映射写在 `.kami-root` 上，
    不上提兜底皮肤读不到），与「美化酒馆 UI」无关。
  - 结构例外（§9.8 全局层那两条）随之作废，留档备查。

## 1.5 前端源码禁忌（酒馆正则引擎的真实语义）

酒馆 1.18 的替换**不是** native `String.replace(regex, str)`，而是 
`public/scripts/extensions/regex/engine.js:419-445` 里的回调写法：

```js
rawString.replace(findRegex, function (match) {
  replaceString.replaceAll(/$(d+)|$<([^>]+)>/g, ...)   // 只认 $n 与 $<name>
  return substituteParams(replaceWithGroups);            // 末尾还会跑一遍宏替换
});
```

由此得出三条**硬规则**（构建期会强制检查，违反直接构建失败）：

1. **前端文档里不得出现 `$` 后跟数字、或 `$<`**（那是捕获组语法）。
   需要用到 `$` 时，用 `String.fromCharCode(36)` 生成，
   或把字符串替换写成**函数式**（`replace(re, function (m, g) { ... })`）。
2. **不得把正文的 `$` 双写成 `$$`** —— 酒馆**不还原** `$$`，
   只会原样留下，并且 `$$1` 还会被读成「`$` + 捕获组」。
3. **不得出现双花括号宏 `{{...}}`** —— 替换结果最后还会过一遍 `substituteParams`，
   `{{char}}` 之类会被当成酒馆宏吃掉。

以上三条由 `node build/verify-frontends.mjs` 按酒馆的逐字语义重放并强制检查
（已接进 `build.mjs`，不通过则构建中止）。

## 2. 皮肤作者硬规则

> 下列 8 条是皮肤 CSS 的纪律清单。其中可机械判定的部分由 `node build/lint-skins.mjs` 检查，
> 逐条对照见 §7；不通过就没有资格进入构建产物。
> （§0 那条「前端不写外观」的登记例外**不在本清单里**，见 §9。）

1. **选择器必须含 `kami`**：皮肤 CSS 的每一条选择器都必须包含 `kami`（类名、属性或变量作用域），
   绝不触碰酒馆自身的 UI（`#chat`、`.mes`、`body`、`.qr--button` 等一律禁止裸选）。
   > **全局层例外 —— 已作废（2026-09-26）**：以前这里为 `src/skin/tavern.css` 开过一个口子
   > （平台级规则可以 `html[data-kami-skin] #chat` 这样碰酒馆 UI）。那份文件与整套全局层
   > 已按用户裁定**整体删除**（§1 那一条），**口子随之关闭**：现在**任何地方**都不许碰酒馆 UI，
   > 没有例外。`lint-skins.mjs` 里那条「全局层 `<html>` 令牌作用域显式豁免」保留着 ——
   > 它是给**令牌上提**用的（皮肤末尾生成块里的 `html[data-kami-skin="x"] { --kami-* }`），
   > 那不是酒馆 UI 规则，是结构与配色，必须留。
2. **CSS-only**：皮肤包**不得**包含 JS、不得引用任何外部网络资源（字体/图片/CDN）、不得使用 `@import`。
   允许：内联 SVG 的 `data:` URI、`mask`、`clip-path`、`filter`、`mix-blend-mode`、`backdrop-filter`、
   `@keyframes`、`@property`、`@container`、`:has()`、`conic/radial/linear-gradient`、`text-shadow`、3D transform。
   *（理由：皮肤 CSS 会被注入到**每一个聊天楼层**的 iframe 里，一个楼层一份；任何 JS 运行时/外部请求都会
   造成按楼层线性增长的开销与断网风险。）*
3. **不得使用 `vh` 做 min-height**：消息 iframe 的高度由 `body.scrollHeight` 决定，
   且酒馆助手会重写 `min-height:*vh`。用 `aspect-ratio`、`%`、或令牌里的固定值。
4. **不得依赖滚动**：消息 iframe 的 `html,body` 被强制 `overflow:hidden`，前端内部必须自己撑高。
5. **不得使用 `position:fixed` 铺满**：会跑出 iframe 可视区。要浮层就在组件内部做 `position:absolute` + 容器 `position:relative`。
6. **移动端优先**：所有布局必须先在 320px 宽下成立；多列用 `repeat(auto-fill,minmax(var(--kami-items-min),1fr))` 之类自适应，禁止固定像素宽。
7. **可访问性**：焦点必须可见（`:focus-visible` 要有明确样式）；`prefers-reduced-motion: reduce` 时把
   动效时长压到 1ms；正文对比度不低于 4.5:1（对 `--kami-bg` 实际合成色计算）。
8. **性能**：单楼层 CSS 中 `blur/backdrop-filter` 使用面积要克制；`filter`/`backdrop-filter` 不得出现在动画的每一帧上；
   长列表避免 `will-change` 滥用。

## 3. 令牌（CSS 自定义属性）

皮肤必须为**全部**令牌提供取值（可只给一部分，其余继承兜底？—— 不行：皮肤生效时兜底 CSS 不匹配，
所以**皮肤必须给全**。缺失的令牌会在验证脚本里报错）。

> **令牌同时定义在 `<html>` 上（2026-09-25，全局层地基）**：每套皮肤除在 `html[data-kami-skin="<id>"] .kami-root`
> 上给全令牌外，`build/sync-tavern.mjs` 还会把同一批 `--kami-*` 声明**复制一份到 `html[data-kami-skin="<id>"]`
> （`<html>` 作用域，含 `[data-kami-scheme]` / `[data-kami-density]` / `[data-kami-motion]` 各档位变体）**，
> 供 §1 的全局层在酒馆 UI 上继承。这是**唯一需要 15 套皮肤同步的点**，由幂等脚本 `build/sync-tavern.mjs`
> 完成（跑两次结果一致；改动 `src/skin/tavern.css` 或皮肤后重跑一次即可，第 16 套皮肤同理自动跟随）。
> `build/lint-skins.mjs` 有一条正向检查（`<html>` 作用域里必须看得到 `--kami-fg`）抓着「漏跑同步 / 手删生成块」。
> `.kami-root` 层行为不变——脚本只**追加**一份 `<html>` 副本到皮肤末尾的「生成块」，不改写任何既有规则。

### 3.6 用户可调参数（**所有皮肤必须支持**）

皮肤管理面板会提供下列全局旋钮，皮肤必须让它们真的起作用：

| 旋钮 | 下发方式 | 皮肤必须做到 |
|---|---|---|
| 字号缩放 | 令牌 `--kami-fs-scale`（默认 1） | `--kami-fs: calc(<你的基准> * var(--kami-fs-scale))`，其余派生字号基于 `--kami-fs` |
| 明暗方案 | `<html data-kami-scheme="dark\|light">` | 给出两套取值（可忽略，但要在方案里说明） |
| 动效档位 | `<html data-kami-motion="full\|calm\|off">` | `calm` 至少把时长降一档、去掉循环动画；`off` 必须全部压到 1ms 且无位移 |
| 密度档位 | `<html data-kami-density="compact\|cozy\|roomy">` | 用属性选择器覆盖自己的 `--kami-pad-*` / `--kami-gap*` / `--kami-row-h` |

### 3.7 文案：功能性 vs 风格性（**机制，不是清单**）

文案分两类，按**谁渲染**划线，而不是按内容划线：

| 类别 | 归属 | 能否被皮肤覆盖 |
|---|---|---|
| **功能性文案** | **前端写死** | **不能** |
| **风格性文案** | 皮肤（用令牌） | 能 |

**功能性文案** = 组件自带的那几个 UI 说法，用户在哪套皮肤下都得看懂同一个动作：
渲染 / 原文、填入 / 发送、复制、N 项、N 字、空态、示例与失败提示。
这些由前端直接渲染，皮肤既不能提供也不能覆盖。

**风格性文案 = 机制（重要）**

前端**不再把风格性槽位写死在代码里**，而是用属性声明；皮肤用同名令牌覆盖：

    <span class="kami-title" data-kami-label="think-title" data-kami-label-open="think-title-open">思维链</span>

- 元素带 data-kami-label="<slot>" → 该元素的文字是**风格性**的；
  皮肤用 --kami-label-<slot> 提供文案，前端在运行时读计算样式并写入。
- 元素带 data-kami-label-open="<slot>" → 该槽位在**展开态**使用另一个令牌；
  皮肤没提供时回退到 data-kami-label 指定的那一个。
- 皮肤没提供令牌时，前端使用元素原本写在 HTML 里的默认文字（中性措辞）。
- **契约只固定「命名法与读取规则」，不固定槽位清单。** 前端以后新增任何风格性槽位，
  只要加一个 data-kami-label="xxx" 属性即可，皮肤写 --kami-label-xxx 就能覆盖 —— 两边都不用改契约。
  槽位名用 kebab-case，带组件前缀（think- / options- / guide- …）。
- 目前已有的槽位（会持续增加）：think-title、think-title-open、options-title。

> **例外**：skin.json 里的 effects[].label / effects[].desc 与 params[].label / params[].group / params[].unit
> **归皮肤自己所有** —— 每套皮肤的特效与参数本来就是它独有的，名字与说明也只能由它给，无法也不该统一。
> 只要求写清楚「它到底做什么」，不玩梗、不写成诗句（最终措辞由专职文案 Agent 统一打磨）。

> **禁用令牌清单（功能性文案，任何皮肤都不得定义）**
> 前端读文案有两条路径：`[data-kami-label]` 属性那套（风格性，见上），以及代码里点名读取的令牌（功能性）。
> 功能性那套一旦被皮肤定义，就会顶掉写死在前端里的文案，四套皮肤的说法立刻不一致 ——
> 所以下面这些令牌**只在契约里登记，不许出现在任何 `skin.css` 里**：
>
> `--kami-label-empty`（空态）、`--kami-label-chars`（字数单位）、
> `--kami-label-unit`（项数单位）、`--kami-label-demo`（示例标记）、
> `--kami-label-filled`（已填入）、`--kami-label-noinput`（未找到输入框）、
> `--kami-label-sent`（已发送）、`--kami-label-sendfail`（发送失败）。
>
> 操作提示（「轻点卡片即可生效」／「轻点卡片直接发送」）同样写死在前端里，**没有可覆盖的令牌**。

### 3.8 皮肤自定义参数（可选）

皮肤包可以声明自己的数值参数，面板会自动生成「折叠分组 + 滑杆 + 数字输入框」：

```js
params: [
  { id: 'glow', label: '辉光强度', group: '氛围', token: '--kami-glow-size', unit: 'px',
    min: 0, max: 24, step: 1, value: 8 },
  { id: 'grain', label: '颗粒量', group: '材质', token: '--kami-grain', unit: '%',
    min: 0, max: 100, step: 5, value: 35 },
]
```

管理器把它们写进一份**后置**的 `<style id="kami-skin-user">`（作用域与皮肤相同，靠文档顺序取胜），
所以皮肤只要把参数接到某个令牌上即可。**参数一律要有合理的默认值**。

> ⚠️ **`unit` 不是纯显示字段**：皮肤管理会把它**直接拼进 CSS 值**（`30-皮肤管理.js` 里 `v + (p.unit || '')`），
> 所以它必须是**合法 CSS 单位**（`px` / `%` / `deg` / `em`…）或**空串**，绝不能写成显示用的符号。
> 写成 `×` 会让 `calc(... * 1×)` 变成非法值、整条 `width`/`height` 声明被丢弃
> （真机表现：骰子宽高归零、压住标题并被纸边裁掉）；写成 `°` 会让 `rotate(-1.2°)` 非法、
> 整条 `transform` 变成 `none`（印章既不倾斜也丢了 1px 错位）。`build/lint-copy.mjs` 的 `checkUnit` 拦这类值。
>
> 顺带记住这个不一致：平台自己的伪参数「字号缩放」写的是 `unit: '×'`，但它是**另一条专用代码**写 CSS 的
> （`--kami-fs-scale` 不带单位），所以那个 `×` 只是显示。**同一个字段两种含义** —— 改参数文案时务必留意。

### 3.9 语义色（按数据类型着色）
前端只输出 `data-kami-kind="…"`，颜色由皮肤给：
`--kami-kind-action`（行动）、`--kami-kind-persona`（性格）、`--kami-kind-plot`（推进）、
`--kami-kind-info`（信息）、`--kami-kind-fun`（搞笑）、`--kami-kind-nsfw`（nsfw）、`--kami-kind-other`（其他）。

### 3.10 透明度阶梯（**可选令牌**：前端带兜底值，皮肤可以不定义）

引导向导的排版层需要"关态压淡 / 禁用压淡"两种效果。§3.1–§3.4 里没有能表达整块元素透明度的令牌，
而排版层又不许写死数值（用户裁定：只做排版、外观全走令牌），所以这里补两个**可选**令牌：

| 令牌 | 含义 | 前端兜底值 |
|---|---|---|
| `--kami-dim-soft` | 关态压淡（如未选中的选项卡） | `.62` |
| `--kami-dim-lock` | 禁用 / 锁死压淡（如非当前模型名下的条目、禁用的主按钮） | `.38` |

- **前端写法**：`opacity: var(--kami-dim-soft, .62)` —— 令牌缺失时用兜底值，皮肤一旦定义就整体接管。
- **皮肤可以不定义**：这两个不在 `lint-skins.mjs` 的必覆盖清单里（那份清单是从 `src/skin/base.css` 抽的），
  所以不定义**不会**构建失败，也不要求六套皮肤同步补值。想统一"压淡到什么程度"的皮肤，
  在自己的令牌块里写一行 `--kami-dim-soft: .55;` 即可。
- ⚠️ 它们只该用在"整块元素需要变淡"的地方。**文字变淡优先用现成的 `--kami-fg-dim` / `--kami-fg-mute`**
  （那是"次要文字/最弱文字"的正解，也比调透明度更可控）。

> 备注：`--kami-r-*` 阶梯里没有"零圆角"这一档。全屏向导需要四角贴边时，用 `border-radius:0!important`
> 压掉几何层的圆角，这是**登记在案的例外**（见 §9），不要为此新增令牌、也不要把向导改成圆角。

**所有皮肤（含兜底皮肤 `src/skin/base.css`）都必须给出「卡片开着」时的可视差别，且不得只靠颜色** ——
形状、边线、字重至少占一样。理由：同一颗 `button.kami-item.kami-card` 在皮肤管理、预设设置、引导向导、
压缩面板里是同一个开关，用户要靠同一套视觉语言认它；只靠颜色时，色觉差异用户与低对比度皮肤上等于没有反馈。
兜底皮肤漏了这条规则的表现是：皮肤管理没跑时，引导面板里的开关卡片开着也看不出来（2026-09-20 已清偿）。

### 4.3 状态钩子（前端保证，皮肤消费）

| 钩子 | 位置 | 含义 |
|---|---|---|
| `.kami-collapse[data-kami-open="0|1"]` | 折叠根 | 前端**只切属性**；显隐与进出动画全部由皮肤实现 |
| `data-kami-view="render|raw"` | 组件根 | 双视图切换；前端只切属性（两个视图的 DOM 始终保留） |
| `.is-done` | 按钮 / 卡片 | 一次性成功反馈（复制成功、已填入 / 已发送）；前端约 1200ms 后自行移除 |
| `data-kami-busy` | **触发元素**（组件根或那颗卡片/按钮） | 正在处理中（可选）。目前唯一实现是 `frontend-options.html` 的发送路径：把 `"1"` 写在**被点的卡片**上、完成时移除（`frontend-options.html:274-277`）。审计按旧文写的「只挂组件根」会误报，这里以实际实现为准 |
| `--kami-value` | `.kami-range` | 滑杆当前值归一化到 0–1，脚本在元素上写入 |

> **`data-kami-*` 是保留前缀，下列「内部标记」不参与外观** —— 皮肤不要依赖，审计也不要再当成「未登记属性」上报：
> `data-kami-ready="1"`（boot 幂等标记：两个前端 `frontend-think.html:181` / `frontend-options.html:305`，各面板同款）、
> `data-kami-default`（风格性文案的**原始文字存档**，`applyLabels()` 在第一次读令牌前写，见 §3.7）、
> `data-kami-timer`（复制按钮的反馈计时器句柄，`frontend-think.html:148-153`）、
> `data-kami-payload`（承载模型原文的 `script[type="text/plain"]`，两个前端的载荷入口）、
> `data-kami-md-engine`（思维链前端**这一条渲染实际用了哪套引擎**：`showdown` 或 `mini`，排障用；见 §9.6）。
> 另外 `data-kami-slot` / `data-kami-role` 是**槽位与角色的选择器钩子**（前端写、脚本自己读，例如 `[data-kami-slot="think-count"]`、
> `[data-kami-role="list|count|hint"]`），皮肤按类名消费即可，不要按它们写样式（值会随组件增加而变）。

**结构性兜底**（由皮肤管理脚本注入，位于皮肤 CSS **之前**，皮肤可用同优先级更高的规则覆盖）：

```css
.kami-collapse[data-kami-open="0"] > .kami-collapse-body { display: none; }
.kami-root[data-kami-view="raw"] [data-kami-view="render"] { display: none; }
.kami-root[data-kami-view="render"] [data-kami-view="raw"] { display: none; }
```

折叠内容**始终留在 DOM**（前端不得用 `hidden`/`display` 控制），否则皮肤无法播放收起动画。

### 4.4 面板专用

**几何契约（重要）**：脚本面板的“位置与尺寸”属于**状态**，由皮肤管理脚本下发，皮肤只负责“怎么摆”：

| 令牌 | 含义 |
|---|---|
| `--kami-panel-x` / `--kami-panel-y` | 面板左上角坐标（拖动时由脚本更新） |
| `--kami-panel-w` / `--kami-panel-h` | 面板尺寸（缩放时由脚本更新） |

- `.kami-root[data-kami-comp="panel"]` 是**铺满视口的定位舞台**，脚本保证它 `position:fixed; inset:0; pointer-events:none`；
- `.kami-drop` 是面板本体，脚本保证它 `pointer-events:auto`；**它的 left/top/width/height 由皮肤用上面四个令牌决定**；
- 脚本会在面板根上写入默认值（宽 420 / 高 560 / 居中 / 距顶 72），**皮肤可以不理会令牌、自己排版**（例如把它做成居中的卡片），但必须保证窄屏下是**贴底的底部抽屉**；
- 皮肤不得使用 `vh`，舞台已经是整个视口，用 `%` 即可。
- **皮肤管理面板的默认尺寸 v2（2026-09-25 增补）**：皮肤管理（30 号脚本）的桌面档默认宽高改为 **840×1120**（旧值 420/560 的两倍；`restoreGeometry` 的 `PANEL_DEF_W/H`，**只在脚本变量里没存过 `w/h` 时使用** —— 老用户存过自定义尺寸的继续用他们存的那套）。且加了两条**可视区约束**：① 尺寸夹取沿用 `min(vw-24)/min(vh-24)`；② 拖动 / 缩放 / 恢复时任何一边不得超出可视区（超出按可视区留边收回位置，`30-皮肤管理.js` 的 `restoreGeometry` 与 `pointermove` 夹取）。**预设设置 / 引导 / 压缩三块面板不在此列**（40/60 号脚本各自维护 `PANEL_W/PANEL_H = 420/560` 常量，引导是全屏向导）——皮肤令牌默认值也不变。手机档（`data-kami-layout="sheet"` 贴底抽屉）完全不受影响。
```html
<div class="kami-root" data-kami-comp="panel">
  <div class="kami-drop kami-surface" data-kami-open="1">
    <div class="kami-head">
      <span class="kami-title">皮肤管理</span>
      <span class="kami-actions">
        <button class="kami-icon-btn" data-kami-act="min">–</button>
        <button class="kami-icon-btn" data-kami-act="close">✕</button>
      </span>
    </div>
    <div class="kami-tabs">
      <button class="kami-tab" role="tab" aria-selected="true">皮肤</button>
      <button class="kami-tab" role="tab" aria-selected="false">参数</button>
    </div>
    <div class="kami-body kami-scroll">…</div>
    <div class="kami-foot">…</div>
    <!-- 尺寸把手（面板可拖动缩放） -->
    <span class="kami-resize" data-kami-act="resize"></span>
  </div>
</div>
```

**注释标记硬规则（2026-09 补，踩过坑）**：

1. `data-kami-note-mark` 的元素**必须与预设面板逐属性同构**：
   `span.kami-card-note`（文字 `ⓘ`）+ `data-kami-note-mark="1"` + `role="button"` + `tabindex="0"`
   + `aria-expanded="false"` + `aria-label`（展开后与 `aria-expanded` 一起翻成收起态）。
   原来用真 `<button>` 的面板换成 `span` 时**必须自己补键盘处理**（Enter / Space 触发同一次切换并 `preventDefault`），
   否则丢键盘可达性。
2. **注释标记与注释正文的皮肤规则一律不得用面板 id 限定**（禁止
   `…[data-kami-comp="panel"]#kami-preset-panel .kami-card-note[data-kami-note-mark]`），
   只写 `.kami-root[data-kami-comp="panel"] .kami-card-note[data-kami-note-mark]` /
   `… .kami-card-note[data-kami-note]` / `… .kami-card-note[data-kami-note][hidden]`。
   理由：面板不止 `#kami-preset-panel` 一块（还有 `#kami-guide-panel`），它们用的是**同一套 DOM**；
   写死 id 就一定会漏 —— 新面板上线时那条规则一条都匹配不上，表现是同一枚 ⓘ 在两块面板里长得不一样。
   这条同样适用于任何「多面板共用同一组件」的规则（`.kami-number` 对比度规则就是这么写的，见下）。

**多面板共用的组件，规则一律不得写死面板 id**（2026-09-20 补，第三条同类坑）：

1. 输入框对比度：面板里的 `.kami-number` 用的是同一个类名（`30-皮肤管理.js` / `40-预设设置.js` / `50-引导.js` 各自生成），所以每套皮肤只要**一条 panel 作用域规则**就能同时命中所有面板。
这条规则必须**显式写 `background-color` + `color` + `color-scheme`，并且三项都要 `!important`** —— 有两层东西会抢色：
① 用户酒馆的「自定义 CSS」（`power_user.custom_css`）给所有数字/文本输入框上了深色底与描边、自带 `!important`；
② 皮肤头部 `.kami-root input { color: inherit }` 把文字压成 `--kami-fg-dim`。两层不挡住就是"黑底配深字"。
**验证纪律**：`getComputedStyle` 的背景为**透明**时，往上层找背景算出的对比度是**假读数**；必须确认背景是非透明的显式值，并在真机读。
目标 ≥ 4.5:1（当前实测：memo 16.05 / nixie 7.17 / rain 13.70 / trpg 12.28 / 兜底 13.21）。

> **`.kami-number` 曾经不只用在一处 `<input type=number>` 上**（2026-09-21 补，当天即收口）：压缩面板把它用在 `select` /
> `textarea` / `input[type=text|password]` 上，后果有两个 —— ① 每套皮肤那条给数字框写的 `text-align:right` 被它们一起吃了，
> 摘要提示词的正文与角色下拉全部变成右对齐（用户真机报的）；② 用户酒馆的「自定义 CSS」对 `select` 与 `textarea` 各有一条
> `!important` 深漆，必须由皮肤的对比度规则挡住。
> **现行分工（2026-09-21 晚）**：`.kami-number` 只给 `input[type=number]`；文本 / 多行 / 下拉各用 `.kami-text` /
> `.kami-textarea` / `.kami-select`。**每套皮肤的对比度规则必须同时写这四类**（五套 + 兜底共六份，新增皮肤照这个写）。
> 另外那条 `text-align:right` 必须收窄成 `input.kami-number[type="number"]`，不要再挂在裸类名上。

2. **条目卡开关态（`.is-on` / `aria-pressed`）——三轮踩坑，现行机制如下**（2026-09-20 收官）：
   - 第一轮：trpg / nixie / rain 把「通电」规则写死在 `#kami-preset-panel` 上，后上线的压缩面板（`#kami-compress-panel`，同一套 `button.kami-item.kami-card` + `.is-on` + `aria-pressed` DOM）在恋雨/辉光管/trpg 下没有高亮（用户真机实测）。
   - 第二轮：改皮肤文件补选择器——**被并行会话的整体重写覆盖，白改**。教训：**并行会话在改皮肤时，不要往皮肤文件里打补丁**。
   - 第三轮（现行）：高亮由压缩脚本**自己注入**一段 CSS（`60-压缩.js` 的 `HILITE_CSS` / `injectHiliteCss`，注销时随 `dropCss` 回收），按皮肤 id 精确补 trpg / rain / nixie 三套 + 无皮肤兜底；声明与令牌逐个抄自各皮肤自己的规则。memo / grokbot 的通用规则是好的，不碰。
   - **已修（2026-09-21）**：那条缺空格的选择器在五套皮肤 + 兜底皮肤里**全部修好**（共 86 处，`[data-kami-comp="panel"].kami-…` → `[data-kami-comp="panel"] .kami-…`）。
     预设设置面板与引导面板的高亮现在都走皮肤自己的规则；压缩脚本里那段自注入的 `HILITE_CSS` 已经是多余的双保险，**可以删**。
   **新面板再上线时**：凡是「多面板共用同一组件」的皮肤规则，一律写成 `.kami-root[data-kami-comp="panel"] X`（**后代选择器，空格不能丢**）；
   确实需要 id 限定的（网格密度、角标），必须把所有使用该组件的面板 id 列进选择器 —— 但更推荐走下面的硬规则，直接不许用 id。

**硬规则：面板内的组件规则一律不得用面板 id 限定**（2026-09-20 用户裁定，与上一条同源）：

皮肤里凡是描述「组件长什么样」的规则 —— 卡片、条目、徽章、开关、按钮、字段、分段控件、折叠组、
注释标记与注释正文 —— 选择器只许写到 `.kami-root[data-kami-comp="panel"]` 这一层，
**不许再往下挂 `#kami-preset-panel` / `#kami-skin-panel` / `#kami-guide-panel` / `#kami-compress-panel`**。
理由：同一个组件在不同面板里必须是同一副样子；一旦按面板 id 分叉，新面板一定会漏 ——
ⓘ 与开关卡片的选中高亮就是这么丢的（`nixie/skin.css:1619-1620` 与 trpg / rain 的同款规则锁在
`#kami-preset-panel`，引导面板里吃不到；兜底皮肤里根本没有这条规则，于是皮肤管理没跑时也看不出来）。

**例外只有一个**：面板自身的**几何与专属结构**可以用 id 限定 —— 舞台、`.kami-drop`、`.kami-resize`、
面板自己的 tab 行排布这类"只有这块面板才有的骨架"。用了就必须在皮肤注释里注明是哪一条、为什么；
**任何「换个面板也长这样」的组件都不许走这个例外**。

**引导面板（`50-引导.js`）的排版层例外**（用户裁定，2026-09 任务⑤）：引导结构层（脚本内的 `GUIDE_CSS`）只做**排版与结构**——报纸式刊头、分栏、照片卡（标题栏＋图片说明）、栏间细线、进度点排布、宽栏皮肤预览卡、grid 卡片列宽——**不定义任何颜色/字体/材质**；底色、墨色、描边、圆角、间距一律引用皮肤令牌，于是每套皮肤一换，引导自动跟着换材质。主按钮用皮肤自己的 `--kami-fg` × `--kami-bg` 反相做「墨块」（契约保证的正文对比度，任何皮肤下都清楚）。
→ 想改引导的**配色/材质** = 改皮肤令牌，属于皮肤决定；引导结构层只负责「怎么排」。这条是硬规则，改引导外观前先读它。
→ 排版层里那 18 个引导专用类名见 **§4.5**；排版层写死的具体数值（字号、字重、行高、透明度）一律必须走令牌，令牌不够用时按 §3.10 补。

> （它们本来就只可能出现在引导面板）；而**多面板共用**的组件（`.kami-item-note` / `.kami-card-note` /
> `.kami-item` / `.kami-field` / `.kami-collapse` …）的排版规则**一律不带 id** ——
> 同一枚组件在两块面板里必须是同一副样子（见 §4.4 硬规则）。

> **⚠️ 跨层取色：令牌必须在「给底色的那一层」拍快照，不许在会被皮肤重定义的元素上现读**
> （2026-09-23 用户报「统御皮肤的确认和下一步按钮看不见，军事工程 / 终端的也有配色问题」）。
> 皮肤**允许**在组件元素自己身上重定义 `--kami-fg` / `--kami-bg` ——
> `empire` / `terminal` / `mileng` 的 `.kami-btn--primary{--kami-fg:var(--kami-accent-fg); background-color:var(--kami-accent)}`
> 就是「整块强调底 ＋ 底上的深色字」的标准写法，**它本身是合法的、也不用改**。
> 出问题的是引导页脚那条墨块规则：它特异性最高（能压过皮肤），但底与字读的是 `var(--kami-fg)` / `var(--kami-bg)`，
> 而这颗令牌在按钮元素上已经被换成了「强调底上的深色字」→ 实测底 `rgb(27,18,38)` 配字 `rgb(22,16,31)`，
> **对比度 1.03**，按钮在屏幕上等于不存在。
> **写法**：外部层要自绘颜色时，先在**它自己给底色的那一层（祖先，如 `.kami-drop`）**把令牌拍成快照再用
> （现在落的是 `--kami-guide-ink` / `--kami-guide-paper`），元素级的重定义就影响不到它。
> 同理，任何「读 `--kami-fg` / `--kami-bg` 再把底翻过来」的规则都要照这个写法来。
> 已知的元素级重定义点（评审对照用）：`.kami-btn--primary`（empire / terminal / mileng）、
> `.kami-icon-btn[aria-pressed="true"]`（wod / grokbot）、`.kami-seg-item.is-on`（五套都有）、
> `.kami-card-note` / `.kami-raw`（grokbot 的黏土内嵌块）。

## 6.5 皮肤作者务必注意的两个坑（真实踩过）

1. .kami-shell 与 .kami-surface 常常是同一个元素。在 .kami-shell 里写 background 简写，
   会把 .kami-surface 上叠的那几层纸面或纹理背景整个重置掉（表现是「纸突然塌成一块灰底」）。
   要叠加就写 background-image 或 background-color 这类长写属性，或者只改其中的一层。
2. 不要给 .kami-root 或 .kami-surface 这一级写定位。面板舞台与 .kami-drop 的定位由脚本注入的几何层负责，
   特异性已抬到 (0,3,0) 与 (0,4,0)，正常情况下皮肤顶不掉；但面板「摆在哪儿」本来就是平台的事，
   皮肤只负责「它长什么样」。

> **新增规则（0）**：皮肤 CSS 的**每一条选择器都必须以该皮肤的作用域前缀原样开头**：

## 8. 装饰模块（decor）：由皮肤声明、由皮肤管理注入

**装饰**是「会动、会响应用户输入」的小组件（目前只有一颗真 3D d20 骰子）。
它既不属于前端（前端不写行为），也不属于皮肤 CSS（皮肤不写 JS），而是**第三个角色**：

```
前端空槽  span.kami-deco[data-kami-deco="d20"]      ← 前端只留这一行，没有任何行为
        ↑ 升级 / 还原
装饰模块  src/decor/d20.js（独立 IIFE，构建期内联进皮肤管理）
        ↑ 注入 / 销毁
皮肤管理脚本（当前皮肤 skin.json 的 decor 里有没有 "d20"）
```

| 环节 | 谁负责 |
|---|---|
| 留空槽（`span.kami-deco[data-kami-deco="d20"]`，带 `aria-hidden="true"`） | 前端 |
| 声明 `"decor": ["d20"]` | 皮肤（`skin.json`） |
| 注入 / 销毁 / 新楼层补注入 | 皮肤管理脚本 |
| 几何、事件、无障碍 | 装饰模块 `src/decor/d20.js` |
| 配色与排版（`.kami-d20-*`） | 皮肤（`skin.css`） |

**硬规则**

1. **没声明的皮肤一分钱不付**：当前皮肤没声明 `decor` 时，皮肤管理**不注入脚本、不注入样式**，
   也不碰槽位（槽位由结构层的 `.kami-deco{display:none}` 收着）。memo / rain / nixie 即属此类。
2. **销毁必须无残留**：切到别的皮肤、脚本被关闭或删除时，模块把槽位还原成**原样**
   （类名、内联样式、`aria-*`、子节点全部还原），并移除自己注入的 `<script>` 与 `<style>`、
   断开 ResizeObserver、解绑事件、清掉定时器、收回 `window.KamiD20`。
3. **模块不许改前端**：装饰只能动自己升级出来的那棵子树，以及槽位自身的属性。

### 8.1 类名契约（d20）

槽位元素**本身就是最外层**（不是外面再包一层）：

```html
<span class="kami-deco kami-d20" data-kami-deco="d20" data-kami-d20="on"
      data-kami-d20-value="17" role="button" tabindex="0" aria-label="掷骰：17，点按重掷">
  <!-- 滚动时最外层与 .kami-d20-body 上都会出现 data-kami-d20-rolling="1" -->
  <span class="kami-d20-stage">                       <!-- perspective 容器 -->
    <span class="kami-d20-body">                      <!-- preserve-3d；转动的就是它 -->
      <span class="kami-d20-face" data-kami-d20-n="1"><i>1</i></span>
      … 共 20 个，按点数 1…20 排列 …
    </span>
  </span>
  <span class="kami-d20-sr" role="status" aria-live="polite">骰子结果 17</span>
</span>
```

| 类名 / 属性 | 含义 |
|---|---|
| `.kami-d20` | 最外层（= 原来的槽位）：承担点击、键盘与焦点 |
| `.kami-d20-stage` | perspective 容器 |
| `.kami-d20-body` | `transform-style: preserve-3d`，**旋转写在它的内联 `style.transform` 上** |
| `.kami-d20-face` | 一个三角面片；`clip-path` 由模块算好写在元素上 |
| `.kami-d20-face > i` | 面片里的数字；内层三角形的裁切值在 `--kami-d20-clip-i` |
| `.kami-d20-sr` | visually-hidden 的结果播报 |
| `data-kami-d20="on"` | 槽位已被升级（没有它 = 槽位还是空的） |
| `data-kami-d20-value` | 当前朝上的点数（1–20） |
| `data-kami-d20-rolling="1"` | 正在滚动（**最外层与 `.kami-d20-body` 上都有**，皮肤钩哪一层都行） |
| `data-kami-d20-n` | 该面片的点数 |
| `--kami-d20-s` / `--kami-d20-r` | 模块量出来的面片方框边长 / 外接半径（px）；皮肤据此排字号 |
| `--kami-d20-clip-i` | 内层（向重心收缩 0.9 的）三角形 `polygon(...)` |
| `--kami-d20-dur` / `--kami-d20-persp` | 滚动时长（默认 1.05s）与透视距离（默认 `--kami-d20-s * 5`），皮肤可覆盖 |

**皮肤写样式时注意**

- 槽位原本的 `::before` / `::after`（占位画法）在升级后不会生成；为让位干净，皮肤应显式写
  `html[data-kami-skin="x"] .kami-deco.kami-d20::before, …::after { content: none; }`，
  并给 `.kami-d20` 放开 `pointer-events`（骰子要能点）。
- **不要**用 `--kami-d20-s` 反推槽位自身的尺寸（会和 ResizeObserver 形成回环）：
  槽位尺寸由皮肤决定，模块只读取它。
- 外层 `.kami-d20-face` 是棱边色、内层 `i` 是面片底色：画棱边就把颜色给外层，画面就给 `i`。

### 8.2 行为

- **点击 / Enter / Space** 掷骰：随机选一面 → 容器 `transform` 朝目标多转两圈 → CSS `transition` 缓动停住。
  滚动期间 `data-kami-d20-rolling="1"`，结束时把点数写进 `data-kami-d20-value` 与 `aria-label`。
- **静止时零开销**：没有逐帧 JS，也没有循环动画，只有容器上的一个 `transform`。
- **`data-kami-motion` 的 `calm` / `off` 与 `prefers-reduced-motion`**：不做滚动动画，直接跳到结果，
  骰子本身照旧可见可点。
- **尺寸自适应**：28–32px 的小骰子与 72–96px 的大骰子都能用。槽位尺寸变了会重算一次位姿：
  ResizeObserver（浏览器主路径）+ 皮肤管理每次下发时的兜底核对（改皮肤令牌 / 字号缩放走这条），
  两条路都是「只在尺寸真的变了才重算」，静止时不做任何逐帧计算。
- **排障**：`window.KamiD20.stats()` 返回挂载 / 重算 / ResizeObserver 回调计数，`geometry()` 返回单位几何表。
- **20 个面的点数**按真实 d20 的排法：**反面之和恒为 21**。

### 9.2 引导向导的几何与四角（`50-引导.js` 的 `GUIDE_CSS`）

- `#kami-guide-panel .kami-drop.kami-drop{left/top/right/bottom/width/height/max-height: …!important}`
  —— 全屏向导是设计意图（用户裁定），要压过几何层的默认摆法与窄屏贴底抽屉。
- `… { border-radius:0!important }` —— 全屏向导四角必须贴边。几何层给 `.kami-drop` 写的是
  `var(--kami-r-lg,14px)`，而 `--kami-r-*` 阶梯里没有"零圆角"这一档，所以这里用字面量 `0`。
  **不要把它改成圆角令牌** —— 那会把全屏向导变成一张四角悬空的浮窗。
- `#kami-guide-panel{max-width:100vw!important}` —— **2026-09-23 加**（用户报「手机端看不到关闭按钮」）。
  向导的舞台是几何层用 `position:fixed;left:0;right:0` 撑的，而**酒馆给 `html` 上了
  transform/perspective（见 `30-皮肤管理.js` 里那段长注释），fixed 的定位包含块因此不是视口、
  而是 `html` 的盒子** —— 页面一旦横向溢出，舞台就跟着变宽、全屏面板整体右移，
  最右边的 ✕ 被推出屏幕（预览台 375px 下实测 wod / trpg 面板 399 宽、✕ 视口右距 -9 ~ -11）。
  `vw` 与包含块无关，`max-width:100vw` 只在「页面比视口宽」时生效：桌面端视口 ≤ 100vw，等于没有这条，
  所以宽屏零影响（实测 1090px 视口下舞台仍是 1090）。契约 §2 禁 `vh/vw` 是对**皮肤**的要求
  （消息 iframe 里没有视口），平台几何层本来就在用 `vh/dvh`（`30-皮肤管理.js:213-216`），两边不冲突。

### 9.5 消息 iframe 的「高度自保」（**主路径是平台，前端只许在启动期兜一次**）

- **主路径（唯一负责人）**：酒馆助手在父窗口对 iframe 里的 `body` 挂 `ResizeObserver`，把
  `frameElement.style.height` 写成 `body.scrollHeight`。**实测可靠**（`docs/真机验证备忘.md` 第三节），
  预览台就是照这套模拟的（`test/harness/preview.html:173-189`）。内容一变高，高度就该跟着变。
- **前端唯一允许做的事**：启动期自己量几次 `body.scrollHeight` 兜一次。
  `frontend-options.html:154-165` 的 `syncHeight()` + `scheduleHeightSync()`（0 / 80 / 260 / 600ms）就是这条 ——
  它覆盖的是「首帧那几次平台重测还没跑到、内容已经比 iframe 高」这个真实缺口
  （iframe 内是 `overflow:hidden`，表现成「内容看不见 / 点了没反应」）。
- **永远不许用 `documentElement.scrollHeight`**：它至少等于视口高度，会让 iframe **只增不减**。
- **不许自己再挂观察者。** `frontend-options.html` 曾经在 boot 末尾挂过一个
  `new ResizeObserver(function () { syncHeight(); }).observe(document.body)`（删除前在第 338 行），2026-09-21 已删除 ——
  它跟平台机制**逐字重复**，只会让每个聊天楼层白付一份观察者。以后想靠 MutationObserver / 轮询
  「保证高度」的念头，先回本节看一眼。
- `frontend-think.html` **没有**这一段，它的折叠展开照样跟着变高（预览台实测：展开 67px → 408px，收起回到 67px）。

> 与另两份文档的关系：`docs/真机验证备忘.md` 第三节与 `docs/交接.md` 第五节第 3 条写的
> 「前端不需要自己 syncHeight」，指的是**不许自己维护高度**（挂观察者 / 轮询 / 反复回写 `style`）；
> 启动期那一次兜底是本节登记的例外，两者不矛盾。

### 9.6 markdown 渲染：showdown **不内联**，沿父窗口链去拿（2026-09-22 定稿）

- **事实**：消息 iframe 与酒馆页面是**同源**的。酒馆助手用 `<iframe srcdoc>` 渲染前端，**没有 `sandbox` 属性**
  （`JS-Slash-Runner/dist/index.js` 里那处 `iframe` 只带 `id/name/loading/class/frameborder`），
  而且酒馆助手自己就依赖这一点 —— 它的脚本预定义脚本第一行就是 `window._ = window.parent._`
  （`JS-Slash-Runner/src/iframe/predefine.js:1`）。行动选项前端能拿到 `window.parent.document` 里的
  `#send_textarea`，也是同一条证据。
- **酒馆把库挂在 window 上**：`public/lib.js` 的 `initLibraryShims()` 里有
  `if (!('showdown' in window)) { window.showdown = showdown; }`，DOMPurify 同款。所以前端只要
  **沿 `window.parent` 链往上找一层**（最多 8 层，每层 `try/catch`）就能拿到酒馆那份 showdown。
- **为什么不在前端里内联一份**：酒馆的正则替换是**逐楼层**跑的。内联 72KB 的库（base64 之后 96KB）
  意味着**每一个思维链楼层**都多背一份库、多编译一次 JS，几十层的聊天就是几十份 —— 手机上白付一大笔体积与解析开销。
- **安全**：showdown 的输出必须过一遍 DOMPurify（酒馆渲染自己的消息也是这么做的）。模型输出不可信，
  而这个 iframe 与酒馆同源。拿不到净化器就**退回极简兜底**，不把未净化的 HTML 塞进同源页面。
- **排障**：组件根上的 `data-kami-md-engine` 写着这一条实际用了哪套引擎（`showdown` / `mini`）。
  预览台要复现这条链路，得让父窗口（预览台页面自己）也有这两个库 —— 走 `test/harness/server.mjs` 的
  `/vendor/showdown.js` 与 `/vendor/dompurify.js`（取自本机酒馆安装目录，可用 `KAMI_ST_ROOT` 指定）。
- 目前**只有**显式思维链前端调 markdown（`frontend-think.html`）。以后新增会渲染 markdown 的前端，
  照它的 `hostGlobal()` + `probeMd()` 抄一份即可，**不要**把库内联进前端文档。

### 9.7 正文包裹层的结构性例外（`30-皮肤管理.js`，2026-09-25 登记；**2026-09-26 隨功能整体退役**）

> 结构性例外**当前没有承担者**，留档备查：将来若又要往消息楼层里插包裹层，照这四条写。

正文包裹层（§4.2 的骨架）由**脚本结构层**生成，不是任何皮肤包的一部分。它落在酒馆自己的 `.mes_text`

1. **包裹层根必须 `display:block`**：`.mes_text` 里混着让位对象（iframe / 插件按钮 / HTML 美化卡片），

`src/skin/tavern.css` 是**不属于任何皮肤包**的平台级共享规则（§1 第三种作用域），落在酒馆自己的
`.mes` / `#chat` 等地盘上，周边全是酒馆的地盘，所以它写的这几类属于本清单的登记例外（形态与 §9.1 / §9.7 同源）：

1. **只读令牌、不写死颜色**：全部取值走 `var(--kami-*)`，于是第 16 套皮肤自动跟随；令牌由 `build/sync-tavern.mjs` 上提到 `<html>`（§3）。
2. **消息卡「谁改色谁配底」**：给 `.mes` 上 `--kami-card` 底时**必须同时给 `--kami-fg` 字色**（§9.7-4 同款纪律）——
   否则浅色皮肤（宣纸 / 樱色）配深色酒馆主题会「白卡配酒馆浅字」整段不可读。这是全局层唯一被允许碰文字色的一处，且与背景成对出现。
3. **只碰五类外观**：底色 / 描边 / 圆角 / 内外间距 / 字体（外加第 2 条的配套字色、第 ⑦ 条的正文排版）。
   **明确不碰**：控件几何 / `z-index` / `pointer-events` / `overflow` / flex 布局（`#sheld` 的高度 `calc` 与
   `#chat` 的 `overflow-y:scroll` 都是酒馆算死的，动它 = 二次踩 §9.2 的坑）、`.qr--buttons` 排布、
   原生弹窗定位、`input`/`select`/`textarea` 可用性、以及插件宿主容器内部（第 ⑦ 条）。
4. **间距加在容器、不加在 `width:100%` 的消息上**：`.mes` 是 `width:100%`，给它加横向 `margin` 会横向溢出；
   所以「消息与左右边缘的间距」加在 flex 竖列容器 `#chat` 的左右 `padding` 上，消息间竖向间距加在 `.mes` 的 `margin-bottom`。
   `.mes` 的 `padding-bottom` / `margin-bottom` / `border` 都是竖向或吃进既有内边距（酒馆全局 `* { box-sizing:border-box }`），不改变 `width:100%` 的外宽。
5. **注入与收回**：由 `30-皮肤管理.js` 的 `applyTo()` 注入 `<style id="kami-tavern">`，**只对酒馆页面**（`doc === HDOC` 守住，不同步到消息 iframe——那里没有 `#chat`/`.mes`，注入也匹配不到还白占体积），`teardown()` 里 `dropStyle` 收回；**不新增观察者**（复用现有 `syncAll` / MutationObserver / 8s sweep 链）。
6. **与用户自定义 CSS（`#custom-style`）的关系**：同特异性下**后注入者赢**，而用户的 `power-user.js` 在运行时把 `#custom-style` 追加到 `document.head`、可能排在我们之后。全局层刻意**只挑用户通常不设的属性**（圆角 / 间距 / 字体 / 描边）先落地，底色是唯一大概率撞车的一格；**不打 `!important` 战争**。冲突逐条清单见 `.audit/酒馆消息区美化.md`。

7. **消息楼层正文排版（2026-09-26 新增，取代 §9.7 的正文包裹层）**：全局层的 ⑤ 段直接给
   `#chat .mes .mes_text` 里的正文与 markdown 上皮肤排版（字号 / 行距 / 字体族 / 段落与标题间距 /
   字色 / 列表与引用 / 代码与表格），整条正文统一，**不往楼层 DOM 里插任何节点**。四类登记例外：
   - ⓐ **`font-size` / `line-height` 只落在「裸子元素」上，绝不落在 `.mes_text` 本身**：它们是继承属性，
     写在 `.mes_text` 上会漏进插件卡片（自带 class、自己不写字号）的整棵子树。
     定稿写法 = `… .mes_text > :where(:not([class], [style]))`，见 `tavern.css` ⑤ 段的说明。
   - ⓑ **插件宿主靠脚本打标让位**：`30-皮肤管理.js` 的 `markMesHosts()` 给 `.mes_text` 里
     「带 class / 带行内 style 的直接子元素」写 `data-kami-mes-host`（既有前端 `.TH-render`、
     我们自己前端的 `.kami-root`、酒馆的 `.mes_*` 容器**豁免不打**），全局层每个后代规则都带
     ``:not([data-kami-mes-host] *)`，于是连宿主里「自己没 class 的 `<strong>`」也一并让位。
     纯 CSS 做不到这件事：`:not([class] *)` 会把 `.mes_text` 自己也排掉（**实测整段失效，别照直觉改**）。
     开关关掉 / 脚本注销时 `unmarkMesHosts()` 把标记摘干净，页面上不留 kami 痕迹。
   - ⓒ **字色只用契约 §2.7 保过对比度的三支令牌**（`--kami-fg` / `--kami-fg-dim` / `--kami-fg-mute`）：
     `--kami-accent` 是装饰色，当正文文字色时 15 套里有多套过不了 4.5:1（wod 暗档 2.56:1、
     trpg 亮档 3.35:1…）。链接用 `--kami-fg` + 下划线做辨识；「有颜色的链接 / 花式引用」是皮肤专属活。
   - ⓓ **不给 `.mes_text` 加底色 / 描边 / 内边距**：底色与描边已经由第 2 条给在 `.mes` 上了，
     再给 `.mes_text` 来一套就是「卡片套卡片」；也不给表格上 `display:block` + `overflow-x`
     （375px 窄屏会撑出横向滚动）。
   - **开关**：面板「显示」卡第一行「消息排版」= 脚本变量 `kami-skin.mesText`（默认**开**），
     脚本写成 `#chat` 上的 `data-kami-mes="1"/"0"`；③ 段（消息卡）与 ⑤ 段都挂在它下面，
     所以「关」= 完全退回酒馆原味。验收口径（15 套逐套实测）见 `.audit/消息楼层排版.md`。
   - **代价一条（如实记）**：消息正文的字号沿用酒馆当前字号（皮肤只改字族 / 行距 / 排版），
     换来「插件卡片内部一个字都不变」。要做到字号也跟着皮肤，等于把插件卡片的尺寸一起改掉，
     不在全局层做 —— 属于第二阶段的皮肤专属活。

8. **消息楼层的「面 + 特效」镜像（2026-09-26 第二轮新增，`build/sync-tavern.mjs` 生成）**。
   用户打回第一轮的观感（「消息楼层仍然是酒馆原生背景，特效也没作用上」），实测根因：皮肤的**面**在
   `.kami-shell` / `.kami-surface` 上、**特效**（`::before` / `::after` / `animation`，15 套共 167 条）
   挂在 `.kami-shell` / `.kami-surface` / `.kami-root` 上，而消息楼层**没有这些类名**，一条都不命中。
   定稿做法：**不改 DOM**（给 `.mes` 加组件类会把 `display:flex` 夺走、头像列与 swipe 全歪，实测），
   由生成器把皮肤写在这些类上的**视觉声明**改写成消息楼层作用域，追加回同一套皮肤的生成块。
   登记例外如下（这一节是**生成器的规范**，改生成器前先读）：
   - ⓐ **作用域映射**：`.kami-shell` / `.kami-surface` / 裸 `.kami-root` → `#chat[data-kami-mes="1"] .mes`；
     `.kami-md` / `.kami-body` → `.mes_text`。**面板与组件内部的类一律跳过**
     （`.kami-drop` / `[data-kami-comp="panel"]` / `.kami-card` / `.kami-item` / `.kami-head` / `.kami-title` /
     `.kami-dot` / `.kami-btn` … —— 消息楼层上没有那些元素）。
   - ⓑ **属性白名单，只搬视觉**：底 / 描边 / 圆角 / 投影 / `clip-path` / `filter` / `backdrop-filter` /
     `mix-blend-mode` / `opacity` / `color` / `letter-spacing` / `animation*` / `content` / `inset` 与四向定位 / `z-index`。
     **几何一律不搬**（`display` / `flex*` / `width` / `height` / `overflow` / `position` / `margin` / `padding` / `gap`），
     **`overflow` 更是永不搬**（会切掉插件浮层与头像列）；圆角贴合改用一条保底 `::after`
     （`inset:0` + `border-radius:inherit` + `var(--kami-border-w) solid var(--kami-line)` + `pointer-events:none`）。
     `.kami-md` 只搬底色族（底色与描边已经由 §9.8-7 的 ③ 段给在 `.mes` 上了，再给 `.mes_text` 是「卡片套卡片」）。
   - ⓒ **保底成对（必须排在生成块最后）**：镜像里混着「组件面 → 另一套配色」的后代规则
     （`.kami-md` 级把 `--kami-fg` 重映射成墨色），漏下来会让正文与卡底脱对 ——
     实测 terminal **1.01:1**、empire **1.03:1**（整段看不见）。所以生成期必须把
     `--kami-bg × --kami-fg(-dim/-mute)` **按皮肤自己的 `var()` 链解析成实际色值**，
     钉一条成对规则（同时命中 `.mes` 与 `.mes_text`，并把三支字色令牌一起钉住）。
     解析器要「逐层剥 `var()` + 选择器回退」，且**令牌基座是 `html[data-kami-skin="<id>"] .kami-root`**
     （不是 `<html>` —— `<html>` 那一份是上提脚本生成的，源码里不存在）。
   - ⓓ **每条生成规则自带宿主闸门** `:not(:where([data-kami-mes-host] *))`：生成的选择器特异性 (1,3,1)
     与全局层那条 `… .mes_text strong:not([data-kami-mes-host] *)` 打平，排在后面就会压过闸门、
     漏进插件卡片（实测：卡里的 `<strong>` 被染上皮色）。用 `:where()` 把它压成 0 特异性，
     不改变生成规则与全局层原有的胜负关系。**伪元素要插在 `::before` / `::after` 之前**。
   - ⓔ **令牌上提判据同步放宽**：从「选择器必须以 `.kami-root` 结尾」改成「选择器里出现 `.kami-root`」，
     于是皮肤给组件面写的**令牌重映射**（grokbot 的 `--kami-clay-*` 等）也进 `<html>`（101 → 193 条）。
     不放宽的话，镜像里的 `background-color: var(--kami-clay-surface)` 会解析成空、整条声明被丢
     （实测：grokbot 拿到炭底而不是黏土白）。
   - ⓕ **幂等**：生成块带独立起止标记（`消息楼层的面与特效镜像` / `END 消息楼层的面与特效镜像`），
     重跑先整块删再重建；剥离与拼装用**确定性写法**（不用「吃掉两侧换行」的正则 ——
     那种写法在拼装把内容末尾与块粘在一起时第二轮就咬不住、块会越滚越大，实测踩过）。
   - **验收口径**：15 套逐套读数（面 / 特效 / 布局 / 插件卡片零污染 / 按钮回调节 / 对比度 / 375px 零溢出 /
     开关还原）见 `.audit/消息楼层排版.md` §八。
