## 一、先给结论

现在这套前端能用，但它的**渲染层一行测试都没有**，而且**重画一次就把用户的界面状态全丢了**。
这两件事不是"打磨"，是继续往下加功能（图标体系、选中焦点）之前必须先还的债。

三句话概括我的建议：

1. **把「变量 → 界面树」这一层抽成新的纯模块**，让它能离线跑、能逐条断言 —— 照抄 `_status-view.js` 已经验证成功的那套做法。
2. **界面树到 DOM 之间加一层差异更新**（只改该改的那几个节点），顺手修掉"折叠打开一下刷新就合上""滚动位置一跳回顶"。
3. **不动几何、不动交互、不动类名**，所以皮肤契约与 651 项单测不受影响。

同时**明确不建议**做的：把 80 号推倒重写。

## 二、现在是什么样（实测，不是印象）

`src/scripts/80-状态栏.js` 一个文件里挤着六件不同的事：

| 职责 | 行号 | 规模 |
|---|---|---|
| 宿主窗口探测、文案常量、toast | 62–100 | ~40 行 |
| 位置与设置的读 / 写 / 防抖落盘 | 102–150 | ~50 行 |
| **内联样式表 BALL_CSS**（球 + 横幅 + 面板 + 控件 + 八个分区） | **158–375** | **218 行** |
| DOM 建节点、拖动、点击、rAF 节流、夹取、画几何 | 393–653 | ~260 行 |
| **三行标题栏 + 面板 + 控件 + 八个分区渲染器** | **655–1353** | **~700 行** |
| 全局 API、启动、注销 | 1355–1544 | ~190 行 |

另一半在 `src/scripts/_status-view.js`（1691 行），它是**纯计算**，里面 DOM 相关调用数为 **0**。
它导出 70 个东西，包括 `widgetOf`（判断一个字段该画成条 / 徽章 / 标签片）、`layoutOf`（算横幅与面板几何）、`hudOf` / `rosterOf` / `mapTreeOf` 等八个分区的**数据整理**。

所以现状是：**「算什么」已经干净地分出去了，「长什么样」全留在 80 号里，而且没有出口。**

## 三、六个具体问题（都带行号）

### 问题 1 · 折叠状态每次刷新都被抹掉（现存缺陷）

`renderPanelBody()` 第 1275 行把整个内容区清空重画：

```js
while (panelBody.firstChild) { panelBody.removeChild(panelBody.firstChild); }
```

而 `fold()` 第 970 行只在**创建那一刻**按 `defaultOpen` 写一次 `data-kami-open`，没有任何"恢复"路径。
后果：你把某个角色的细节折开，来了新回复，300ms 后刷新 —— 折叠块自己合上了。
要不要展开、展开哪一个，用户没法保留。这是**用户一定会碰到**的行为，不是边缘情况。

### 问题 2 · 滚动位置每次刷新都跳回顶部

同一个清空动作的另一面。内容区在重画后 `scrollTop` 归零。
面板内容一屏放不下时（八个分区里角色卡最长），每次回复都把你弹回最上面。

### 问题 3 · 设置页每次重画都重建复选框

`renderSettings()`（第 1330 行）连同它的 `checkbox()`（第 1314 行）每次都是新元素。
键盘焦点会丢，`change` 监听器一直累积重建 —— 功能上目前还正常，但这是"每重画一次就重建一次交互件"的典型写法，加功能后会变成 bug 温床。

### 问题 4 · 渲染层零测试，且**没法**加测试

`test/harness/status-view.mjs` 用 `new Function` 把纯模块在 Node 里跑起来 —— 这招对 `_status-view.js` 有效，因为它不碰 DOM。
对 80 号无效：它开口就 `HDOC.createElement`，Node 里没有 `document`。
于是那 ~700 行渲染逻辑的唯一验收手段是**截图**（现在的做法是拿 CDP 开 Chrome 截图，`.audit/cdp-measure.mjs` 有现成脚本）。
截图能看"长得对不对"，看不了"数据到控件映射对不对"（比如某字段该画成双向条却画成了普通条）。

### 问题 5 · 同一份判断在两个文件里各写一遍

`widgetOf`（纯模块）算出 `kind: 'bar' | 'signed' | 'rank' | 'badge' | 'chips' | 'text' | 'num' | 'bool' | 'kv' | 'empty' | 'card'`，但**把它画成什么类名**的决定写在 80 号的 `renderWidget()`（第 825 行）里。

同时 `renderWidget` 与 `renderValue`（第 896 行）是两套并行实现：`renderValue` 自己也画 bool、也画 list、也递归，而 `renderWidget` 的最后一档又回头调 `renderValue`。第 929 行的注释就写着这里踩过坑（"只有第一层有控件"的 bug 就是这么来的）。
**"一个值长什么样"这件事，现在有两个半地方在决定。**

### 问题 6 · 218 行 CSS 与生成它的类名隔了 1100 行

改一个控件要同时动第 255 行附近和第 825 行附近。类名字符串在 80 号里出现 **134 次**。
更要紧的是：**没有"JS 生成的类名在 CSS 里都有定义"的检查**。拼错一个类名 = 控件变形且无人报错。

### 附带两条：两条不许删的防线现在**没有守卫**

`verify-status-ball.mjs` 盯着悬浮球的图标与类名，但下面这两条只在注释里（第 231–233、207–209 行），一旦重构手滑删掉就会出视觉故障、且测试全绿：

- 标签行 `flex:none` + 内容区 `min-height:0` —— 少了它内容一多标签行被压扁；
- 横幅与面板 `margin:0` —— 少了它被 `src/skin/base.css` 的通用子元素规则顶下去 10px、接缝开裂。

**重构的同时要把它们变成断言**，否则等于把已经踩过的坑重新挖开。

## 四、核心思路：一行判断只留一处

把现在的三段式

```
纯模块算数据  →  80 号里同时决定"画成什么"和"怎么建 DOM"  →  真实 DOM
```

改成四段式，关键是**把"画成什么"从"怎么建 DOM"里切出来**：

```
① 纯模块 _status-view.js      变量 → 分区的数据整理（已有，不动）
② 新模块 _status-ui.js       数据 → **界面树**（纯对象，不碰 document）
③ 新模块 _status-css.js      界面树用到的类名 → 样式文本（类名与样式挨着放）
④ 80 号                       界面树 → 真实 DOM（**差异更新**），外加拖动 / 持久化 / 启动
```

为什么加第 ③ 层差异更新，而不是"清空重画"：因为要修问题 1 与问题 2。
差异更新只需要认四种动作 —— 换文字、换属性、加节点、删节点。这套东西写在 ③ 里是纯逻辑，Node 里能跑。
④ 只负责把四种动作翻译成 `createElement` / `setAttribute` / `appendChild` / `removeChild`，**一共几十行，所有分区共用一份**。

**这样切的最大好处：问题 4 消失了。**
"数据 → 界面树"是纯函数，可以在 Node 里对八个分区逐条断言；"界面树 → DOM"是唯一的 DOM 代码，只需要在预览台里验一次而不是每个分区各验一次。

## 六、差异更新具体怎么修那两个缺陷

**折叠状态（问题 1）**：折叠块的 `data-kami-open` 由界面树携带。
差分会算出"这个属性从 1 变成 0"，只改属性，**节点本身不动** —— CSS 的 `grid-template-rows` 过渡照旧。
用户折开的块，刷新后依然是折开的：因为新旧树里它都写着 `open: 1`。

那么"用户点开"这件事怎么进到树里？**不再靠读 DOM，而是靠一份 `uiState` 明账**：

```js
var uiState = { folds: {}, activeTab: null, bodyScrollTop: 0 };
```

点折叠 → 写 `uiState.folds[id]` → 重画。这样状态是数据，不是 DOM 的副作用，也就顺带变得可测（给它灌一份 `uiState` 就能断言树里那个块是开的）。

**滚动位置（问题 2）**：节点被复用 ⇒ `scrollTop` 天然不归零，不需要额外保存恢复。

**交互件（问题 3）**：事件从"每个节点各挂一个"改成**内容区挂一个委托监听**，靠 `data-kami-fold` / `data-kami-tab` / `data-kami-act` 分派。
好处：节点被复用后也不会积累重复监听；`checkbox` 的 `change` 同样走委托。

## 七、测试与守卫（这才是重构的收益所在）

### 单测：新增 `test/harness/status-ui.mjs`

照 `status-view.mjs` 的写法（`new Function` 拼装纯模块），对**八个分区逐个断言界面树**。举例：

- 角色分区：`rosterOf` 给两个角色 + 一个 `is_user`，断言树里有**恰好两张卡**、`is-self` 只落在自己那张、头像没图时**必须有兜底首字**与一个色相；
- 地图分区：未探明的区域断言 `data-kami-fog="1"`、名字被替换成"未探明区域"、**不给描述**；
- 剧情线：`phase` 三种取值分别断言 `is-future` / `is-now` / 无修饰，且未来节点的连线是虚线类；
- 设定集：剧透开关关掉时树里**一个 `truth` 节点都不许有**（现在是靠 `loreOf` 不给，这条断言把它钉死）；
- 控件映射：喂 D&D 六维数字断言 `kind` 决策落到 `bar`、喂 `affinity: -40` 断言落到 `signed` 且 `is-neg`。

目标：**把现在靠截图看的那些"对不对"，变成几百条能逐条指出名字的断言。**

### 单测：新增 `test/harness/status-patch.mjs`

差分层是纯逻辑，可以直接测：
- 同一棵树 diff 两次 ⇒ 动作清单为空（幂等）；
- 换一个文字 ⇒ 只有一条 `setText`，没有 insert / remove；
- 折叠属性 1 → 0 ⇒ 只有一条 `setAttr`，节点身份不变；
- 列表中间删一项 ⇒ 只有一条 `remove`，其余项的 key 不变。

### 守卫：`build/verify-status-ball.mjs` 增补四条

1. **两条不许删的防线进断言**：产物里存在 `flex:none`（标签行）与 `min-height:0`（内容区），且横幅与面板的 `margin:0` 在。
2. **类名交叉检查**：`_status-ui.js` 里出现的 `kami-*` 类名，必须都能在 `_status-css.js` 里找到定义；反之 CSS 里的类名允许有剩余（皮肤可能用），但要打印出来给人看。
3. **新模块的内联契约**：三个新模块零 import、无美元符号、无 DOM 调用（`_status-ui.js` 与 `_status-patch.js` 必须零 `document`）。
4. **保留现有的球类名与令牌断言**（`kami-root` / `kami-ball` / `kami-ball-img` / `--kami-ball-x|-y|-size` / `--kami-ball-shadow` / `setPointerCapture` / `touch-action:none`）。

### 视觉回归：改动前先录基线

重构**不可能**用单测抓住所有视觉退化，所以动手前先做两件事：

1. 用现有 CDP 脚本（`.audit/cdp-measure.mjs`）把**重构前**的八个分区 × 手机(390) / PC(1440) 截图存进 `.audit/`；
2. 再录一份"关键盒模型读数"：标签行高度、内容区高度、面板上缘 − 横幅下缘（必须为 0）、球直径。

改完重跑同样两份，逐张对比。**接缝差值必须是 0**，这是已经验收过一次的硬指标，不许退化。

## 九、风险与应对

**风险 1 · `verify-status-ball.mjs` 会不会因为搬家而失败。**
它读的是**产物里那段脚本文本**，检查 `kami-root` / `kami-ball` / `kami-ball-img` 三个类名、`__hubDefs` 不存在、几何令牌、`setPointerCapture`、`touch-action:none`、`ICON_STATUS` 与图标字节。
类名与令牌在 80 号里还会出现（DOM 适配器要用），所以大概率能过；但 `ICON_STATUS` 的常量与那几行内联注释必须在。**第 1 步之前先跑一遍确认基线，改完再跑一遍**，不靠推测。

**风险 2 · 视觉退化。** 靠第八节第 0 步的基线与第 7 节的盒模型读数兜，不靠肉眼。

**风险 3 · 文件互斥。** `_status-ui.js` / `_status-patch.js` / `_status-css.js` 是三个新文件，可以分给不同人；但 `80-状态栏.js` 只有一个写入方。
按交接文档的纪律：**同一时刻只有一个队友写 80 号**，Lead 负责合。

**风险 4 · 范围失控。** 明确**不在本次范围**内的东西（下面单列一节），一并在动手前说清。

## 十、明确不做的事

- **不碰 MVU 数据链路**（读楼层变量那条）。它是另一个方向的活，交接文档第三节把它列为最高优先级风险，与本次重构无关。
- **不改几何算法**（`layoutOf` / `headerGeom` / 夹取 / 断点 640 / 调宽持久化）—— 已经端到端验收过，动它等于把 5 个真 bug 重新引入一遍。
- **不改类名、不改令牌名** —— 18 套皮肤与 `docs/皮肤契约.md` §4.6.1–§4.6.3 不受影响。
- **不动其它前端**（思维链 / 行动选项 / 正文外壳 / 四个面板）。
- **不动悬浮球的拖动与点击那两道闸**（4px 位移阈值 + 300ms 防补发）。
- **不在这一步做图标体系与文案密度** —— 它们改的是"界面树长什么样"，正好接在重构之后做，那时改起来才便宜。

## 十一、工作量估计

| 步 | 规模 | 说明 |
|---|---|---|
| 1 CSS 搬家 | 小 | 218 行搬家 + 分段整理，零逻辑改动 |
| 2 界面树抽取 | **大** | 约 700 行改写法，是本次主体 |
| 3 差异更新 | 中 | 新写 120–150 行 + 替换 3 处清空重画 |
| 4 合并控件 + 事件委托 | 中 | 两处合并、三处事件改委托 |
| 5 测试与守卫 | 中 | 新增两个测试文件 + 守卫增补 |
| 0+6 基线与真机 | 小 | 脚本现成 |

**一句话**：主体在第 2 步，其余都是配套。可以让一个队友做第 1 步（CSS 搬家，机械活、零判断），另一个队友写第 3 步的差异更新（纯逻辑、可单测），Lead 自己啃第 2 步并负责合。

## 十二、需要用户拍板的三件事

1. **要不要按这个方案做**，还是只想先要"折叠状态不丢"这一个修复（那个可以单独做，只改 3 处，约 50 行）。
2. **面板刷新时机**：现在每次 `MESSAGE_SENT` / `CHAT_CHANGED` 后 300ms 重画。要不要顺手改成"面板关着的时候不重画内容"（省电，也少一次无谓重建）？
3. **折叠的默认态**：现在细节块**默认全部收起**。有了状态保留之后，要不要"上次折开的记着"（推荐）还是要"每次开面板都收起"（现状）。

---

## 十三、怎么退回

三步各自独立，都能单独回滚：
- 第 1 步只换 CSS 的出处，回滚 = 把字符串搬回 80 号；
- 第 2 步保留 80 号原来的渲染函数直到第 3 步验收通过（**先并存、再删旧**），所以第 2 步出问题可以把开关拨回旧路径；
- 第 3 步的差异更新接在一个开关后面（`USE_PATCH`），出事拨回清空重画。

**第 2 步"先并存再删"是这套方案最重要的安全绳**，别省。
