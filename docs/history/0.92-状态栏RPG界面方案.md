## 一、先给结论

1. **视觉与工程一起做，但视觉是主线**。工程结构（结构层抽取 + 差异更新）之所以仍然要做，是因为
   **不先把它做掉，视觉方案落不了地** —— 见第二节。
2. **令牌分两层**：通用控件层（新的、所有组件可用）+ 状态栏形态层（现有 40 个 `--kami-status-*` 的位置）。
3. **不给 18 套皮肤手写 18 份样式**，改为**一张集中数据表 + 生成块**（机制已经存在）。
4. **PC 与手机做两套形态**，不是一套挤一挤：PC 是连体横幅 + 可调宽面板，手机是**底部抽屉**。

## 二、为什么"只做视觉"这条路走不通（先讲清这个）

今天的状态栏长这样（.audit/ia-sections.png、matrix.png 实测）：

- **八个分区是一堆长得很像的圆角方块**：角色卡、任务卡、产业卡、设定集条目，四种东西同一副面孔。
  游戏感来自「一眼分辨这是什么」，现在做不到。
- **标签行被挤**：八个标签 + ✕ 在 330px 宽里排不下，末尾用省略号吃掉。
- **属性条标签被截成"【占…"**（`--kami-status-kw` 固定 3.4em），用户看不到那是什么属性。
- **没有图标体系**：分区靠文字，档位靠字母，状态靠"●"。—— 这是交接文档第四节自己点名的第 2 条。
- **没有"当前在哪"的焦点**：当前 tab 只比其他 tab 亮一点，其余没有任何选中语言。
- **深浅两族皮肤下，状态栏只有"能看"，没有"这是那套皮肤的东西"** ——因为 18 套皮肤
  对状态栏的令牌定义数**都是 0**（实测）。现在这套外观完全是脚本里的兜底值。

而这一切的根因是同一件事：**决定"长什么样"的代码有 700 行，困在一个 1544 行的文件里，
和拖动、落盘、几何算在一起，没有任何出口。**

我要加图标、加徽章形状、加选中态、加两套形态 —— 按现在的结构，这些全部要塞进 80 号那个文件，
再长 400 行。**所以工程结构不是"顺带还债"，它是视觉方案的前置条件。**

## 三、设计语言：什么才算"RPG 游戏式界面"

我按六条可执行的原则来做，不用形容词。

### 原则 1 · 深度是三层的，不是一层的

游戏界面看起来"厚"，靠的是**明暗三层叠压**，不是阴影大。三层固定为：

    L0 面板底（.kami-status-body 的背景）
    L1 卡片（角色卡 / 任务卡 / 产业卡 抬起来一层）
    L2 凹陷槽（条轨道 / 输入框 / 空槽，压下去一层）

每层给一支令牌。**"凹陷槽"这一层现在完全没有** —— 这是现在界面发平的第一主因。

### 原则 2 · 边缘语言统一：外描边 + 内高光 + 切角

游戏 UI 的边框几乎都是"外深内亮"的双线感（像金属倒角）。统一成：
外 1px 深描边 + 内 1px 亮高光（`inset 0 1px 0`）。可选**切角**（corner notch）用 `clip-path` 做，
但切角是**每套皮肤自己决定要不要**（有的皮肤不适合切角，比如笔记本 / 水墨）。

### 原则 3 · 徽章有形状语义（这才是"游戏感"的来源）

现在所有徽章都是同一个圆角胶囊，只换颜色。改成**形状即语义**：

| 类型 | 形状 | 用在哪 |
|---|---|---|
| 档位 / 评级 | **菱形**（旋转 45°） | `kami-w-rank`，D&D 六维、FATE 档位 |
| 状态 / 病情 | **环形**（左侧一枚色点 + 胶囊） | `kami-w-badge`，"轻度疲惫" |
| 物品 / 装备 | **矩形**（小圆角） | `kami-w-chip`，标签片 |
| 数值 | **数字牌**（等宽数字 + 底衬） | `kami-w-num`，回合数 |
| 任务状态 | **旗帜形**（右侧斜切） | 任务日志的状态标 |

这条改完，用户扫一眼就知道"这是个评级"而不是"这是个词"。

### 原则 4 · 分区有图标

八个分区各一枚图标，走**构建期内联 SVG**（不是 emoji：emoji 有默认字形、跨端不一致、也没法吃 `currentColor`）。
图标统一 16px，与文字基线对齐。形状也顺便带语义：

    状态=六边形   角色=圆     地图=菱形    势力=旗帜
    剧情线=节点轴  任务=卷轴   不动产=屋   设定集=书

### 原则 5 · "当前在哪"必须有视觉焦点

现在没有。要三处同时给语言：
- 当前 tab：底色 + 下沿一条强调色横线 + 字号提一档；
- 当前楼层 / 当前节点：已有的 `.is-now` 加上**左侧色条 + 强调光环**；
- 悬停：整行抬一层（换 L1 底色），不是只变文字色。

### 原则 6 · 两套形态，不是一个布局挤两头

**PC**（≥1024px）：连体横幅 + 面板，面板**宽 380–520px**，角色卡可两列。
**手机**（<640px）：面板变 **底部抽屉**，占满宽、向上展开、顶部一条抓握提示、支持下拖收起。

现在的手机形态只是"把 PC 的窄面板贴到屏幕左下角"，330px 宽塞八个 tab，是挤的根因。

- 全部用 `--kami-` 前缀，**通用层不带 status 字样**（能用在任何组件上）；

## 五、18 套皮肤怎么落地：一张表 + 生成块（不手写 18 份）

### 5.1 机制（已经存在，只需扩用）

`build/sync-tavern.mjs` 现在做的是：从皮肤 CSS 抽 `--kami-*` 声明，生成 `html[data-kami-skin="x"]` 作用域副本，
追加到皮肤末尾的**生成块**里（带起止标记、重跑先删再建、幂等）。
实测皮肤末尾就有这样一个块（`crt80s` 的 `--kami-items-min`）。

**扩用方式**：新建 `design/status-rpg-tokens.json`，每套皮肤一份取值：

    { "crt80s": { "--kami-sunken": "rgba(0,0,0,.45)", "--kami-notch": "6px", … } }

`sync-tavern.mjs` 读它，把新令牌的值追加进每套皮肤各自的生成块。

### 5.2 为什么必须走生成块，而不是手改 18 个文件

**因为 `build/lint-skins.mjs` 会拦。** 实测第 15–17、113–115 行：
它把 `base.css` 里所有 `--kami-*` 声明当作 **MUST 清单**（当前 75 个），
要求**每套皮肤都定义**，缺一个就 FAIL。我抽查了三套（crt80s / grokbot / memo），当前都是缺 0 个。

所以：`base.css` 加 34 支通用令牌 ⇒ 18 套皮肤各缺 34 支 ⇒ **18 套全部构建失败**。
要么手改 18×34 处（易错、难审），要么一张表生成。**选后者。**

好处不只是省事：18 套皮肤的取值**摆在一张表里能横向对比**，
哪套丑了一眼看得出，也不会出现"改好 17 套漏了 1 套"。

### 5.3 具体的数值设计（举例，正式实施前会出完整表）

| 皮肤 | 切角 | 凹陷色 | 边缘语言 |
|---|---|---|---|
| crt80s 扫描显示 | 6px | `rgba(0,0,0,.5)` | 琥珀/荧光单色描边 + 磷光辉光内高光 |
| empire 统御 | 0 | `rgba(0,0,0,.38)` | 金色细双线 + 内高光 |
| mileng 军事工程 | 4px | `rgba(0,0,0,.4)` | 直角 + 军绿描边 + 铭牌感 |
| terminal 终端 | 0 | `rgba(0,0,0,.55)` | 纯单色方块 + 无圆角 |
| nixie 辉光管 | 0 | 深管腔 | 管色描边 + 外发光 |
| rain 恋雨 | 0 | `rgba(0,0,0,.18)` | 柔和圆角 + 水光内高光 |
| memo 记事本 | 0 | 纸色压深 | 手绘边 + 纸纹 |
| xianyun 闲云野鹤 | 0 | 淡墨 | 水墨描边 + 无高光 |

**明暗两档要各给一份**（`isekai` / `manga` / `memo` / `senren` / `trpg` / `xianyun` 是浅色系）。
浅色系的"凹陷槽"与"内高光"方向要反过来，这是最容易做错的地方。

## 六、PC 与手机两套形态

### 6.1 手机（<640px）：底部抽屉

- 面板从底部向上展开，占满宽，高度 `--kami-sb-drawer-h`（默认 68dvh，**不用 vh 计量**，
  因为契约 §2 禁止 `vh`；用 `dvh` 并由脚本在拿不到时退回固定值）；
- 顶部一条**抓握提示**（`.kami-sb-grab`），向下拖收起 —— 与现有四个面板的贴底抽屉同一套手势
  （`_panel-gestures.js` 已有实现，复用，不新写）；
- 标签行：图标优先 + 文字可省，横滑，且**末尾的 ✕ 始终可见**（现状是被挤掉）；
- 角色卡改**单列**（330px 放不下两列）；设施格子改两列；属性条标签宽度改成 `auto` + 允许换行。

### 6.2 PC（≥1024px）：连体 + 可调宽

- 保持现在的连体关系（横幅左缘 = 面板左缘、上缘 = 横幅下缘，接缝差值为 0）**不动**；
- 面板宽度范围扩到 380–560px；`>=1280` 时角色卡两列、设施格三列；
- 悬停态变成完整语言（整行抬层 + 左侧色条）。

### 6.3 三档断点的判定位置

沿用现在的规矩：**形态判定是纯逻辑**（`_status-view.js` 里加 `formOf(viewW)`，返回 `'drawer' | 'ribbon'`），
DOM 只负责按它加 `data-kami-sb-form` 属性。皮肤按这个属性写规则 —— **皮肤永远不知道设备，只知道形态**。

## 七、工程结构（第一稿的结论，保留）

视觉要落地，需要第一稿那套结构。**但工作量可以压**：先只做「结构层抽取 + 差异更新」这两件事，
不合并 `renderWidget` / `renderValue`（那是独立的清理，可以晚一轮）。

    ① _status-view.js    变量 → 分区数据整理（已有）
    ② _status-ui.js      数据 → **界面树**（纯对象；新增图标与形状语义都在这一层）
    ③ _status-patch.js   新旧树 → 四种动作（换文字 / 换属性 / 加节点 / 删节点）
    ④ 80-状态栏.js       动作 → 真实 DOM + 拖动 + 落盘 + 两套形态的切换

**顺带修掉的两个现存缺陷**（第一稿已核实）：折叠状态每次刷新被抹掉、滚动位置跳回顶部。
它们和视觉是同一批改动的一部分 —— 差异更新落地后自动消失。

## 九、风险

1. **18 套皮肤一起动**，任何一套做丑都是全体可见。对策：跑量。每套都出截图，
   且**浅色系六套单独复核**（凹陷 / 高光方向反过来）。
2. **新令牌写错默认值 = 所有组件一起坏**。对策：默认值一律串到现有令牌，
   且第 1 步只加令牌不删不改任何既有令牌。
3. **`lint-skins` 的 MUST 清单会被撑大**。第 1 步落地后 18 套必然 FAIL —— 这是**预期的中间状态**，
   第 2 步必须紧接着做。**不能把 1 和 2 分开交付。**
4. **预设体积**：新令牌约 34 支 × 18 套 × 两档 ≈ 每套多 1–2KB，18 套共约 20–35KB。
   相对产物 3.79MB 可忽略，但我会在实施时实测并报告。
5. **视觉退化单测抓不住**。对策：第 0 步的基线 + 每步截图对比 + 盒模型读数（接缝必须仍为 0）。
6. **范围失控**。明确不做：不改几何算法、不改四个面板的交互、不改令牌里的既有名字、
   不碰 MVU 数据链路。

## 十、需要用户拍板的三件事

1. **图标体系走内联 SVG 还是 emoji。** 我推荐 SVG（跨端一致、能吃 `currentColor`、
   形状可控），代价是每套皮肤可以选择性覆盖，脚本体积增加约 4–6KB。
2. **手机端改成底部抽屉，还是保持现在的窄面板。** 我推荐抽屉 —— 现在 330px 塞八个 tab 是挤的根因。
3. **旗舰皮肤做几套。** 18 套全部按同一套通用令牌走，这点不变；
   但"每套额外的专属装饰"（比如 crt80s 的扫描线叠在状态栏上、nixie 的管腔）我只做
   **用户点名的几套**，其余靠通用令牌。请点名。
