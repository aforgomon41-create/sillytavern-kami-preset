# 前端重构 · 消息前端方案（讨论稿，2026-10-28）

> 回答用户的三个问题：正文前端要不要框、四个消息前端怎么协调（一 4），对白与心理描写的渲染（一 2），思维链 / 行动选项 / 搜索资料的形态（七）。
> 第五节 A–F 已于 2026-10-28 由用户拍板（结论见第六节）；预览已出，实现细节见第七节。

## 一、现状

| 前端 | 现在怎么渲染 | 问题 |
|---|---|---|
| 正文 | 45 号脚本在酒馆的消息 DOM 里给 `<content>` 套一层卡片外壳（标题「正文」+ 字数 + 渲染 / 原文 + 复制） | 故事正文被框起来，沉浸感打折；正文本身由酒馆的 Markdown 渲染，排版不归我们管 |
| 思维链 | 46 号脚本把思维链搬进酒馆原生思维链块，并装饰成卡片 | 展开后和正文一样醒目，抢正文的注意力 |
| 行动选项 | 正则替换成 iframe（酒馆助手渲染），卡片网格 | 每条消息一个 iframe，样式各自内联 |
| 搜索资料 | 同上，iframe，默认折叠 | 同上 |

预设对输出格式的要求（`📌 输入解析` / `📌 输出规范` 等条目）：

- 对白用全角日式引号「」包裹；
- `*星号*` 包裹的是角色的内心想法（酒馆会渲染成斜体 `<em>`）；
- 段首全角空格缩进「　　」；
- 每个步骤前有一行 `<!-- 步骤[n]/Token[m] -->` 注释；
- 指代一律写作【名称】（全角方括号）。

## 二、建议：正文也由我们渲染

把正文从「酒馆渲染 + 我们套壳」改成「我们直接渲染」（消息挂载，契约 8.3）：载荷取自聊天原始数据，自己做段落与行内排版，渲染在 Shadow DOM 里。好处：

1. **排版完全可控、分设备**：用 5.7 的阅读令牌（电脑限制行长约 42 字、行高 1.8；手机铺满、行高 1.75）。
2. **按预设格式加强渲染**（回答一 2），每一种都是皮肤可以单独设计的部件：

   | 原文 | 渲染成 | 部件钩子 | 「碎光」的默认处理（建议） |
   |---|---|---|---|
   | 「……」 | 对白 | `[data-k-part="dialogue"]` | 正文色，字重略重；引号本身用次要色 |
   | `*……*` | 心理描写 | `[data-k-part="thought"]` | 次要色 + 楷体（外链字体，失败时退回系统楷体 / 衬线） |
   | 其余文字 | 叙述 | `[data-k-part="narration"]` | 正文 |
   | 【名称】 | 专有名词 | `[data-k-part="term"]` | 极淡的强调色下划线 |
   | `<!-- 步骤… -->` | 不显示 | — | 原文视图里仍可见 |
   | 段首「　　」 | 首行缩进 | — | ~~电脑保留两字缩进；手机改用段距~~ → **电脑、手机都两字缩进**（用户拍板 C） |

3. **复制、原文视图照样有**：工具不再常驻在正文上方，电脑上悬停时淡入，手机上长按出现。

代价与风险：

- 酒馆和其他插件对 `<content>` 里内容的处理（例如别的插件给正文加的效果）不再生效；只影响 `<content>` 内部，消息的其余部分照旧。
- **流式生成**：正则要等 `</content>` 闭合才匹配，生成期间显示的是酒馆渲染的原文，结束后切成我们的排版，会有一次切换。可选做法见第五节问题 E。

## 三、四个前端怎么协调（回答一 4）

不需要「全都有框」或「全都无框」二选一。平台只规定**结构与节奏**，框不框由皮肤决定：

1. **同一条对齐轴**：四个前端左右边界一致，都受正文行长约束（电脑上不会出现正文窄、选项卡片撑满宽的情况）。
2. **同一套间距节奏**：彼此之间用 `--k-gap-group`，内部用 `--k-pad-card`，圆角用同一档。
3. **三种存在感**（平台给结构，皮肤给外观）：

   | 层级 | 前端 | 定位 |
   |---|---|---|
   | 主体 | 正文 | 阅读区，最安静 |
   | 边注 | 思维链、搜索资料 | 退后：默认收起成一行摘要（「思考了 49 字：先确认场景……」「参考了 3 个来源」） |
   | 操作 | 行动选项 | 可交互：轻量列表，按下时才有存在感 |

4. **框是皮肤的事**：每个前端都有自己的组件钩子（`msg-body` / `msg-think` / `msg-search` / `msg-options`），皮肤用部件 CSS 决定有没有框、框长什么样。
   - 「碎光」：正文无框；边注用一条左侧细线 + 次要色；选项是无框列表。
   - 喜欢卡片的皮肤：给四个都加卡片；因为对齐轴、间距、圆角是共用的，四张卡片自然协调。
   - 也可以只给正文加纸张感的底，边注保持细线。

## 四、各前端的形态（第七条）

| 前端 | 收起时 | 展开 / 交互时 |
|---|---|---|
| 思维链 | 一行：图标 + 「思考了 N 字」+ 首句摘要（截断） | 次要色、略小字号的 Markdown；渲染 / 原文 / 复制；酒馆原生的编辑 / 删除按钮保留 |
| 搜索资料 | 一行：「参考了 N 个来源」+ 来源站点名 | 编号事实列表 + 来源表 |
| 行动选项 | 直接列出选项（每项：类型小标 + 标题 + 一行内容） | 点按：电脑上悬停预览完整内容；按下即填入或发送（沿用现在的「填入 / 发送」切换）；按下时局部碎裂 |

## 五、请用户拍板的问题

- **A. 正文改由我们渲染吗？**（建议：是。不改的话，对白 / 心理描写的加强渲染只能有限地做，而且受酒馆的 Markdown 规则左右。）
- **B. 对白、心理描写、专有名词的默认处理**：上表的建议可以吗？要不要更明显一些（例如对白用强调色）？
- **C. 段首缩进**：电脑保留两字缩进、手机改用段距，可以吗？
- **D. 行动选项的位置**：留在消息末尾（现在的做法），还是只在最新一条消息出现、贴在输入框上方？
- **E. 流式生成**，三选一：
  1. 生成期间看酒馆的原文，结束后切换（最简单，有一次切换）；
  2. 生成期间就用我们的排版逐步渲染（体验最好；要在流式更新时增量挂载，工作量最大）；
  3. 生成期间显示一个轻量的「正在书写」占位，结束后一次性出现（没有切换，但看不到逐字输出）。
- **F. 思维链默认收起成一行摘要**，可以吗？

拍板后先出消息前端的预览（四个前端放在一条真实消息里，电脑 / 手机两种排版，碎光的三档配色）。

## 六、用户拍板结果（2026-10-28）

| 问题 | 结论 |
|---|---|
| A. 正文由我们渲染 | **是**（第二节方案） |
| B. 对白 / 心理描写 / 专有名词 | **按第二节表格的建议**（对白正文色略加粗、引号次要色；心理描写次要色 + 楷体；专有名词淡强调色下划线） |
| C. 段首缩进 | **电脑、手机都两字缩进**（不改段距） |
| D. 行动选项位置 | **留在消息末尾，但只有最新一条回复渲染**；旧消息里的行动选项不显示 |
| E. 流式生成 | **选 2**：生成期间就用我们的排版逐步渲染（流式更新时增量挂载） |
| F. 思维链 | **默认折叠**，收起时显示字数（第四节的「图标 + 思考了 N 字」，首句摘要不是必需） |

## 七、预览实现（2026-10-28）

预览：`design/previews/message/index.html`（模拟酒馆聊天区 + **真的**消息挂载服务；`?scheme=light|dark|reading`）。代码在 `src/frontend/message/`：

| 文件 | 内容 |
|---|---|
| `parse.ts` | 拆回复（思维链 / 搜索资料 / 正文 / 选项），容忍流式时未闭合的标签、对白、JSON；正文切段与行内切分；选项 JSON 容错与旧前端一致；搜索资料直接复用 `src/scripts/_search-pure.js` 的读写格式 |
| `markdown.tsx` | 思维链的轻量 Markdown（只输出 React 节点，无注入风险） |
| `view.tsx` | `MessageView` 与四个前端组件 |

与方案相比的取舍（都在预览里能看到）：

1. **一条回复一个挂载点**，四个前端在同一个渲染面里排（对齐轴、间距天然一致），而不是四个标记各挂各的。
2. **消息前端自己铺底色**（一张「纸」）：酒馆主题可能是深色、皮肤是浅色，透明叠上去保证不了对比度（预览里第一版就是深底深字）。皮肤可以把纸做得很淡，但不能透明。
3. **正文工具**（看原文 / 复制）：电脑上悬停正文时淡入；手机上一直显示但很淡——没用「长按出现」，长按在手机上是选字。
4. 正文里还认 `<n>角色名</n>`（角色名部件）与 `**关键词**`（关键词部件），这两种是 📌 输出规范里有的写法，方案表格里漏了。
5. 行动选项：电脑上悬停 / 键盘聚焦时展开完整内容，手机上显示两行；「填入 / 发送」切换放在选项标题行；模式在新回复上保持。

**用户第二轮意见（2026-10-28）**：思维链显示「奈亚子思考了 N 字」；相关按钮放在前端头部（思维链头部右侧是排版 / 原文与复制，正文头部是字数与看原文 / 复制）；
行动选项的类型标签与标题一起作为头部，内容在下面占满宽度。已改。

**实机（测试酒馆）**：「🧪 消息前端」脚本（`src/scripts/03-消息前端.js`，支线测试包）+ 运行库 `chatFrontend()`（`src/frontend/message/tavern.tsx`），
怎么挂、怎么拿流式原文见[前端契约](前端契约.md) 8.3。支线测试包里「💭 思维链」默认关闭（会和新前端重复）；「📄 正文外壳」构建守卫要求开着，它套的壳在被藏起来的 `.mes_text` 里，看不到。
实机 32 项（电脑 / 手机各一遍）全过。还没验证：切换回复（swipe）、长聊天（上百条）的性能；`.mes_text` 里的图片 / HTML 美化等其他内容现在跟着被藏起来了，要等对应功能迁过来。

## 八、v0.2：内容留在酒馆的 DOM 里（2026-10-29，用户实测意见）

用户在真实酒馆里测 v0.1 后的意见：思维链没生效（main 的「💭 思维链」会把正文里的思维链搬进酒馆原生思维链块，美化是盖在原生块上的）；
对白 / 心理描写的颜色没应用上，**不如直接用酒馆的字体颜色设置**；消息前端要有开关，放显示面板；main 的正文前端做法与其他嵌入式前端不同，
是为了兼容其他往 DOM 里插东西的插件，v0.1 也兼容不了正文里的 HTML 美化；所有前端都要支持 Markdown 与 LaTeX。

所以**拍板 A（正文由我们渲染）与 E（生成期间用我们的排版）作废**，改成与 main「📄 正文外壳」同一个思路：

| 部分 | v0.2 的做法 |
|---|---|
| 正文 | 酒馆自己渲染（markdown、正则、HTML 美化、插件插的按钮都照常）。正则「前端\|正文」的两个空标记之间的节点原样搬进宿主元素；宿主的 Shadow DOM 里是头部（字数 / 看原文 / 复制）和 `<slot>`，正文节点仍在 `.mes_text` 里。字体、颜色全部跟酒馆设置走（拍板 B 的对白 / 心理描写样式随之作废） |
| 思维链 | 「💭 思维链」照常流式搬进 `extra.reasoning`（支线上重新默认开启），只是不再美化；新前端在 `.mes_text` 前面显示它，原生块藏起，编辑 / 删除点的是原生按钮，酒馆进入编辑状态时让回原生块。生成中读它正在扣的内容显示「思考中 N 字」。老楼层正文里内联的思维链也认 |
| 搜索资料 / 行动选项 | 认出酒馆助手渲染的 iframe（`.TH-render` 里保留的源码）后藏起，原位换成我们的；只有最新回复有选项（拍板 D 不变）。选项正则只作用于最后两条，删掉最新回复后新的「最新一条」没有 iframe，就把选项接在 `.mes_text` 末尾 |
| 生成中 | 只更新思维链；正文 / 搜索资料 / 选项等酒馆最后一次渲染之后再接管（流式时酒馆每片都重写 `.mes_text`） |
| 公式 | 酒馆的 markdown 会吃掉 `\(` `\[` `\\` 的反斜杠、把公式里的 `*` `_` 变斜体，所以新增两条显示用正则「前端\|公式(独立 / 行内)」，只在 `<content>` 范围内把公式原样包进 `<code data-kami-tex>`（code 里的内容不被 markdown 动），前端再用 Temml 渲染成浏览器原生 MathML（不需要字体）。前端关掉时显示公式原文。思维链 / 搜索资料 / 行动选项是我们从原文渲染，Markdown 组件直接支持公式 |
| 开关 | 显示面板「消息」一组第一行「消息前端」（localStorage `kami.msgfe`）。关掉：正文放回、标记放回、iframe 取消隐藏，「📄 正文外壳」「💭 思维链」的装饰接回 |

顺带修了 main「📄 正文外壳」的一个老问题：酒馆统计提示词（dry run）也发 `GENERATION_STARTED` 却没有结束事件，它会把套壳停到 3 分钟看门狗超时；现在忽略 dry run。

实机：`test/st/message-next.mjs` 电脑 / 手机（见 test/st/README.md）。还没验证：切换回复（swipe）、长聊天（上百条）的性能。

## 九、v0.3：正文前端开着时由我们排版（2026-10-30，用户意见）

用户：v0.2 的正文等于交回酒馆渲染、只加了字数，「纯偷懒」。要求：**正文前端开着时由我们渲染**（同时支持 Markdown / LaTeX / HTML 美化 / 其他插件插入 DOM），
可以借用酒馆的渲染库，但**样式由我们来渲染**；关掉正文前端才交回酒馆。颜色仍按上次的意见用酒馆的字体颜色设置。

做法（`src/frontend/message/body-style.ts`）：
- Markdown / 正则 / HTML 美化借用酒馆的渲染；我们在酒馆渲染出的节点上**原地**加结构标记——段落、对白（q）、心理描写（em）、关键词（strong）、
  专有名词【…】、场景转换（hr）、公式。只加属性、只在专有名词处拆文字节点，不移动、不替换节点：插件之前插进去的按钮不丢，之后的插件照常找得到正文。
  段首「　　」去掉，缩进交给 text-indent（和预览里的排法一致，拍板 C）。
- 样式就是设计系统与当前皮肤里写给 `[data-k="msg-body"] > [data-k-part="text"]` 的那套正文排版（碎光：宋体、心理描写楷体、专有名词点状下划线、场景转换菱形），
  运行时从样式表里抽出来、前缀改写成 `#chat [data-kami-msg-text]` 放进宿主文档；换皮肤 / 配色时重建。颜色：正文 / 对白 / 心理描写 = 酒馆的 Body / Quote / Em 颜色。
- 生成中也按这套排版（拍板 E 恢复）：酒馆每个片段重写 `.mes_text`，标记在下一个微任务里补上，赶在绘制之前。
- 正文正则只作用于最后两条：更早的楼层没有正文标记，整段 `.mes_text` 按同一套排版。
- 关掉消息前端：标记、样式全部移除，交回酒馆渲染。

实机 `test/st/message-next.mjs` 36 项（电脑 / 手机）：多了「生成中就按我们的排版」「皮肤字体 / 缩进 / 场景转换 / 专有名词 / 对白」「更早的楼层也排」「关掉后标记与样式全部移除」。

## 十、v0.4：依附于消息的前端统一一条渲染管线；底色与字色交给皮肤（2026-10-30，用户意见）

用户：正文、思维链、搜索资料、行动选项以及以后依附于消息的前端，渲染逻辑应该统一（之前只有正文有排版，其他几块没有）。我提了方案 A（四块走同一条管线；
其他前端面板只统一「内容 / 文字」层，控件仍在 Shadow DOM 里），用户同意，并补充：**底色、字体颜色交给皮肤**；显示面板加开关「皮肤字体颜色」，
**默认开**（用皮肤的颜色和底色，盖过酒馆的字体颜色设置），关掉就跟酒馆的字体颜色设置、底色让出来。

一条管线（`src/frontend/message/body-style.ts`、`tavern.tsx`）：
1. **内容由酒馆渲染**：正文就是酒馆渲染好的 `.mes_text`；思维链 / 搜索资料的每条事实 / 行动选项的标题与内容，用酒馆的 `messageFormatting` 渲染
   （Markdown、HTML、正则与酒馆一致）。公式先保护成 `<code data-kami-tex>`，渲染后换成 MathML（Temml）。
2. **内容留在页面 DOM 里**，经 `<slot>` 显示在我们 Shadow DOM 的外壳里：插件插的节点不丢，之后的插件也找得到。正文的外壳就挂在 `.mes_text` 自己身上
   （影子树在酒馆重写 innerHTML 后仍在），所以生成中、生成完、更早的楼层是同一种样子；思维链 / 搜索资料的宿主在 `.mes_text` 前，行动选项在后（只最新一条）。
3. **结构标记**：`markBody` 原地加 `data-k-part`（段落、对白、心理描写、关键词、专有名词、场景转换）。
4. **样式约定**：内容容器标 `data-k-content="body|think|search|option"`；设计系统与皮肤里以 `[data-k-content` 开头的规则就是内容样式——
   影子树（预览）里直接生效，页面里由运行时抽出来加 `#chat ` 前缀放进宿主文档。令牌、颜色、字体经 slot 从外壳继承。皮肤写一份，四块都用上。

### 10.1 实测后的三处修正（2026-10-30，用户：「皮肤字体颜色看不出区别」「显示按钮总会掉」）

- **碎光有了自己的对白 / 心理描写颜色**：之前皮肤没定义 `--k-msg-dialogue` / `--k-msg-thought`，对白与正文同色，开关开着时看不出「皮肤字色」。
  现在：宣纸 对白 `#2c6a58`（青瓷压深）、心理描写 `#6b6356`（淡墨）；墨 `#9ccfbd` / `#aaa294`；阅读 `#7a4520`（赭）/ `#6a5c49`。关掉开关时仍换成酒馆的 Quote / Em。
- **「🎨 显示」按钮会掉**：「🧪 显示」登记按钮时只给了一次 `ping`，没有心跳；按钮中转站 3 分钟收不到 ping 就当登记方已死、撤下按钮（旧 🎨 又已让位）。补上 2.5 秒心跳（与工具箱 / 预设设置 / 引导一致）。
- **长聊天性能**：之前每次 DOM 变动（流式每个片段）都把全部楼层重查一遍，`STREAM_TOKEN_RECEIVED` 还会让所有楼层重画。实机 100 楼：每次 15ms。
  改为增量：观察器只记下变动的楼层；单楼事件（流式片段、编辑、切换回复、思维链编辑）走 `touch(id)` 只查那一楼；生成开始 / 结束、换聊天、删除、改设置才全部重查。
  实机 113 楼流式：每次中位 0.5ms。
