## 〇、结论先行

1. **推荐数据模型乙（名字带组），但写法要改一个字序。** 不建议写成任务单里的
   `<名字> | 自定义文风 | <组名>`，建议写成 **`<名字> | <组名> | 自定义文风`** ——
   这样标记落在名字**末尾**，与已有 ` | var` ` | model` 的 `endsWith` 约定完全同构
   （`test/harness/preset-parse.mjs:25-26,328-329`）。理由见第三节。
2. **任务单里模型甲的前提要纠正一处**：解析器**不看 `prompts[]` 的顺序**。
   `preset-parse.mjs:189` 是 `orderArr.forEach(...)`，它按 **`prompt_order[0].order` 的排列**
   展开条目。所以「位置法」的位置指的是 **order[] 里的位置**，而且还要满足
   「同一层区间内、卡片头之后、下一个卡片头之前」（`preset-parse.mjs:362-377`）。
3. **位置会被远程更新搬走，而且不弹提示。** `_preset-merge.js:319-333` 的合并逻辑把
   「不在基准序列里的存活条目」一律**追加到表尾**；`_preset-merge.js:356-361` 又明确把
   用户自加的新条目排除在「谁调过排列」的判定之外。两条合起来 = 一次预设更新就可能
   把用户的自定义文风从 `[写作文风]` 组里甩到整个预设末尾，而用户看不到任何提示。
   **这是推荐模型乙的决定性理由。**
4. **「选一」互斥是脚本层保证的，不是酒馆保证的**（`40-预设设置.js:3033-3048`、
   `50-引导.js:1404-1415,1452-1460`），而它依赖解析器把条目归进那张卡 —— 归组又靠位置。
   所以**条目一掉出组，互斥就静默失效**，用户能同时开两个文风。
5. **全仓没有任何「新增/删除预设条目」的先例**（`prompts.push/splice`、order 增删均为 0 命中）。
   这条通道要新开，而且必须真机验证 —— 见 R2。
6. **落点**：按 `50-引导.js:16-21` 自述的架构规则（引导页「自己不碰预设，全部走各脚本暴露的
   现成 API」），**结构写入必须落在 `40-预设设置.js`**，作为 `KamiPreset` 的新方法暴露；
   引导页只负责渲染与调用。本轮不建议在引导页里直接写预设。

## 二、现状里两个必须知道的事实

**事实一：解析器走 order，不走 prompts。**
`preset-parse.mjs:189` `orderArr.forEach((o, index) => {...})`，`:209` `:index = index`，
`:214` `enabled: o.enabled === undefined ? p.enabled : o.enabled`。
后果：
- `prompts[]` 里有、`order[]` 里没有 → **完全不可见**（不会被遍历到），**不报错**
- `order[]` 里有、`prompts[]` 里没有 → 记一条 `level: 'error'` 的 issue 然后 `return` 跳过（`:190-193`）

**这两种「半截条目」都不会让面板崩。** 现成证据：这份预设自己就有 4 条这种状态 ——
`main` / `nsfw` / `jailbreak` / `enhanceDefinitions`（181 − 177 = 4），它们是酒馆内置条目，
属于正常容忍状态。**反过来说：自定义条目写半截也不会有任何报错，只会静默消失。**

**事实二：解析器收集的 `issues` 运行时没人读。**
`40-预设设置.js` 与 `50-引导.js` 里 grep `issues`：**各 0 命中**。
解析器只在 `prompt_order` 整体为空时 `throw`（`preset-parse.mjs:181`）。
所以解析期的任何结构异常**都不会浮到界面上**。

## 三、两个数据模型的对比与推荐

### 模型甲 · 位置法
名字只写 `<用户起的名字> | 自定义文风`，归属靠它在 `order[]` 里的位置。

### 模型乙 · 名字带组
归属从名字里解析出来。**推荐写法**：`<名字> | <组名> | 自定义文风`
（任务单原写法是 `<名字> | 自定义文风 | <组名>`，见下方「写法」一节）

| 维度 | 甲 · 位置法 | 乙 · 名字带组 |
|---|---|---|
| **解析成本** | 零解析。但「归属」这件事**根本没有可读的真相**——每次都要重新走一遍位置推算 | 一次 `endsWith` + 一次切分。与 `\| var` `\| model` 同一套写法 |
| **改名** | 改名字零成本 | 改「名字」段零成本；改「组名」段 = 改一个字符串，条目原地不动 |
| **移动组** | **要动数组元素**：必须同时改 `prompts[]` 与 `order[]` 的相对位置，两个数组都得保持一致 | 改名字里那一段就行。**数组一个元素都不动** |
| **名字长度/观感** | 短（只多一个标记） | 长（多一段组名）。但卡片上本来就要把标记剥掉再显示，实际观感只差「组名要不要显示」 |
| **预设可读性** | **差**。打开预设文件只看得到一条条 `xxx \| 自定义文风`，得靠上下位置才知道属于哪组 | **好**。一眼看出归属，不依赖上下文 |
| **抗手改** | **最差**。用户手改预设时「挪一行」比「改一个词」自然得多；挪错一次就静默掉组（见事实一，无任何报错） | **好**。名字是自解释的，改坏了也看得出来 |
| **抗远程更新** | **最差**。`_preset-merge.js:319-333` 会把用户自加条目在 `winner==='next'` 时**追加到表尾**，直接掉出组；`:356-361` 还保证**不弹提示** | **好**。名字里带着组名，被搬到哪里都还认得出；面板可以按名字归位 |

### 推荐：模型乙（名字带组）

三条决定性理由：

1. **位置会被远程更新搬走，而且用户不会知道。**
   `_preset-merge.js:319-333`：合并后的 order 先按 base 序列排（`winner==='next'` 时 base = next 的序列），
   再把「合并后还存在、但不在 base 序列里」的条目**补进表尾** —— 注释原文就写着
   「用户自加的在 theirs 段、新版新增的在 next 段」。
   而 `:356-361` 的 `knownSet` 明确把「theirs 独有的新条目」排除在「谁调过排列」的判定之外。
   两条合起来：**一次「新版往文风组里加了个新风格」的更新，就可能把用户的自定义文风甩到整个预设末尾，
   并且不产生任何待裁决项。** 而新版往文风组加风格，恰恰是这个预设最常见的更新形态。
2. **位置法把「归属」存进了一个没有名字的地方。** 它存在「两个数组的相对位置」里，
   而这个位置同时被解析、被合并、被用户手改三方改。名字法是**把一个字符串存在名字里**，
   任何一方改坏了都看得见。
3. **移动组的代价差一个数量级。** 甲要动数组（且要维持两个数组一致），乙只改一个字符串。

### 关于写法：建议改成 `<名字> | <组名> | 自定义文风`

任务单原写法 `<名字> | 自定义文风 | <组名>` 的问题：**标记不在末尾**，
与已有约定不同构 —— `preset-parse.mjs:328-329` 判定 ` | var` / ` | model` 用的是 `endsWith`。
用原写法就得改成 `indexOf` 判断，等于给「标签约定」开第二个判据，
以后谁改解析器都要记住「这个标签特殊」。

`<名字> | <组名> | 自定义文风` 的写法：`endsWith(' | 自定义文风')` 成立，与现有标签**完全同构**，
组名在中间可切分，且标记永远在最后不会被别的东西挤走。

代价：组名夹在中间，人读预设时不如「标记紧跟名字」直观。**这是可接受的取舍**，
但如果你更看重预设里的直观度，也可以坚持原写法 + `indexOf`，那我建议在常量旁边写一句
为什么这个标签不用 `endsWith`。**这条要 Lead 定。**

### 组名用什么做锚

**不要用卡片头的显示名**（如 `🖊️ [写作文风]`）—— 它会被改名，而改名后这张卡会
从引导的 `PAGE_GROUPS` 精确对位里退场（`50-引导.js:65-66,419-420`）。

两个可选锚：
- **卡片头的 identifier**（`prompt_1789202230919_g831g9s` / `prompt_kami_style_opt`）——
  这是项目自己声明的「主键一律用完整 identifier」（`40-预设设置.js:349-350`），最稳。
  但它太长，不适合写进名字。
- **短 slug**（如 `write` / `opt`），在 `40-预设设置.js` 里维护一张
  `slug → 卡片头 identifier` 的映射表，解析时用 identifier 找卡片。
  **推荐这个**：名字短、锚稳、改显示名不影响。

## 四、风险清单

### R1 · 硬阻断级：新增/删除必须同时维护两个数组，否则静默失效

- `prompt_order` 少一条 → 该条目**完全不可见**，不报错（`preset-parse.mjs:189-193`）
- `prompts` 少一条 → order 里留孤儿，解析时记 error issue 后跳过，**也不报错**（`:190-193`），
  而 issue 运行时无人消费（事实二）
- **两侧必须同增同删，且相对顺序一致。**
- 删除时若只删 `prompts[]`：预设进入不一致状态，**要等下一次合并才自愈**
  （`_preset-merge.js:323` 只保留 `mergedSet` 里的 id）—— 这不是设计，是巧合。

### R2 · 高风险：结构写入这条通道没有先例，必须真机验证

- 全仓没有 `prompts` / `order` 增删的先例（第一节 1.3 已列证据）。
- **推断（未验证）**：往**活设置**的 `settings.prompts` 与 `settings.prompt_order[0].order`
  里增删条目，再走 `savePresetFile()`（`40:613-670`）点 `#update_oai_preset`，
  理论上能无损落盘 —— 依据是 `:606-609` 那句「请求体由 getChatCompletionPreset() 从活设置
  按酒馆自己的字段表组装，prompts / prompt_order 整段 structuredClone」。
- **但这条推断没有任何代码先例、没有单测。** 必须验证：
  1. 落盘后 `prompts` 与 `order` 条数是否都 +1 / −1（`watchSave` 的 `:507-509` 自证读数可直接看）
  2. 重载预设后条目还在不在
  3. 相邻条目的字段有没有被顺手改掉（对比写盘前后）
- **验证不过就退回「只读展示 + 引导用户手动改预设」**，不要硬上线。

### R3 · 中风险：`prompt_order` 本身会不会被写坏

- **`character_id` 必须动对。** `pickOrder()`（`40:225-235` / `50:267-277`）优先 100001，
  取不到退到「条数最多的那一条」。这份预设只有一条，所以安全；
  **但用户导入的预设可能有多条** —— 建议操作前断言
  `prompt_order.length === 1 && prompt_order[0].character_id === 100001`，不满足就拒绝写入。
- **不要碰 `forEach` 之外的字段。** `order[]` 每一项还有 `enabled`；新增时要给默认值
  （参考 `_preset-merge.js:342` 的 `enabledOf`，以及 `preset-parse.mjs:214` 的回退规则：
  `o.enabled === undefined` 时读 `p.enabled`）。
- `:345-358` 已登记的禁令照旧适用：**绝不走** `replacePreset / updatePresetWith / setPreset`。
- 未知：酒馆是否对 `prompts[]` 自身的顺序有额外假设（本仓代码只证明解析器走 order）。
  **不确定**，所以新条目在 `prompts[]` 里的插入位置建议**紧挨同组现有条目**，
  不要图省事 append 到数组末尾。

### R4 · 中风险：「选一」互斥会被破坏（两个方向）

- **掉出组 → 互斥失效**：条目一旦不在卡片头与下一个卡片头之间，
  它就不在 `rec.items` / `grp.items` 里（`40:3040-3048`、`50:1408-1415` 都按组内 items 遍历），
  于是**用户能同时开两个文风，且没有任何提示**。这正是模型甲最现实的失效形态。
- **留在组里 → 参与互斥（期望行为，但要告知）**：自定义条目开的时候会把
  `[写作文风]` 组内其它 **23 条**全部关掉。UI 必须提前说明。
- **目标组的模式不一样**：`🖊️ [写作文风]` 是**选一**，`✒️ [文风优化]` 是**任选**
  （`preset.base.json:2655` vs `:2603`）。把自定义条目指到「文风优化」组，
  语义从「选一个」变成「可叠加」。**UI 必须把目标组的模式显式标出来**，
  否则用户会以为「都是文风，行为应该一样」。
- **不要新造互斥逻辑**：现有两处实现（`:3040-3048`、`:1408-1415`）已经把互斥建立在
  「解析器算出的组」上。自定义条目只要正确进组，互斥自动生效，**一行新互斥代码都不用写**。

### R5 · 中风险：新条目的字段表

现有条目的字段（`preset.base.json:2596-2605` 等）：
`content / enabled / forbid_overrides / identifier / injection_depth / injection_order /
injection_position / marker / name / role / system_prompt`。

- **少字段会怎样 —— 不确定。** 这轮没验证过。
- 保守做法：**克隆同组一条现有条目的字段表**，只替换 `identifier` / `name` / `content`（含 `enabled` 默认 false）。
- `identifier` 形态观察：这份预设里有**三种**约定 ——
  纯 UUID 62 条、`prompt_` 前缀 104 条、`prompt_kami_` 前缀 2 条。
  酒馆自动生成的是 `prompt_<时间戳>_<随机>` 形态，**新条目沿用这个形态最不突兀**。

### R6 · 低风险：` | 自定义文风` 标记的唯一真相放哪

**推荐放在 `test/harness/preset-parse.mjs` 顶部的常量区（第 25-28 行那一块）。**

理由：
- 那里已经是 `VAR_SUFFIX` / `MODEL_SUFFIX` / `CARD_ONCE` / `CARD_ANY` 的住处，**是既有的唯一真相位置**
- 解析器是**构建期内联**进 `40` 与 `50` 的（`40:16,123`、`50:12,166`），
  常量跟着一起进去，两个面板天然同源，不会分叉
- 反面教材就在眼前：`_preset-cards.js:10-13` 的头部注释写着，
  同一枚组件在两个脚本里各写一套，已经因此丢过两次功能，这是**第三次收口**。
  标签解析绝不能重演 —— **只能有一份 `parseCustomName()`**
- 需要导出两个东西：`CUSTOM_SUFFIX` 常量 + `parseCustomName(name) → { base, group }`
- **不建议**新建独立的 `_custom-style.js`：多一份要内联的模块，而读写方已经共享解析器了

### R7 · 低风险：名字里的分隔符与 emoji

- 用户起的名字里可能本来就含 ` | `。解析要**从右往左**切（先剥末尾标记，再切最后一个分隔符），
  不要 `split(' | ')[0]`。
- 名字里的 emoji 会被摘成卡片角标（`_preset-cards.js:70-94`），最多 4 枚、有注释时 3 枚（`:164`）。
  这是既有行为，不是 bug —— 但自定义文风的 UI 要提示「名字里的 emoji 会变成角标」。
- 带组名后名字更长，卡片会变高（`_preset-cards.js:167-169` 说明名字故意放在会换行的 `.kami-item-main`）。

### R8 · 低风险：两条渲染路径要一起改

- 引导的**文风页**自己建结构（`50-引导.js:1336-1354`，`.kami-guide-plate`）
- 引导的**模型页**与预设面板走 `_preset-cards.js` 的 `buildItemCard`
- 自定义条目在文风页显示，但用户在预设面板里也能看到它（它在预设里就是普通条目）。
  **两边的名字处理（剥标记/剥组名）必须是同一个函数**，否则会出现「面板显示全名、引导显示短名」。
