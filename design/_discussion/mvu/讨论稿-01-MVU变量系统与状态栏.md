## 二、MVU + zod 到底能给我们什么

1. **每楼层一份变量**：模型在回复里输出 `<UpdateVariable><JSONPatch>…`，
   MVU 自己扫出来、算好、存进这一楼的变量里，不依赖上下文里有没有旧楼层。
2. **zod 管类型与兜底**：`registerMvuSchema(Schema)` 之后，缺的字段会被自动补上、
   越界的数字会被自动夹回范围。模型写歪了，能救回来一部分。
3. **两个隐藏前缀**：字段名以 `_` 开头 = 模型能看不能改；
   以 `$` 开头 = 模型完全看不到，留给脚本和前端用。
4. **状态栏的正规姿势**：MVU 会往它处理过的消息尾部放 `<StatusPlaceHolderImpl/>`；
   一条 `promptOnly` 正则把它对模型隐藏，另一条 `markdownOnly` 正则把它替换成前端 HTML，
   前端在自己的 iframe 里读**本楼层**的变量。
   → 和我们已经跑通的两个前端是同一种东西，只是数据源从「消息文本」变成「楼层变量」。
5. **前端接口是固定的几条**：等 `Mvu` 就绪、取本楼层变量、监听变量更新事件后重画。
6. **模型看到的不是 schema，而是提示词**：schema 管校验，
   给模型看的是「当前变量值的 JSON」+「更新规则」+「输出格式」这三样。
   预设提供这三样，正好就是我们最擅长的地方（条目 + 开关）。

## 三、这套东西和「角色卡自带变量」的关系（最关键的一题）

一张卡自己带 MVU 变量结构是常态。所以必须先定**归属**：

| 路线 | 卡自带变量时 | 卡不带变量时 | 风险 |
|---|---|---|---|
| A 只补位 | 完全不管，状态栏也不显示 | 上我们的通用结构 + 状态栏 | 用户会觉得「有时有有时没有」 |
| B 补位 + 自适应（我推荐） | 状态栏照常显示，但只读卡的数据、不注册我们的 schema | 上我们的通用结构 + 状态栏 | 自适应渲染要做得好，否则长得丑 |
| C 常驻 | 也上我们的结构 | 上我们的结构 | 两份 schema 打架，最不推荐 |

`registerMvuSchema` 是全局注册，**两张结构同时注册会怎样还没验证过**——
这是路线 C 的硬伤，也是路线 B 要先确认的第一件事。

## 四、待你拍板的四件事

1. **定位**：走上面哪条路线？（我建议 B）
2. **形态**：状态栏是「每条 AI 消息底部一个」，还是「只贴最新一层」，还是「悬浮固定在屏幕上」？
   移动端屏幕小，每条消息都塞一个会又长又重复；我倾向**楼层内嵌 + 默认折叠成一条细栏**。
3. **谁写变量**：主模型直接在正文末尾输出补丁（零额外成本、占输出长度），
   还是用 MVU 的「额外模型解析」（另开一次便宜模型的请求，把正文喂给它专门产出补丁）？我倾向做成开关，默认前者。
4. **显示什么**：通用 RPG 那一套（时间/地点/在场人物/关系/物品/任务）？
   还是轻量一套（时间/地点/在场人物/当前目标）？
   还是**由 schema 自动生成**（数字出进度条、字符串出文本、列表出条目，皮肤只管外观）？

## 五、我建议的推进顺序（等上面定了再细化）

- **阶段 1 · 打通链路**：一份正式的 zod 通用结构 + 三条提示词条目（变量列表 / 更新规则 / 输出格式）
  + 两条正则（隐藏占位符、渲染状态栏）+ 状态栏前端 v1 + 四套皮肤各补一套状态栏外观。
  目标：一条真实对话里，变量能被正确初始化、被模型更新、状态栏能画出来。
- **阶段 2 · 自适应与开关**：状态栏自适应渲染（不看 schema 也能画）、
  显示范围与折叠方式交给用户在面板里调、接入「🌟卡密预设」面板。
- **阶段 3 · 共存与引导**：把 00 脚本的探测逻辑转正（卡自带变量时不插手）、
  额外模型解析开关、接进「引导」脚本的初始化流程。

## 六、必须在动手前验掉的坑

1. **schema 归属**：卡自带变量结构时，我们的注册要不要退让？退让后状态栏怎么知道该读谁。
2. **没有世界书怎么初始化**：00 脚本这条自建变量的路子必须真机跑通一次，否则一切免谈。
3. **iframe 数量**：每条消息一个状态栏 iframe，几十层楼的性能与视觉重复，得先定显示范围。
4. **反截断脚本**：它把请求改造成工具调用（`src/scripts/20-反截断.js`），
   会不会破坏 `<UpdateVariable>` 在正文里的解析，要专门验证一次。
5. **四套皮肤的工作量**：状态栏是新前端，记事本/恋雨/辉光管/奈亚子的TRPG 都要补一套外观。
6. **和现有酒馆宏变量的分工**：`cot_budget` 那些设置继续用宏变量，MVU 只管剧情状态，不要互相搬迁。
