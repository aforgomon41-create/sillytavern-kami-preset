## A. 调研一：怎么认出「这张卡已经有变量 / 状态栏了」

你要求「卡自带变量我们就不出现」，这句话落到实现上就是**一张信号表**。
市面上的做法一共就这几类，各自的识别特征如下（都是可机械检测的字符串或对象）：

| 体系 | 是什么 | 识别特征 |
|---|---|---|
| **MVU（MagVarUpdate）** | 目前事实标准，两层命令风格：Beta（`_.set`）与 ZOD（JSON Patch），**两套互不兼容** | 世界书条目名含 `[initvar]` / `[mvu_update]`；条目内容含 `<UpdateVariable>`、`_.set(`、`<initvar>`、`{{get_message_variable::stat_data}}`、`{{format_message_variable::`；角色卡自带脚本里 import `MagVarUpdate` 或 `registerMvuSchema`；正则里出现 `<StatusPlaceHolderImpl/>`；开场白里有 `<initvar>` 块 |
| **SAM**（态势感知管理器） | 扩展 + 核心脚本，靠世界书锚点激活 | **世界书条目的「注释」里有 `__SAM_IDENTIFIER__`**；宏 `{{SAM_serialized_memory}}` / `{{SAM_serialized_db}}`；正文里被插入隐藏数据块、指令形如 `@.insert(key="…")` |
| **ST-VarSystem** | 可视化变量管理扩展 + 后端插件，支持 MVU 与 SAM 两种语法 | AI 消息里出现 `<VarSystemStatusPlaceholder/>`；聊天变量 `vs_stat_data` |
| **Horae 时光记忆（记忆增强类）** | 扩展形态的记忆插件，自带一批正则，自己在管时间/关系/物品/待办 | 页面存在 `window.Horae`；它的设置里对应模块开着；提示词里被注入了它的表格 |
| **酒馆原生 / 散装** | 没有框架，靠 `{{getvar::}}`/`{{setvar::}}` + 正则 + 提示词模板拼出来的好感度或状态栏 | 角色卡自带正则的替换内容里有状态栏 HTML 或占位符；世界书里有 `setvar` 写变量；开场白里直接带状态栏结构 |
| **纯正则状态栏** | 用正则把消息里的固定文本美化，不涉及变量 | 角色卡自带正则的替换串是一大段 HTML |

**退场判断的建议顺序**（从便宜、确定的开始，命中即退场）：

1. 本会话的消息变量里**已经有变量数据**（`stat_data` 非空）→ 直接退场；
2. 扫世界书：条目名/注释/内容命中上面的关键词表 → 退场；
3. 扫角色卡自带脚本：内容含 `MagVarUpdate`、`registerMvuSchema`、`__SAM_IDENTIFIER__` 等 → 退场；
4. 扫角色卡自带正则：出现状态栏占位符或大段界面 HTML → 退场；
5. 扫开场白与最近几条消息：出现 `<initvar>`、占位符、数据块 → 退场；
6. 全都没命中 → **我们接管**：写变量结构 + 显示状态栏。

第 1、2、3 步现有代码里已经有雏形（`src/scripts/00-mvu初始化测试.js:95-139`：
`isInitialized()` 查变量、`looksLikeMvuCard()` 查世界书条目名与开场白标记），
我们要做的是把它扩成上面这张完整表，并且**加一个明确的人工开关**（用户说「这张卡我自己有」就永久退场）。

要区分两件事：**卡自带**（要对卡退场）和**用户自己装的扩展**（Horae、ST-VarSystem）。
后者不是卡的属性，只能提示一次，别自动退场。

## B. 调研二：MVU 的「随AI输出 / 额外模型解析」到底是什么机制

**设置存在哪**：`SillyTavern.extensionSettings.mvu_settings`（全局设置，页面加载时读进 MVU 内部）。
关键字段就是 `更新方式`，取值只有两个：`'随AI输出'` 或 `'额外模型解析'`，默认前者。

**额外模型解析能配什么**（都在同一份设置里）：
破限方案（内置破限 / 使用当前预设 / 使用其他预设）、应答格式（聊天消息 / 工具调用 / 格式化输出 / 格式化输出-v4兼容）、
关闭 thinking、兼容假流式、随机头部、是否自动触发、请求方式（依次重试 / 同时多次 / 先一次再多次）、请求次数、
给额外请求用的**世界书条目白名单与黑名单正则**、模型来源（与主插头相同 / 自定义 / 更多）、api 地址、密钥、模型名、
温度、频率惩罚、存在惩罚、top_p、top_k、带入的历史轮数、最大回复 token、以及多套可保存的 api 方案。

**还能按角色卡覆盖**：`更新方式`、`额外模型解析配置.启用自动请求`、`兼容性.更新到聊天变量`、
`兼容性.sendas不视为user消息` —— 这份覆盖数据挂在**世界书条目**上（内部记的是世界书名 + 条目 id + 内容）。

**运行时**：`Mvu.isDuringExtraAnalysis()` 能问「现在是不是额外模型正在解析」，
同时 MVU 会往全局变量写一个 `extra_analysis` 布尔值。

**对外接口只有这些**：`getMvuData` / `replaceMvuData` / `parseMessage` / `isDuringExtraAnalysis`，
加事件 `VARIABLE_INITIALIZED`、`VARIABLE_UPDATE_STARTED`、`COMMAND_PARSED`、`VARIABLE_UPDATE_ENDED`。
**没有一个「切换更新方式」或「现在跑一次额外解析」的公开接口。**

所以我们有三条路，我推荐第三条：

1. **读它的设置、跟着它走**：我们只读 `mvu_settings.更新方式`，
   用户自己在 MVU 面板里选了什么我们就当什么。成本最低，也最不容易打架。
2. **替它改设置**：`extensionSettings` 是明文对象，我们写得进去、也能触发保存。
   但 MVU 内部的内存设置只在**页面加载 / 脚本被重新启用**时刷新，写完当场不一定生效，
   用户会看到「我点了个开关，但它没反应」。不推荐当交互用。
3. **我们自己实现额外解析（推荐）**：用酒馆助手的生成接口另发一次请求（地址/密钥/模型由用户在我们的面板里配），
   把正文交给它，用 `Mvu.parseMessage()` 解析出补丁，再用 `Mvu.replaceMvuData()` 写回本楼层。
   好处：触发时机（只在正文没带补丁或补丁解析失败时才补）、模型、开关全归我们；
   坏处：多写一段逻辑，且**必须先读 `更新方式`**，用户在 MVU 面板里选了「额外模型解析」时我们别再跑一遍，否则同一层会更新两次。

## C. 变量结构草案 v0

### C.0 六条设计约束（先说清楚，不然结构没法评）

1. **每轮都要发给模型**：变量列表是常驻上下文，字段越多越贵 → 字段要少、值要短。
2. **zod 4 的写法限制**：默认值用 `.prefault()` 不用 `.default()`；数值范围用 `.transform(夹紧)` 不用 `.min/.max`；
   容器优先 `z.record()` 少用数组；不用 `.optional()/.strict()/.passthrough()`；`.transform()` 只收一个参数。
3. **世界无关**：预设配的是任意卡（现代/奇幻/科幻/校园/跑团），字段不能带世界观色彩。
4. **模型友好**：路径要短（层级 ≤3）、键名固定、键名用中文短词，模型手写 JSON Patch 才不容易歪。
5. **前端友好**：数字能画条、字符串能出文本、`record` 能出列表，状态栏不用为每张卡改代码。
6. **可增删**：人物、任务、物品天然是「模型自己长出来的」，要用 `record` 让它可以自由增键。

### C.1 骨架（标准版）

| 路径 | 类型 | 含义 | 怎么更新 |
|---|---|---|---|
| `世界.时间` | 字符串 | 故事内时间，如「第3天 傍晚 18:40」 | 剧情推进到跨时段才改 |
| `世界.地点` | 字符串 | 当前场景，如「旧城区·废弃教堂」 | 换场景才改 |
| `世界.概况` | 字符串 | 一句话：天气/氛围/正在发生什么 | 每次回复都可改 |
| `世界.在场` | 字符串 | 这一场景里有谁，顿号分隔 | 有人进出才改 |
| `主角.状态` | 字符串 | 身体+精神一句话 | 受伤/疲惫/情绪转折时改 |
| `主角.目标` | 字符串 | 当前短期目标 | 目标达成或改变时改 |
| `人物.<名字>.关系` | 字符串 | 与主角的关系，如「青梅竹马」 | 关系阶段变化时改 |
| `人物.<名字>.好感` | 数字 0–100 | 态度数值 | 有明显互动时小幅变 |
| `人物.<名字>.状态` | 字符串 | 当前情绪/身体状态 | 每次互动可改 |
| `人物.<名字>.在场` | 真假 | 是否在当前场景 | 进出场景时改 |

「人物」是模型自己增删的容器：新角色登场才加，离场**不删**（好感与关系要留着）。

### C.2 三个可选分组（用户在面板里开关，各自增加上下文成本）

- **物品**：`物品.<名称>` = 数量（数字）。只记会消耗、会失去的东西，描述性物品不进。
- **任务**：`任务.<名称>` = 状态（「进行中 / 已完成 / 已放弃」）。
- **线索**：`线索.<名称>` = 一句话（伏笔、秘密、已知情报）。这个对长篇连贯性最有用，也最占字数。

### C.3 两个特殊前缀的用法

- `$` 开头 = **模型完全看不到**，只给脚本和前端用：`$结构版本`（结构升级时用来迁移）、`$启用`、`$配置`。
- `_` 开头 = **模型能看不能改**：`世界._类型`（现代/奇幻/科幻，脚本按卡或用户设置填）、`主角._名字`（用玩家人设名填）。
  这两个字段是「给模型定基调」的，让它知道该用哪套世界观写。

### C.4 初始值从哪来（这是「补位」方案最值钱的地方）

预设比角色卡多知道几件事，可以拿来做种子，让状态栏**第一轮就有内容**：

- `主角._名字` ← 当前玩家人设名（宏替换）；
- `人物` 里预填**卡的主角名**（`{{char}}`）一条，关系留空，等第一轮回复补；
- `世界._类型` ← 用户在我们的面板里选，或按卡的标签猜；
- 其余字段填空串/0，靠 zod 的 `prefault` 兜底，第一轮由模型补全。

### C.5 还没法定的三件事（定了 C 才算完成）

1. **初始值、结构、更新规则是一套三件**：结构只解决「有哪些字段」，
   每个字段「什么条件才变」得写进给模型的更新规则条目，否则模型会乱改或漏改。
2. **token 成本要量**：这份结构每轮都发。我的估算方法是不靠猜 ——
   写好草案后，用真机发一轮，在提示词查看器里看「变量列表」条目占多少 token，再决定要不要砍分组。
3. **结构版本与迁移**：以后改结构，老聊天里的旧数据会缺字段（`prefault` 能补），
   但改名/删字段会留垃圾，需要一个 `$结构版本` + 一次迁移。

## D. 需要你定的三件事

1. **骨架认不认**：`世界 / 主角 / 人物` 这三块是否是你要的最小集？要加（如「势力」「日程」「身体状态」）还是砍？
2. **人物块**：只跟踪「卡的主角 + 剧情重要角色」（模型自己判断加谁），还是允许用户手动预填几个？
3. **可分组认不认**：物品 / 任务 / 线索 三个开关式分组，默认开哪几个？
