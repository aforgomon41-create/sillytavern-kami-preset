## 一、六条命门逐条核对

### ① `registerMvuSchema` 是不是全局注册？两张 schema 同注册会怎样？

**是全局注册，而且比"注册一次"更激进 —— 它在每次事件里重新注册。**

证据：`src/scripts/00-mvu初始化测试.js:1` 从 `https://testingcf.jsdelivr.net/gh/StageDog/tavern_resource/dist/util/mvu_zod.js` 导入。
我把那份 `mvu_zod.js`（4505 字节，压缩成一行）取下来读了，关键结构是：

```js
function s(s) {                       // s 就是 registerMvuSchema
  const a = () => {
    const t = typeof s === 'function' ? s() : s;
    const e = t instanceof r.z.ZodObject ? r.z.looseObject(t.shape) : t;
    return typeof registerVariableSchema === 'function'
      && registerVariableSchema(r.z.object({ stat_data: e }), { type: 'message' }),
      e;
  };
  a();                                                      // ← 注册一次
  eventOn('mag_variable_initialized', (t, e) => {
    const s = a();                                          // ← 每次事件**再注册一次**
    const a2 = s.safeParse(_.get(t, 'stat_data', {}), { reportInput: true });
    if (a2.success) return void (t.stat_data = { ...t.stat_data, ...a2.data });
    n('error', r.z.prettifyError(a2.error), `开局 '${e + 1}' 变量初始化失败`);
  });
  eventOn('mag_command_parsed_for_zod', (r2, s2, c, u) => {
    const l = a();                                          // ← 这里又一次
    ...
  });
  eventOn('mag_variable_update_ended_for_zod', t => { ... });
}
export { s as registerMvuSchema };
```

从这段能确定三件事：

1. **注册是全局的、按 `type:'message'` 登记**（`registerVariableSchema(schema, {type:'message'})`），**不是按角色卡**。所以同一份 preset 的一套 schema 对所有卡生效。
2. **两张 schema 同时注册不会抛错、不会互相顶掉** —— 因为每个事件回调里都**各自 `a()` 一次拿到自己的 schema**，再用**自己的** schema `safeParse`。
3. **后果是字段叠加，不是崩溃**：用的是 `looseObject`（未知键原样放行），校验后又 `{ ...t.stat_data, ...a.data }` 合并回去。所以 A 的 prefault 和 B 的 prefault **会都落进同一份 `stat_data`** —— 也就是讨论稿表格里路线 C 说的"两份 schema 打架"，**真实形态是"变量表被撑大/互相污染"，而不是报错**。这比崩溃更隐蔽。

**未确证的一处**：`registerVariableSchema` 自己的存储语义（是一个 `type → schema` 的 map、还是数组、后者会不会覆盖前者），以及 **MVU 本体读的是哪一份**。要确证得读 MVU 的 `artifact/bundle.js`，那是个体积很大的压缩包，我这轮没读成。**这一条影响的是"MVU 原生 UI 显示哪套结构"，不影响上面三条结论**（那三条只依赖 `mvu_zod.js` 自身）。建议动手前补一次。

**对路线选择的推论**：路线 B（卡自带变量时不注册我们的 schema）是对的，而且理由比讨论稿写的更硬 —— 不是"怕打架"，是**打架的后果是静默的字段污染**。

### ③ iframe 数量与现有前端的控制方式

**现在是"每个匹配到的楼层一个 iframe"，没有任何收敛。**

- `docs/皮肤契约.md:105`：「皮肤 CSS 会被注入到**每一个聊天楼层**的 iframe 里，**一个楼层一份**」
- `docs/皮肤契约.md:18 / :30 / :43`：皮肤管理脚本往「酒馆页面 + **每个消息 iframe**」下发
- `docs/皮肤契约.md:342`：`think` → `frontend-think.html` → 「**消息 iframe 里的组件根**」
- `src/regex/list.json:72-88`：思维链那条 `markdownOnly` 正则，`findRegex` 匹配到几层就替换几层 → 几个 iframe

**所以"三层消息 / 十层消息"分别是 3 个 / 10 个 iframe（前提是每层都含前端标记）。**

**现有两个前端都没有"只贴最新一层"的先例** —— 它们是"匹配到就贴"。
这对状态栏是个**真问题**：思维链是"这一层有思考就看"，重复出现是合理的；状态栏是"当前状态"，**每一层都贴一份会又长又重复**，而且每多一个 iframe 就多一份皮肤 CSS 注入。

→ 阶段一按 Lead 定的"楼层内嵌 + 默认折叠成一条细栏"能缓解**视觉重复**，但**不解决 iframe 数量**。折叠态仍是一个 iframe。**收敛策略（比如只贴最后 N 层）应作为阶段二的显式议题**，见 §四。

### ④ 反截断脚本会不会把正文里的 `<UpdateVariable>` 吃掉？

**结论：不会。它是静态可判的 —— 这个脚本从头到尾不碰正文文本。**

- 全文件 grep `UpdateVariable` / `json_patch` / `JSONPatch` → **0 命中**。它根本不认识这个标签。
- 它只做两件事（`src/scripts/20-反截断.js:5-7` 的自我说明，与实现一致）：
  1. **请求侧**：往生成请求里挂一个"把正文塞进函数参数"的函数（`:176-187` 解析请求体、`:187` 读 `body.tools`）；
  2. **响应侧**：把流式响应里那段函数参数的 `arguments` 抽出来，还原成普通的 `delta.content`（`:433` `const args = fn.arguments`）。
- 它**不删标签、不重写文本**，只是把同一段文字从"函数参数通道"搬回"文本通道"。

**但有一处必须真机验**（这不是"会不会吃标签"，而是"搬回来的是不是原文"）：
它自己实现了一个手写转义解码机（`:215` `unescapeOf`、`:262-280` 逐字符处理 `\uXXXX`），面向的是**流式分块**。如果 `\uXXXX` 正好被切在两个 SSE chunk 之间，拼接逻辑一旦有缝，还原出来的文本就会**多一个反斜杠或少一个字符**。
对 MVU 来说，`<UpdateVariable>` 里是 JSON Patch，**多一个反斜杠就是语法错** → 补丁解析失败。

→ 真机清单里专门有一条验这个（§五 B）。

### ⑥ 与酒馆宏变量的分工会不会混淆

**确认互不相干，但有三处会让人混。**

- 宏变量：`src/preset.base.json` 里 `setvar::` 出现 **86 次**、`getvar::` **63 次**。它是**提示词文本里的宏**，在发送前被酒馆替换成字面量 —— 生命周期只到"这一条请求"。
- MVU 的 `stat_data`：存在**楼层数据**里（`swipes_data` / `variables`），跨轮次持久。
- `stat_data` 在 `preset.base.json` 里出现 **3 次**，**全部来自 `:480` 那条 00 脚本的正文**（不是别的地方在用）。→ **目前两者在文件层面零重叠。**

**会混的三处：**
1. **都叫"变量"**。预设设置面板里已经有「🧩 设置变量」页（那是宏变量），再出一个 MVU 状态就是两套"变量"。
2. **写法都像模板**：宏是 `{{getvar::cot_budget}}`，MVU 的补丁是 `<UpdateVariable><JSONPatch>` —— 模型可能把两者混着写。
3. **决策落点不同**：宏变量的开关在预设条目里（随预设走），00 脚本的"用不用"决策在**聊天变量**里（随存档走，`00-mvu初始化测试.js:38`）。同一份预设、不同会话行为不同，容易被当成 bug 报。

→ 建议在文档与面板文案里**给两者起不同的名字**：宏变量叫「**设置项**」，MVU 的叫「**剧情状态**」。这一条我写进阶段一的验收里。

### 2.2 三条提示词条目草案

风格与现有预设一致：**每条一个开关、一条 `.kami-card`、内容尽量短**。三条都建议在「📖 创作要求」或新建一个「状态栏」组下。

**条目 A · 变量列表（把当前值喂给模型）**
> 占位符思路：用宏变量或 MVU 自己的 `display_data` 注入当前 `stat_data` 的 JSON。
> 内容要点：一句话说明"这是当前剧情状态"，然后给 JSON。**不要**把 schema 源码贴进来（讨论稿 §二.6 的判断是对的）。

**条目 B · 更新规则**
> 要点（按 yaml 里的注释归纳，逐条给模型）：
> 1. 只在**剧情真的发生变化**时才写补丁，没变就整块不输出；
> 2. 数值变动幅度上限（`affinity` 单次 ±10、`lust` 0–200）；
> 3. `_` 开头的字段**不许改**；
> 4. 新建实体必须先建 ID 再引用；`role` 为 `minor` 的龙套不许建实体；
> 5. 关系/声望的键必须是已存在的 ID；
> 6. `map_nodes` 三级结构（realm→area→spot）不许跳级。

**条目 C · 输出格式**
> 要点：正文结束后另起一段，输出
> `<UpdateVariable><JSONPatch>[ { "op": "replace", "path": "/status/time", "value": "…" } ]</JSONPatch></UpdateVariable>`；
> 没变化就**整块省略**（不要输出空数组）。

> **三条的开关**：建议合成一个组（"MVU 状态栏"），组内三条各自可开关 —— 与现有 `.kami-card` 的 `once`/`any` 模式一致。

## 三、我认为讨论稿判断错或低估的地方

1. **§六.5 与 §五 的"四套皮肤"是硬伤。** 实际 **18 套**。若按 4 套排期，工作量差 **4.5 倍**。（§一⑤）
2. **§六.3 把 iframe 说成"得先定显示范围"，但它其实已经发生了。** 现有两个前端就是"匹配到就贴"，**没有先例可抄**。"默认折叠"缓解视觉，**不减少 iframe 数量**。（§一③）
3. **§三 表格里"路线 C → 两份 schema 打架"的措辞低估了后果。** 从源码看它**不会报错**，而是**静默地把两套 prefault 叠进同一份 `stat_data`** —— 这种"不报错的污染"比崩溃难查得多。（§一①）
4. **§二.6 说"schema 管校验，提示词管模型"，这条是对的，但漏了一句**：schema 的 `prefault` 也**在替模型补字段**。所以提示词里"变量列表"给模型的 JSON，**最好是 prefault 之后的**，否则模型会以为自己该补一堆默认值。
5. **§六.2 只说"00 脚本必须真机跑通"，没说它现在是关的。** `meta.json` 里 `enabled=false`，所以"没验证过"的真实原因是**它根本没运行过**，而不是"跑了但没过"。这条差别影响排查方向。
6. **讨论稿没提"两个变量体系的重名问题"**（宏变量 vs `stat_data`）。§一⑥ 里那三处混淆会直接变成用户报障。

**一条我不同意 Lead 口径的地方（供权衡）**：
Lead 定"**默认主模型直接输出补丁**"。我同意默认值，但**建议把它做成阶段一就要有的开关，而不是阶段三**。
理由：主模型直写补丁会**占用输出长度**，而本项目已经有一整套"反截断"就是为了对抗输出被截断（`20-反截断.js`）。**补丁写在正文末尾，恰好是最容易被截掉的位置。** 一旦被截断，MVU 拿到的是一段残缺 JSON → 补丁整块失败，而且**用户看不出是截断导致的**。
→ 建议阶段一就把"额外模型解析"作为一个**可选项**留出口子（哪怕先不实现），并在文档里写明这个风险。
