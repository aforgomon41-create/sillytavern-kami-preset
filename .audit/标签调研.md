## A2 逐个说：未闭合会发生什么

### 1. `<out_body>` / `<introduction>` / `<appendix>` —— 几乎没有后果

`list.json:4` 的 findRegex（逐字抄）：

```
/(<(?:out_body|introduction|nyaruko_think|content|appendix|summary|options|char_setting)>)(?:[ \t]*\r?\n)+(?!```)/g
```

它**只匹配开标签**，后面跟一个或多个"空格/制表符 + 换行"（且后面不能是 ```）。闭合标签根本不参与，所以这三个标签未闭合**照常生效**（该收的换行还是收）。

`list.json:22` 的 `隐藏|XML结构间换行B` 同理，只认闭标签：
```
/(?<!```)(?:[ \t]*\r?\n)+(<\/(?:out_body|introduction|nyaruko_think|content|appendix|summary|options|char_setting)>)/g
```
开标签缺失时它不生效 —— 但换个角度说，它失效时"损失"只是标签前多几个空行。

**结论**：这三个标签对管线无实质影响，属于"规范层面该闭合，但坏了不炸"。

### 2. `<content>` 未闭合 —— 正文外壳整块不出现

`前端|正文 v0.1`（`list.json:57-70`）的 findRegex 逐字：

```
/[ \t]*<content>([\s\S]*?)<\/content>[ \t]*/g
```

拆开读：开头吞掉行内空格/制表符 → 匹配 `<content>` → 捕获组 1 用**惰性** `[\s\S]*?` 一路吃到**第一个** `</content>` → 结尾再吞空格/制表符。`g` 全局。

**`<\/content>` 是硬条件。** 没有闭合标签 → 整条正则零匹配 → `replaceString`（`src/preset.base.json:117`，展开后是 68 字节的 `<div data-kami-body-start></div>\n\n$1\n\n<div data-kami-body-end></div>`）一次都不执行 → 楼层里不会出现那一对 `data-kami-body-*` 标记。

接下来：

- `src/scripts/45-正文外壳.js:177-179`
  ```js
  var start = mes.querySelector('[' + MARK_START + ']');
  var end = mes.querySelector('[' + MARK_END + ']');
  if (!start || !end) { return 0; }
  ```
  直接放弃，`dress()` 返回 0 → 这一楼**没有外壳**：没有「正文」标题、没有字数、没有「渲染/原文」双视图、没有复制按钮。
- **正文文字本身照常显示**。原因是未闭合的 `<content>` 留在消息文本里，走的是 ST 自己的 markdown→HTML→净化流程。`ST:\scripts\chats.js:1937-1972` 的 `uponSanitizeElement` 钩子专门处理 `HTMLUnknownElement`（把里面的换行转成 `<br>`），说明这类未知标签确实会进净化器；按 DOMPurify 默认的 `KEEP_CONTENT`，标签本身被丢掉、里面的子节点被保留。所以表现是「**正文还在，外壳没了**」。
  ⚠️ 这一段是**读代码推出来的，没有真机实测**（本轮不许开浏览器）。实现时建议在预览台确认一次。
- 另一种坏法：两个 `<content>` 只配一个 `</content>`（`<content>A<content>B</content>`）。惰性匹配会从**第一个**开标签吃到唯一那个闭标签，捕获到 `A<content>B`，第二个 `<content>` 落进正文里 —— 表现是「外壳在了，但正文里混进一个裸露的 `<content>`」。

### 3. `<summary>` / `<char_setting>` 未闭合 —— 双重伤害（这一条最值钱）

两个消费者，坏了各坏一处。

**(a) 显示侧**：`隐藏|摘要/设定`（`list.json:194`）findRegex 逐字：

```
/<summary>[\s\S]*?<\/summary>|<char_setting>[\s\S]*?<\/char_setting>/gs
```

两个分支都要求闭合。未闭合 → 零匹配 → replaceString 是空串（`"replaceString": ""`，`list.json:203`）也就没机会执行 → **摘要/人设原文不再被隐藏，整段露在楼层里**。这是用户一眼就能看见的破相。

**(b) 发送侧**：`压缩|摘要/设定(默认最小深度20)`（`list.json:177-190`，id `0c74198f-1acc-43e3-8d88-d776d7242b89`）findRegex 逐字：

```
/^[\s\S]*?((?:<(?:summary|char_setting)>[\s\S]*?<\/(?:summary|char_setting)>\s*)+)[\s\S]*$/gs
```

拆开读：
- `^[\s\S]*?` 惰性吃掉开头任意内容；
- 捕获组 = **一个或多个连续的、完整的** `<summary>…</summary>` 或 `<char_setting>…</char_setting>`（`(?:…)+` 至少一组）；
- 尾部 `[\s\S]*$` 吃掉剩下的全部；
- 替换成 `$1` → 结果是**整条消息只剩那些摘要块**，正文被丢掉。这就是"滚动压缩"。

关键：**至少要有完整的闭合对**。未闭合时分组匹配不到 → **整条正则零匹配** → JS 的 `String.replace` 在没有匹配时原样返回字符串 → **这一楼的全文原封不动照发**。

后果：该楼层体积按全文计（不是摘要），token 消耗暴涨；而且由于这条正则 `minDepth: 20`（`list.json:181`），命中的都是 20 层以上的老楼层，一层一层堆积，压缩机制等于**静默失效**。

`<char_setting>` 走的是同一个正则的两个分支，表现完全一样。

### 4. `<options>` 未闭合 —— 选项卡片消失，JSON 原文露出来

`前端|行动选项 v0.1`（`list.json:91-105`）findRegex 逐字：

```
/<options>([\s\S]*?)<\/options>/gs
```

`g` + `s`，惰性捕获。未闭合 → 零匹配 → 不会产出 `@@FRONTEND:options@@` 占位 → 楼层里**不出现行动选项卡片**，那段 JSON 变成一坨纯文本显示在消息里。

同一个标签还有第二条消费者：`隐藏+屏蔽|行动选项数据`（`list.json:160-174`），findRegex 一模一样，但 `markdownOnly: true` **且** `promptOnly: true`，`minDepth: 2`，替换成空串 —— 作用是「老楼层里把选项数据藏起来、发提示词时也剔掉」。未闭合 → 同样零匹配 → 老楼层的 JSON 也照样露着，发出去的历史里也带着。

顺带一个边界情况：`<options>A<options>B</options>` 会因为惰性匹配把 `A<options>B` 一起捕获，`JSON.parse` 失败 → `frontend-options.html:120-145` 的 `parseList()` 返回 null → 落到 `mount.demo = true`，渲染的是 `SAMPLE`（`frontend-options.html:296-299`）示例卡片 + 提示「未检测到选项 JSON，以下为示例内容」。**这是"卡片出现了但全是假数据"**，跟"完全没卡片"是两种现象。

### 5. `<nyaruko_think>` 未闭合 —— 思维链从"折叠组件"退回"裸文本"

两条消费者：

- `屏蔽|显式思维链`（`list.json:40-54`）：`<nyaruko_think>([\s\S]*?)<\/nyaruko_think>`（**没有 g 标志，只替换第一处**），`promptOnly: true`，替换成空串 → 发送前把思维链剔掉。未闭合 → 零匹配 → **思维链原文照发给模型**，白烧 token，还可能干扰模型。
- `前端|显式思维链 v0.1`（`list.json:74-88`）：`/\s*<nyaruko_think>([\s\S]*?)<\/nyaruko_think>\s*/gs`，`markdownOnly: true`，替换成 `@@FRONTEND:think@@` → 渲染成可折叠的「思维链」组件。未闭合 → 零匹配 → 楼层里**直接显示思维链原文**（丑、占屏，但能看）。

### 6. `<medium>` / `<medium_content>` 未闭合 —— HTML 源码露出来（而且有误伤陷阱）

- `屏蔽|HTML美化代码`（`list.json:143-157`）：`/<medium>[\s\S]*?<\/medium>/gs`，`promptOnly: true` → 发送前剔掉 HTML 卡片代码。未闭合 → 代码留在历史里。
- `隐藏|HTML美化留档文字`（`list.json:126-140`）：`/<medium_content>[\s\S]*?<\/medium_content>/gs`，`markdownOnly: true` → 显示时藏掉纯文本副本。未闭合 → 纯文本副本露在楼层里。更糟的是 `<medium>` 本身没藏掉，那一大坨 HTML 会以源码形式显示。

⚠️ **误伤陷阱（实现时务必注意）**：预设条目 `🎥 HTML美化`（`src/preset.base.json:3102`）明确允许 AI 在 `<medium>` 里用 HTML 的 `<details><summary>`：

> 可适当利用 `<details><summary>` 实现简单的折叠/点击展开交互。

所以**在 `<medium>…</medium>` 范围内，`<summary>` 是合法的 HTML 标签，绝对不能当"未闭合的摘要标签"去补 `</summary>`**。同理 `<options>`、`<content>` 这些词也可能作为属性值或普通文本出现。任何自动补全必须先在 `<medium>` / 代码围栏外做排除。

### 7. `<image>` / `<image_Tag>` / `<MakeImage>` 未闭合

`屏蔽|图片与<god>(仅保留一楼)`（`list.json:108-123`）findRegex 逐字：

未闭合 → 该分支不匹配 → 老楼层的 `<image>` 内容（往往是一两百个 tag 的长块）**留在发送内容里**，token 直接翻倍。

### 8. `<god>` 未闭合

未闭合 → 一楼之后的历史里那段 `<god>` 指令不会被剔除，会被反复重发给模型（浪费，且可能造成指令权重的意外累积）。

### 9. `<think>` 未闭合 —— 酒馆本体的推理解析静默失败

`ST:\scripts\reasoning.js:1421-1450`：

```js
export function parseReasoningFromString(str, { strict = true } = {}, template = null) {
    template = template ?? power_user.reasoning;
    // Both prefix and suffix must be defined
    if (!template.prefix || !template.suffix) {
        return null;
    }
    try {
        const regex = new RegExp(`${(strict ? '^\\s*?' : '')}${escapeRegex(template.prefix)}(.*?)${escapeRegex(template.suffix)}`, 's');
        let didReplace = false;
        let reasoning = '';
        let content = String(str).replace(regex, (_match, captureGroup) => {
            didReplace = true;
            reasoning = captureGroup;
            return '';
        });
        if (didReplace) {
            reasoning = trimSpaces(reasoning);
            content = trimSpaces(content);
        }
        return { reasoning, content };
    } catch (error) { ... }
}
```

前缀和后缀都必须在。未闭合 → 不匹配 → `didReplace` 保持 false → 返回 `{reasoning: '', content: 原文}` → **推理块没被切出来，整段连同 `<think>` 一起留在正文里显示**。

注意两个前提，别把这条当成必然：
- `ST:\scripts\power-user.js:276` 里 `auto_parse: false` 是默认值，得用户开了自动解析才会走这条路；
- DeepSeek / GLM 的推理通常是走接口的 `reasoning_content` 字段，不经文本标签。

### 10. `<n>` 未闭合 —— 只影响"发出去的那一份"，不影响显示

`src/scripts/35-角色名包裹.js:33`：

```js
var MARK_RE = /<n>([^<]*)<\/n>/g;
```

`[^<]*` 意味着中间不能有 `<`。未闭合 → 零匹配 → 这个名字不会被换成当前档位的包裹符（反引号 / 双下划线 / 什么都不加），`<n>` 字面量**原样发给模型**。

好消息：**显示侧没有任何正则认 `<n>`**，而它又是标准 XML 形状的未知标签，会走 ST 的净化流程被丢掉（同 A2-2 的推断）。所以画面上 `<n>奈亚子</n>` 和未闭合的 `<n>奈亚子` 都显示成「奈亚子」——**用户看不出差别**。这是一个纯 prompt 侧的隐性问题。

## B2 `MESSAGE_RECEIVED` 到底在渲染前还是渲染后？

**答案：看路径，两条路径不一样。** 这是本节最重要的发现。

### 路径一：非流式（一发一收）—— **渲染之前**

`ST:\script.js:6720-6724`（在 `saveReply` 里，非 swipe / 非 append 的常规分支）：

```js

上下文完整读一遍：`chat.push(newMessage)` 在 `:6685`，`newMessage.mes = getMessage` 在 `:6698` —— **消息已经进数组了**；`:6722` 广播 `MESSAGE_RECEIVED`；`:6723` 才 `addOneMessage` 建 DOM。所以：

swipe 分支同样顺序（`ST:\script.js:6632-6634`）、`append`/`continue` 分支同样（`:6657-6659`）、`appendFinal` 分支同样（`:6679-6681`）。

### 路径二：流式 —— **渲染之后**

- `ST:\script.js:3562-3582` `onStartStreaming` → `:3574` `await saveReply({ type, getMessage: text, fromStreaming: true })` → 因为 `fromStreaming: true`，`:6722` 那句 `!fromStreaming && …emit` **被跳过**，但 `:6723` 的 `addOneMessage(chat[chat_id])` **照跑** → DOM 当场就建好了。

1. **🔴 `<summary>` 会误伤 `<medium>` 里的 HTML 卡片。** `_tags-pure.js:42` 把 `summary` 登记为要配对的标签，但 `codeRanges()`（`:62-70`）只跳过 ``` / ~~~ 围栏，**没有把 `<medium>…</medium>` 区间排除**。而预设明确允许 AI 在卡片里用 HTML 的 `<details><summary>`（`src/preset.base.json:3102`：「可适当利用 `<details><summary>` 实现简单的折叠/点击展开交互」）。AI 若把 `<details><summary>标题</details>` 写成省略闭合的形式（HTML 里合法，浏览器会自动收），补全逻辑会把 `</summary>` 补到 `<medium>` **外面**，把卡片 HTML 改坏。
   `test/harness/tags-pure.mjs` 里也**没有**这一条的用例（只有 `:53-54` 的嵌套补全用例）。
   **建议**：`tokenize` 的 skip 区间里加上一层「`<medium>` 开标签到 `</medium>` 闭标签」的区间（找不到闭标签就一路到消息末尾）。

2. **🟡 三个标签白登记了。** `_tags-pure.js:44-46` 把 `UpdateVariable` / `JSONPatch` / `Analysis` 登记成尾巴块，注释写「MVU 变量框架」。但本预设 181 条条目里这三个标签出现 **0 次**（A1 扫描结果），本机也**没装** MVU / MagVarUpdate 扩展（`ST:\scripts\extensions\third-party\` 只有 5 个扩展）。它们永远不会出现在 AI 回复里 —— 留着无害（纯死条目），但如果面板要显示"管哪些标签"，会把用户看懵。

3. **🟡 `god` 是用户侧的标签，不是 AI 输出。** `_tags-pure.js:47` 把 `god` 登记为尾巴块。`<god>` 的语义在 `src/preset.base.json:1750`（`📌 输入解析`）：「ROOT 最高权限指令」——它出现在**用户输入**里。AI 回复里正常不会出现（除非模型复述用户输入）。同理 `<image>` 只在 AI 回复里、`<god>` 只在用户输入里，两者混在一张表里会让"该管哪些标签"的边界含糊。

4. **🟡 注释里的正则名对不上。** `_tags-pure.js:14-15` 写「正则『排版|HTML美化 / HTML抽取』」「正则『图片|图片\<god\>』」，但 `src/regex/list.json` 里的真名是 `隐藏|HTML美化留档文字`（`:126`）/ `屏蔽|HTML美化代码`（`:143`）和 `屏蔽|图片与<god>(仅保留一楼)`（`:108`）。不影响功能，但以后按名字找正则会扑空。

# 给实现者的结论

**该管哪些标签** —— 以 `src/preset.base.json:1508`（`🧩 标签格式`）那份官方名单为准，去掉不在 AI 回复里的两个（`<god>` 是用户输入、`<image>` 交给生图插件），剩下真正需要补/清的成对标签是：`<out_body>` `<introduction>` `<content>` `<appendix>` `<summary>` `<char_setting>` `<options>` `<nyaruko_think>` `<think>` `<n>` `<image>` `<image_Tag>` `<MakeImage>` `<medium>` `<medium_content>`。按"坏了有多疼"排序，**必管的是 `<content>` `<summary>` `<char_setting>` `<options>` `<nyaruko_think>`**（这五个坏了分别导致：正文外壳消失、摘要原文外露 + 压缩静默失效、选项卡片消失 + JSON 外露、思维链裸奔），`<medium>*` 和 `<image*>` 次之，`<out_body>` `<introduction>` `<appendix>` 只是规范要求、坏了不炸。

**在哪个时机改** —— 订阅 `tavern_events.MESSAGE_RECEIVED`（`TH:\function\event.ts:188`）。它同时覆盖两条路径：非流式时它发在 `addOneMessage` **之前**（`ST:\script.js:6722-6723`），改完直接被渲染；流式时它发在**渲染之后**（`ST:\script.js:3740`），靠下面的重画补上。`emit` 会 `await` 我们的 async 监听器（`ST:\lib\eventemitter.js:130-152` + `TH:\function\event.ts:56-62`），所以"改完再渲染"是有保证的，不会闪。

**怎么让界面重画** —— 用 `await setChatMessages([{ message_id, message: 新文本 }], { refresh: 'affected' })`（`TH:\function\chat_message.ts:212-215`，默认值就是 `'affected'`；项目先例 `src/scripts/60-压缩.js:1449`）。它会走 `refreshOneMessage`（`TH:\function\displayed_message.ts:145-161`）：先把 `.mes_text` 用 `messageFormatting` 重写 —— 于是 `前端|正文` / `前端|显式思维链` / `前端|行动选项` 三条正则重跑、载荷重新生成 —— 再补发一次 `CHARACTER_MESSAGE_RENDERED`，而酒馆助手的 iframe 运行时正挂在这个事件上（`TH:\store\iframe_runtimes\message.ts:120-136`），会把消息里的 `pre` 重新扫一遍挂上新 iframe。**不要**用 `refresh: 'all'`（会 `reloadCurrentChat()` 整份重载），**不要**指望 `updateMessageBlock`（`ST:\script.js:1974`，虽然 `getContext()` 里有，但它不重建楼层 DOM、且楼层不存在时静默空转），**更不要**把 `MESSAGE_UPDATED` 当成重画触发器（`ST:\script.js:8277` / `:8371`，它只是编辑流程结束的通知）。

**两条硬约束别忘了**：① 自动补全必须先在 `<medium>…</medium>` 和 ``` 围栏**之外**做判断 —— 预设明确允许 AI 在 HTML 卡片里用 `<details><summary>`（`src/preset.base.json:3102`），无脑补 `</summary>` 会把正常卡片改坏；② 改动要落进存档（`setChatMessages` 会顺手 `saveChatConditionalDebounced()`，`TH:\function\chat_message.ts:189`），所以建议同时留一份原文快照，给用户一个"撤销/还原"的口子 —— 这一条是设计建议，不是调研结论。
