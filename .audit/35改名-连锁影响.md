**要动的文件：8 个，共 21 处。其中 1 处是「不改就构建直接失败」的硬拦。**

8. src/scripts/40-预设设置.js —— 1 处注释（第 1551 行的文件路径）。

**再加文档 2 处（不影响构建，只影响后来人）**：docs/皮肤契约.md 第 366 行（文件路径）、第 363 行（API 名，视第 2 节的选择）。docs/交接.md 的三处旧名是**编年史记录，建议不改**（理由见第 5 节）。

**有没有破坏性影响：没有。** 三条硬结论：

- **产物里的脚本 id 不会变。** build/build.mjs:197 是 id: m.id —— 原样抄 meta.json 的 id 字段，与文件名、脚本显示名都无关。用户那边的**脚本开关状态**与**脚本内设置**都按 id 对齐，不会重置（证据：src/scripts/_preset-merge.js:425-438 全程按 id 匹配；dist/build-manifest.json:28467-28471 连续多次构建 id 恒为 c3a7f2e1-…）。
- **用户已有的角色名档位设置不会丢。** 档位存在酒馆**全局变量** kami_name_wrap（外加派生键 kami_name_wrap_rule）里，跟脚本名、脚本变量一点关系都没有。**只要不改这两个键名，用户设置原样保留。**
- **唯一真正的硬拦是守卫 build/verify-name-wrap.mjs:93。** 它按脚本显示名找脚本，不同步改就是构建中止。

**新功能并进来的两条提醒（不是改名问题，是设计问题）**：① 35 号是**没有面板、没有按钮、没有脚本变量、没有 DOM** 的纯后台脚本，新功能需要一个让用户填指令文本的界面 —— 把它塞进 35 号意味着要在 35 号里新建一整套面板，代价远大于在 30/40 号挂一张卡（建议见第 6 节）。② 35 号现有的注销写法有个既有缺陷（第 6 节第 2 点），加退订时顺手修掉。

### 3. 档位 / 设置存在哪：不是脚本变量，是酒馆全局变量

**关键事实：35 号没有任何脚本变量**，证据是 src/scripts/meta.json:143 的 data 字段是空对象 {}（脚本变量表是空的）。

**档位真正的存储位置 —— 酒馆「全局变量」两个键：kami_name_wrap（档位）与 kami_name_wrap_rule（派生措辞）**

**src/scripts/35-角色名包裹.js:31-32（键名常量，唯一真值来源）**
~~~js
  var VAR_MODE = 'kami_name_wrap';        /* 档位（唯一真值来源） */
  var VAR_RULE = 'kami_name_wrap_rule';   /* 输出规范那句的措辞（由档位派生） */
~~~

**读写在 35 号内部的哪几行**
- 76-89 readGlobal(name)：优先走 c.variables.global.get()，兜底读 c.extensionSettings.variables.global
- 91-110 writeGlobal(name, value)：优先 variables.global.set()，兜底直写 extensionSettings.variables.global，随后 saveSettingsDebounced()
- 113-122 syncVars(force)：缺了 / 认不出 / 措辞对不上都**当场修正**（幂等自愈）
- 117-118：写两个变量
- 196-197 api.set(id)：一次写两个变量（VAR_MODE / VAR_RULE）
- 217-218 api.status()：回读两个变量

**外部依赖这两个键的地方**
- src/preset.base.json 的「📌 输出规范」第 4 条用 {{getglobalvar::kami_name_wrap_rule}} —— 由 build/verify-name-wrap.mjs:87 守着：
~~~js

~~~
- src/scripts/30-皮肤管理.js:1078-1079（注释）：档位不在皮肤 state 里，而在酒馆**全局变量** kami_name_wrap 里（跨聊天、跨角色跟账号走），读写都走 35 号脚本的 API。
- docs/皮肤契约.md:363：档位存在酒馆**全局变量** kami_name_wrap 里
- test/harness/preview.html:371-373（注释）与 886-890（探针逐字断言 g.kami_name_wrap === 'none' 且 g.kami_name_wrap_rule === '一律直接书写、不加包裹'）
- build/verify-name-wrap.mjs:102：ok(wc.indexOf('kami_name_wrap') >= 0 && wc.indexOf('kami_name_wrap_rule') >= 0, '④ 档位与措辞两个全局变量的名字对得上预设里那处引用');

**裁定：改名后 kami_name_wrap / kami_name_wrap_rule 两个键名必须原样保留 —— 保留 = 用户已有设置不丢。**
键名与脚本名没有任何字面关联（kami_ 前缀是本项目的命名习惯，不是脚本 id），改脚本名**不需要**动它们；反过来，一旦动了键名，用户档位当场回落到默认值 bt，而且**输出规范那句会读不到值**（{{getglobalvar}} 展开成空），属于真丢数据。

**新功能（常驻附加指令）的指令文本建议存哪**
调研报告 .audit/常驻附加指令-调研.md §5.2（第 377-418 行）给的现成模板是 40 号的脚本变量键 kami-preset（40-预设设置.js:63 var VARS_KEY = 'kami-preset';）。
⚠️ 若按用户的决定并进 35 号，则 35 号需要**新开一个脚本变量键**（meta.json:143 的 data 要从空对象补上默认值），并且注意调研报告第 418 行的警告原文：
> ⚠️ 注意这是**整块覆写**：新增一个字段必须同时改 readVars() 和 saveVars() 的这一个对象字面量，漏一处就会被下一次保存抹掉。
另一条路（与 35 号现有风格一致）是继续用**全局变量**，照 35 号 readGlobal/writeGlobal（76-110 行）那对函数写。
**两条路的取舍**：全局变量跟账号走、跨预设；脚本变量跟预设走、可被三方合并的「用户的 data 一律保留」规则（_preset-merge.js:438）保护。用户手打的指令文本属于「用户数据」，**建议走脚本变量**（并且注销时不要删，见调研 §5.3 第 425 行）。
