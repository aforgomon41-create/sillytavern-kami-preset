## T2. `build/verify-*.mjs` 的通用写法

### 2.1 三条铁律

1. **读的是「产物」而不是源码**。七个守卫全部先 `JSON.parse(fs.readFileSync(产物))`，再从
   `preset.prompts` 与 `preset.extensions.tavern_helper.scripts[].content` 里找证据。
   也就是：**改完 `src/` 必须构建过，守卫才有意义**（`build/verify-inherit.mjs:25-30`）。
2. **没有共享工具函数** —— 每个文件各抄一份 `ok()`，只有 3 行，宁可重复也不抽公共库
   （`verify-name-wrap.mjs:39-42`、`verify-inherit.mjs:39-42`、`verify-model-switch.mjs:26-29` 三份逐字雷同）。
3. **退出码约定统一**：`bad` 计数 → 末尾 `process.exit(bad ? 1 : 0)`；
   **用法错误/找不到产物 = 退出码 2**（`verify-inherit.mjs:23-24`、`verify-model-switch.mjs:20-21`）。

### 4.5 两块新逻辑具体该测什么（用例清单）

**A. 摘要响应解析器**（输入 = `generateRaw` 返回的字符串；输出 = 结构化对象 + 是否失败）

必测的 8 类输入（每条一个断言，全部是纯字符串进、对象出）：

1. 干净 JSON：`{"timeline":"…","summary":"…","changes":["…"]}` → 解析成功、字段齐全。
2. 带 ``` 围栏的 JSON（`60-压缩.js:1192` 现在只剥**首尾**围栏：`text.replace(/^```[a-zA-Z]*\s*/, '').replace(/```\s*$/, '')`）。
3. JSON 前后带客套话（「好的，以下是总结：」+ JSON + 「希望有帮助」）→ 抓出中间那段。
4. 模型输出**含未转义换行的 JSON 字符串**（真实高频）→ 容错策略要明确：修好还是判失败。
5. 截断的 JSON（末尾 `}` 缺失）→ **必须判失败**，且错误信息要说人话（否则会把半截提要写进世界书）。
6. 模型返回错误文本（`401 Unauthorized` / `context length exceeded` / `quota`）→ 识别为「接口错误」而不是「格式错误」，
   因为两者的补救动作完全不同（一个让用户去改配置，一个让用户重试）。
7. 空字符串 / 只有空白 → `COPY.toasts.emptyReply`（`60-压缩.js:330`）那条路径。
8. 模型把提要吐成 Markdown（`时间线：…` 纯文本，不是 JSON）→ 降级接受还是判失败，要**写死在用例里**。

**B. 世界书对账器**（输入 = 账本 JSON 对象 + 真实条目名列表；输出 = 三份清单）

1. 账本与条目完全一致 → 三份清单全空（幂等：跑两次结果相同）。
2. 账本里有块、条目**缺失**（用户手删了世界书条目）→ 进「要补写的条目」，正文用账本里的 `text` 重建（走 `blockContent`，`60-压缩.js:760`）。
3. 条目在、账本里**没有**（手改坏了 JSON 账本）→ 现在靠 `60-压缩.js:733-749` 的「按条目名收养」兜住，对账器要把这段逻辑的**判定结果**也算出来。
4. 条目**正文被用户手改**（头和账本 `text` 不一致）→ 进「被用户手改后应采用的新正文」，且**以用户改的为准**，账本跟着更新。
5. 账本前沿 `covered` **比条目实际覆盖的范围更靠后**（用户把后面的块删了）→ 进「要退回的压缩前沿」，退回值 = `max(条目.to)`。
6. 条目名对但**楼层范围对不上**（用户手改了条目名里的数字）→ 必须判冲突而不是静默采信。
7. 条目存在但 `content` 不是 `【剧情提要｜楼层 X-Y】` 头（`60-压缩.js:766-770` 的 `stripBlockHeader`）→ 明确算「头被改坏」。
8. 空账本 + 一堆条目 / 有账本 + 零条目 → 两个极端都要有断言（对应 `60-压缩.js:734` 的 `if (!st.blocks.length)` 分支）。

> 这两块的用例都不需要 `getChatMessages`、不需要 `loadWorldInfo`、不需要 `eventOn` ——
> 所以它们的测试**天然适合 route 乙 / 丙**，不必去搭 `update-flow.mjs` 那种整套假环境。
>
> 📌 **顺带一条会影响解析器契约的事实**（另一份同目录审计已有取证，本报告不重复验证）：
> 酒馆助手的 `generateRaw` **支持 `json_schema`**（`ordered_prompts` 那条路径上，
> 助手会监听 `chat_completion_settings_ready` 把 schema 注进请求体）——
> 见 `.audit/api-facts-压缩JSON.md:38-60`。若下决心走结构化输出，用例 4/5/8 的容错压力会大幅下降；

所以建议**除纯逻辑单测之外**，再加一条 10 行左右的守卫：从产物里取 60 号的 `content`，
断言「两块纯逻辑的函数名/关键串都在里面」。否则「占位符写错了」这类事故，
单测全绿、`node build/build.mjs` 也全绿，只有真机打开面板才发现（`60-压缩.js:2417` 的 `bindPanelGestures` 就是这个形态的真实先例）。
