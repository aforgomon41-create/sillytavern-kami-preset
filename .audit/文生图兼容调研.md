## 一、一句话结论

我们的「正文前端」把 `<content>…</content>` 整段换成了 iframe 载荷，`image###…###` 这段文字**只剩在 iframe 内部**；而本机在用的那支文生图插件，两种扫描方式**都只在父文档的 DOM 里找这段文字**——所以智能模式**一个按钮都不插**，深度模式**插不出按钮、还可能把 iframe 里那段文字换成一串占位符**。

最省事、且不用改插件的接法是：**由我们自己（父窗口侧的一条酒馆助手脚本）读 `chat[mesid].mes` 拿原文，用插件现成的 `RBQ.api.createPromptCard()` 造卡片，插在 iframe 外面。**

  ```js
  if (messageDiv.length === 0) return;

  ```
  → **同样读不到 iframe 里的文字。**
- 注入（`src/index.js:191-216`）：`container.after(buttonHtml)` —— 挂在 `.mes_text` **后面**，不替换。
- 重扫：`MESSAGE_RECEIVED` + `CHAT_LOADED`（`src/index.js:59-66`），配 `setTimeout(...,100)` 等 DOM 渲染。

### 3.5 那条正则 `屏蔽|图片与<god>(仅保留一楼)` 跟文生图**不是同一条链路**

原文（`src\regex\list.json:106-123`；产物 `dist\kami-v0.91-42-20260926.json` 里同一 id `be9d54f7-…` 逐字一致）：

```json
{
  "findRegex": "/<image_Tag>[\\s\\S]*?<\\/image_Tag>|<image>[\\s\\S]*?<\\/image>|<MakeImage>[\\s\\S]*?<\\/MakeImage>|<god>[\\s\\S]*?<\\/god>/gm",
  "markdownOnly": false,
  "maxDepth": null,
  "minDepth": 1,
  "placement": [1, 2],
  "promptOnly": true,
  "replaceString": "",
  "runOnEdit": false,
  "scriptName": "屏蔽|图片与<god>(仅保留一楼)"

```

**它是「只改发给 AI 的上下文」的一条清洗正则**：`promptOnly: true` + `markdownOnly: false` → 只在拼提示词时生效，**不碰显示、不产生任何按钮**。

`minDepth: 1` 的确切含义（酒馆本体的代码）：

- 拼提示词时算深度：`D:\SillyTavern\SillyTavern\public\script.js:3619`
  ```js
  let options = { isPrompt: true, depth: (coreChat.length - index - (isContinue ? 2 : 1)) };
  ```
  → **深度从最新一条往回数，最新一条是 0**。
- 判断在 `public\scripts\extensions\regex\engine.js:106-110`：
  ```js
  if (typeof depth === 'number') {
      if (!isNaN(script.minDepth) && script.minDepth !== null && script.minDepth >= -1 && depth < script.minDepth) { …return; }
  ```
  → `depth < 1` 才跳过，所以 **depth 0（最新一楼）不屏蔽，depth ≥ 1 的历史楼层全屏蔽**。「仅保留一楼」这个命名跟行为是对得上的。

所以答案是：**它跟文生图插件无关，也不是「图片变按钮」的那条路。** 它只负责「别把一堆插图标签灌进上下文烧 token」。

## 四、我们的正文前端为什么会挡住它

### 4.0 先把链条摆清楚（这一步是理解全部现象的前提）

1. `src\regex\list.json:55-71` 的 `前端|正文 v0.1`：
   ```json
   { "findRegex": "/[ \\t]*<content>([\\s\\S]*?)<\\/content>[ \\t]*/g",
     "markdownOnly": true, "maxDepth": 1, "minDepth": null,
     "placement": [2], "replaceString": "@@FRONTEND:body@@" }
   ```
   构建期把 `@@FRONTEND:body@@` 换成一整份 HTML 文档（外面套 ` ``` ` 代码围栏）。
2. 酒馆助手（JS-Slash-Runner，**本机没装，但它渲染前端这件事工作区文档里已验证过**）把代码围栏里的 HTML 渲染成 `div.TH-render > iframe[srcdoc]`（见 `docs\皮肤契约.md:986`「酒馆助手用 `<iframe srcdoc>` 渲染前端，**没有 `sandbox` 属性**」，以及 `docs\皮肤契约.md:414` 的让位清单里点名了 `div.TH-render`）。
3. 正文原文被塞进 iframe 文档里的 `<script type="text/plain" data-kami-payload>@@PAYLOAD@@</script>`（`src\regex\frontend-body.html:21`），`@@PAYLOAD@@` 就是捕获组 `$1`。
4. → **`image###…###` 这段文字从这一刻起只存在于 iframe 文档里，父文档 `.mes_text` 里一个字都没有。**
5. 还有个容易被忽略的边界：`maxDepth: 1`。按上面 §3.5 那套深度语义，**只有最新两楼（depth 0 和 1）才做替换**；`depth ≥ 2` 的老楼层，`<content>…</content>` 原样留在 `.mes_text` 里（`content` 在酒馆 DOMPurify 的默认白名单里，会作为真元素活到 DOM —— 工作区 `docs\交接.md:923` 记过这条）。**也就是说：老楼层的插图标签其实还在 DOM 里，插件在那些楼上是能工作的；坏掉的只有最新两楼。**

### 4.1 模式 A（深度扫描 deep）为什么会失效

它的判断分两步，**第一步能过、第二步打在错的地方**：

**第一步（在聊天数组上，能过）**：`nr()`（`@247,047`）先 `const o=gt(s?.mes)` —— 从 `chat[mesid].mes` 里把 `image###…###` 抽出来。这一步读的是**原始消息文本**，`<content>` 也好、iframe 也好，都不影响它。所以插件**知道这一楼有插图标签**。

**第二步（在 DOM 上，打偏了）**：`$n()`（`@219,536`）里的判断是
```js
let n=r.innerHTML;                       // r = .mes_block
if(n.includes(t.raw)) return n=n.split(t.raw).join(c), void(i=!0);
```
- 对**最新两楼**：`image###…###` 已经被烤进 `iframe[srcdoc]` 的**属性值**里。`innerHTML` 序列化时属性值是会被一起吐出来的，所以 `n.includes(t.raw)` **很可能仍然为真**（`image###` / `###` 里没有会被 HTML 转义的字符）。但接下来的替换是 `n.split(t.raw).join(占位符)` —— 它替换的是**属性值内部的那段文字**，最后 `r.innerHTML = n` 写回去。结果是：**按钮不会出现**（占位符 `<span>` 落在属性值里，不会被解析成元素），而且**正文前端 iframe 里那段插图标签被换成了 `__ST_BTN_PH_0_…__` 一串乱码**。
- 对**更老的楼层**（depth ≥ 2，正则没生效）：`<content>` 原样在 DOM 里，`image###…###` 就在 `.mes_text` 的文本里，deep 能正常命中并插按钮。

> ⚠️ 上面「很可能仍然为真」这一段是**推断**，不是实测（本机没装插件、也没装酒馆助手，我没法真机复现）。推理链条是：`iframe.srcdoc` 是属性 → `innerHTML` 会把属性值序列化出来 → `srcdoc` 里是正文原文，`image###…###` 不含 HTML 特殊字符。**这条必须真机验一次**（验证方法见 §六）。

### 4.2 模式 B（智能兼容 smart / 经典 legacy，以及 Smart Draw 的 DOM 插入）为什么会失效或位置不对

这一条**是确定的**，机制上没有含糊的地方：

1. 宿主是 `.mes_block`（§3.1 ②，我用 cheerio 实测过选择器命中谁）。
2. 智能/经典模式用 `document.createTreeWalker(r, NodeFilter.SHOW_TEXT|…)` 遍历宿主的文本节点，把文字拼成一个字符串再跑标签正则。
3. **`TreeWalker` 不会跨文档边界** —— `iframe` 内部是另一个 `document`，里面的文本节点根本不在遍历范围里。
4. 于是拼出来的字符串里**没有** `image###…###`，`p` 是空数组，代码走这一行直接返回：
   ```js
   if(!p.length) return void(r.dataset.stSceneSignature=s);
   ```
   → **一个按钮都不插**。而且它**顺手把这一楼标记成「已处理」**（写 `stSceneSignature`），后续扫描默认跳过；要等 `MutationObserver` 发现正文变动才会清掉这个签名重扫。
5. **Smart Draw 那一侧也一样，但表现是「位置不对」而不是「什么都没有」**：
   - 它的识别读 `message.mes`（`smart-draw-trigger.js:5715`），**能认出标记**，所以卡片一定会被造出来；
   - 但 `insertAtMarker()` 在 `visibleTextNodes()`（第 10496 行，同一个 document）里找不到标记文本 → `insertBySentenceMap()` 的两次文本匹配也必然落空 → 最后走 `mountFallbackFragment()`（第 11000–11004 行）**`container.append()`**；
   - 容器是 `.mes_block`，所以卡片被**追加到整块消息的末尾**：按钮在、能点，但它永远在正文前端 iframe **下面**，跟正文没有任何位置关系。`cardPosition:'top'` 时更糟，会跟 `.ch_name` / `.mes_buttons` 抢位置。
   - 同理，`insertAfterSentence()`（第 10611 行）这种「插在第 N 句之后」的锚点，也会因为句子里数不到 iframe 内的文字而整体偏移。

## 五、可行的接法对比

前提先说明：**卡片本身不可能同时「活在 iframe 里面」又「吃到父文档的事件委托」。** RBQ 的点击是委托在**父文档 `document.body`** 上的（`@343,155`），iframe 里的点击**不会冒泡到父文档**。所以下面每个方案都要在这一条上做取舍。

| # | 做法 | 改哪里 | 代价 | 风险 | 推荐度 |
|---|---|---|---|---|---|
| 1 | **父窗口侧「文本影子 + 借用插件 API」**：我们自己在每个楼层的 `.mes_text` 里，把 `<content>` 里的 `image###…###` 用 `RBQ.api.createPromptCard({messageId,prompt,raw,id})` 造成插件原生卡片，插在 `.TH-render` 之后 | 新增一条我们自己的酒馆助手脚本（不碰插件、不碰 iframe、不碰 `src/regex/*.html`） | 小。数据源直接读 `chat[mesid].mes`，不需要从前端里往外掏 | ① 会和插件自己在老楼层插的卡**重复**，必须去重（按容器里已有的 `.st-scene-trigger-inline-wrap` 或 `data-prompt-id`）；② `RBQ` 不在时要降级（自己画按钮）；③ 插件升级改 API 名会断 | ★★★★★ |
| 2 | **iframe 内部自绘按钮 + 直接调插件函数**：iframe 里解析 payload，自己画按钮，点击时 `window.parent.RBQ.api.generateImage(prompt,'kami-body',{messageId},cb)`，拿结果自己塞回 iframe | `src/regex/frontend-body.html` | 中。loading / 失败 / 灯箱 / 历史全要自己写 | ① 绕开了插件的图库、缓存、历史、灯箱联动；② 插件不在时整块功能空转；③ iframe 里取 `mesid` 要绕 `window.frameElement.closest('.mes[mesid]')`（同源，可行） | ★★★ |

| 4 | **让标签不进 `<content>`**：改预设提示词，让 AI 把 `<image>…</image>` 块写到 `<content>` **外面**（或另起一个正文前端不匹配的标签） | `src/preset.base.json` 的 🎨 文生图条目 / `src/scripts/*` 里的标签设置 | 小（只改提示词） | ① 破坏「插图紧跟相关正文」的排版意图；② 裸标签会以文本形式露在消息里（`屏蔽|图片与<god>` 只清上下文不清显示）；③ 落到 deep 模式时它会**重写整个 `.mes_block` 的 innerHTML**，把 `.ch_name` / `.mes_buttons` / 思考块一起重建，风险很大 | ★★ |

## 六、还没搞清的问题（诚实清单）

1. **真机上「深度扫描」到底命不命中。** §4.1 的结论是推断的：`iframe[srcdoc]` 里的正文原文会不会在 `innerHTML` 里原样出现、`t.raw` 的换行会不会被 `srcdoc` 属性序列化改掉，我没法在本机实测（没装插件、没装酒馆助手）。**验证方法**：真机上开 deep 模式，控制台看 `[RBQ-dbg] #N force=… prompts=… mesLen=…` 里 `prompts` 是不是 > 0（若是 0，说明第一步就断了，跟我推的不一样），再看那一楼的 `.mes_block` 里有没有 `st-scene-trigger-inline-wrap`；最后翻 iframe 的 `srcdoc` 里那段文字有没有被换成 `__ST_BTN_PH_…__`。
2. **`Tn()` 真的取到 `.mes_block` 吗。** 我用 cheerio 按 `index.html` 的模板结构跑的选择器，结论是 `.mes_block`。但 cheerio 不是浏览器，**建议真机上敲一行 `document.querySelector('.mes[mesid="0"]').querySelector('.mes_text, .mes_block')` 复核**。如果真是 `.mes_block`，那插件「不插在 `.mes_text` 里」这件事本身就是一堆位置问题的源头。
3. **`maxDepth: 1` 到底是不是有意的。** `docs\交接.md:1056` 写的理由是「与行动选项同档：一楼是用户输入，正文只出在 AI 输出里」，但酒馆的 `depth` 是**从最新往回数**的（`public\script.js:1575` / `:3619`）。按代码看，实际效果是「只有最新两楼走前端」。这跟作者写下的理由**对不上**——是真有意为之还是理解偏差，我没法从文件里判定。
4. **chami 插件 `image###` 的调用点没还原。** 字符串表里确认有 `"image###"` / `"###"` / `".mes_text"` / `"txt2img"`，但混淆代码里字符串是按下标取的，我没把调用行还原出来，所以**「它确实在 `.mes_text` 上跑这个正则」这句我不敢写死**。
5. **`RBQ.api.createPromptCard` 的稳定性没保证。** 它在 `window.RBQ.api` 上、插件自己的子插件也在用，但没有找到任何官方文档或版本兼容声明。`RBQ.version` 是 `1.1.0`，扩展版本是 `0.3.106`（`@97,184`），两个号都对不上，跨版本行为没法预判。
6. **`RBQ.on/off/emit` 这套 hooks 有没有人真的 emit 过。** 我只看到它定义在 `@100,064`，**没有**在压缩代码里找到可靠的 `.emit(` 调用点（压缩后调用形式不固定，grep 不可靠）。所以「挂 `RBQ.on('xxx')`」这条路**目前不推荐**，能用的是 `CustomEvent`（名字见 §3.1 ⑧）和 `RBQ.api.*`。
7. **Smart Draw 的 `markers` 用户实际填的是什么。** 默认是 `[draw]\n[画图]`（第 2442 行），但用户真机上大概率自己改过（`docs\交接.md` 第十九轮记的是它插了一枚 `🎨 生成` 按钮）。这直接影响方案 1 要去重时的判据。
