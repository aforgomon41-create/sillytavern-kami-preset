## 一、口径落实对照表

### A. 一律以用户为准（theirs 永远赢，不询问、不覆盖）

| 条 | 口径 | 落实位置 | 自测 |
|---|---|---|---|
| A1 | 条目开关 `prompts[].enabled` | `analyze()` 合并条目一律 `cloneObj(t)` 或 `fromNextPrompt()` 里 `enabledOf(tObj,…)`，先看 theirs | update-flow 合并②」「用户的条目开关保留」；preset-merge「条目开关留在用户手里」 |
| A2 | 顺序表开关 `prompt_order[].order[].enabled` | `mergedOrderEntry()`：合并顺序表条目的 enabled 先看 theirs 的顺序项、再 theirs 条目本体 | preset-merge「顺序表里的开关同样留在用户手里」＋「顺序裁决用新版后开关仍关」 |
| A3 | 脚本 enabled 与 data | `mergeScripts()`：正文/名字/info/button/export_with 全给 next，`enabled` 与 `data` 原样回填 theirs（运行时状态在 data 里，跟着不丢） | preset-merge「脚本正文一律用 next／开关留在用户／data 整个留用户」 |
| A4 | `extensions.tavern_helper.variables` | theirs 的 tavern_helper 整体克隆保留，只有 theirs 真没有 variables 键才接 next 的默认 | preset-merge「脚本变量留在用户手里（新版改了也不覆盖）」 |
| A5 | 顶层参数 | merged = theirs 的全部顶层字段原样保留；next 独有的顶层字段才加进来（没有用户的东西被覆盖） | preset-merge 顶层参数组（temperature / openai_max_context） |
| A6 | 正则开关 `regex_scripts[].disabled` | `mergeRegexes()` 每条合并后 `disabled` 一律取 theirs（新版想重开也改不了） | preset-merge「正则的开关留在用户手里」 |

### B. 条目内容 / 顺序 / 增减（自动辨别，真冲突才问）

| 情形 | 落地 | 备注 |
|---|---|---|
| 条目对齐 | 按 `identifier`；theirs 独有 → 原样保留（口径「用户新增」；没有 theirs 条目的分类不会复活被删条目） | |
| 用户动过 | `diffPair(b, t, 'enabled')` 非（只比 base 里**两边都有**的字段，除 enabled） | 酒馆运行时往活设置挂的标准字段不算「用户动过」（镜像里那份原始文件没有） |
| 新版动过 | `diffPair(b, n, 'enabled')` | |
| 只有用户动过 | theirs，不问 | 「只有用户改过 → theirs（不问）」 |
| 只有新版动过 | 吃 next（正文更新就算更新本身），enabled 仍留用户 | 「只有新版动过 → 富 next」 |
| 两边都动过 | 进清单 key='pm:<id>'，默认 choice='mine' | 「两边都改过 → 进待裁决清单」、一键全覆盖时吃 next |
| 新版新增 | 直接加（含顺序表追加，不问） | 「新版新增条目直接加进来」 |
| 用户新增 | 保留（在 theirs 里，自然在） | 「用户新增条目仍在」 |
| 用户删 + 新版没改 | 不加回来 | 「默认裁决下 b 保持删除」 |
| 用户删 + 新版改 | key='rm:<id>' 进清单；默认保持删除，改选 next 时恢复 | 「删改冲突选『用新版』→ 条目恢复」 |
| 新版删 + 用户没动 | 跟着删（不问） | 「新版删掉、用户没动 → 跟着删除」＋ report.followedRemovals |
| 顺序（排列） | 正常模式：用户动过=已知条目排列 ≠ base、新版同理；双边都动 → key='ord:<cid>' 一项；degraded 时直接比 theirs vs next。过滤口径：只比**两边 base 里都有的**条目位置，两个版本各自往尾部加自己的新条目不算「调过排列」 | 「顺序两边都调过 → 单独一项待裁决」＋「各自加新条目不误伤成排列冲突」 |
| **退化模式（base 取不到）** | theirs 与 next 的**每处**共享条目差异都进清单（userF=nextF=theirs↔next 的差异），默认保留我的；新增照加、删除的照删 | preset-merge「退化模式」组 + update-flow「合并⑥」 |

### C. 一律用 next

- 脚本正文 / 名字 / info / button / export_with → `mergeScripts()` 直接拿 next 的那份，只回填 enabled 与 data。
- base 里没有而 next 有的条目结构（全新条目 / 全新脚本 / 全新正则）→ 照加。
- **正则条目的口径落地说明**：口径原文把「正则正文一律 next」写进 A6；实现里正则按条目走**同一套三方合并**（与提示词条目同一条 changedField 机），`find_regex` / `replace_string` 在「只有新版动过」时照常更新；用户与新版两边都动过的才进裁决（key='rx:<id>'，默认保留我的）。理由：宁可少更新、不动用户手改的内容；常见情况（用户没碰正则）正文一定吃新版，硬规格的正文目标不受影响。
- `name` 例外：合并结果的顶层 name 取 next（这份文件就是新版；ST 加载时会剔除顶层 name，不影响用户任何读数）。

### D. 写盘

| 步 | 口径 | 落实 |
|---|---|---|
| ① 备份 | `importRawPreset('<当前预设名> · 合并前备份', theirs)` | `writeMergedFiles()` 第 1 步（`70-远程更新.js`），备份写不进去就整体停手（备份不许跳过） |
| ② 导入合并结果 | `importRawPreset(<新版预设名>, mergedText)` | 第 2 步；**绝不覆盖原文件**（两次都是新名字导入） |
| ③ 提醒切换 | 沿用原 toast 口径 | `finishImported()` 保留原句「打开左侧抽屉的『AI 响应配置』…」 |
| ④ 合并报告 | 人话 | 日志一行 + `last.merge`（status() 里可看）：应用 X 处 / 保留 Y 处 / 新增 Z 条 / 待裁决 W 处（保留我的 a / 用新版 b）；面板页头也写同样的数字 |

再往下的编排判定（70 号侧）：
- theirs 不可得（读不到活设置 / 没有 prompts）→ 不合并、不备份，按老流程原样导入（保守退化，绝不半途 break 预设）。
- 冲突为 0 → 不弹任何裁决，直接「备份 + 导入合并结果」。
- 主路径 → `HOST.KamiPreset.openMergeReview(plan, onApply)`；返回 false / 抛错 → 原生弹窗兜底。
- 用户在面板上点 ✕（或脚本被关）→ `onApply(null)` → 70 号记 `last.action='merge-cancelled'`，本次不写盘；下次查更新可以重来。
- 原生弹窗兜底：摘要（条目数 + 每项名字与字段摘要，滚动区）+ 两枚一键；**Esc/关窗也算「保留我的」**（宁可少更新）。
- base 取法：`https://cdn.jsdelivr.net/gh/<o>/<r>@<用户的 tag>/mirror/manifest.json` → file → `@<tag>/mirror/<file>`；任一步失败 → 退化模式 + 一行日志。没做 GitHub Releases 附件的兜底源（守「别把这块做复杂」）。

## 二、计划数据结构

```
plan = {
  degraded: <bool>,            // base 取不到 = true
  stats: { applied, kept, added, conflicts },
  conflicts: [                 // 待裁决清单（每项 choice 默认 'mine'）
    { key, kind, id, name, fields }   // kind: prompt | delete | order | regex
  ]                             // key: 'pm:<id>' / 'rm:<id>' / 'ord:<character_id>' / 'rx:<id>'
}

applyMergePlan(base, theirs, next, plan) → { merged, report, plan }
report = { degraded, applied, kept, added, followedRemovals, restored,
           decidedMine, decidedNext, conflicts }
```

## 三、UI 与退化路径

**主路径（🌟 预设设置面板）**：
- 新 tab「🔀 更新合并」，`special:'merge'`；裁决定期打开时它**排在 tab 第一格**（用户正等着完成一次更新，别的 tab 得让位），其余 tab 照旧。
- 只在裁决页存在（`openMergeReview` 传入 plan -> `mergeCtx`）时出现，70 号没有待裁决就永远不会造这页（普通面板不受影响）；读不到预设时这一页也照常能出（裁决与面板读数链是两回事）。
- 内容：摘要卡（有多少要裁决 + 「没列进来的一律以你为准」）→ 顶部「全部保留我的 / 全部用新版」（契约 `.kami-btn`）→ 每个冲突项一张卡（`.kami-card` 头 + 「改了：content…」note + `.kami-seg` 保留我的/用新版 二选一，默认保留我的，就地重画不丢滚动位置）→ 底部「应用并完成更新」（`.kami-btn--primary`）。
- 关掉面板（✕ / 手势收起 / 抽屉下拉）= 放弃裁决 → onApply(null) → 70 号中止，不写盘。
- 类名只用契约已登记的；**没有新增皮肤类名 / 没有新增令牌**（皮肤契约 §4 不受影响）。
- 清单长时正文区（`.kami-body .kami-scroll`）自己滚（预览台 9 tab、420px 悬浮窗内实测有滚动条）。

**退化（原弹窗路径，面板脚本没跑 / 没开成时）**：
- `triggerSlash('/popup result=true scroll=true okButton="全部用新版" cancelButton="全部保留我的" <摘要>')`；
  HTML 走 `escText()` 净化（离线自测覆盖斜杠命令字符安全）。
- 回执 '1' = 所有冲突吃新版；'0'/Esc/关窗 = 全部保留我的。
- 弹窗失败 → 直接按「全部保留我的」继续合并（只是不落覆盖层），新增照加。

## 五、遗留与风险

1. **脚本正文的覆盖**（实现读法）：A3/C 说脚本正文一律 next。用户如果在脚本库里手改过某脚本的正文，那些改动会被新版覆盖（data 里的设置不会丢）。这是口径明文，但值得在发版本说明里提示一次「脚本正文以新版为准」。
2. **正则的三方合并**：正文（find_regex/replace_string）在「你动了、上游没动」时会留你的 —— A6 的字面「正文 next」被实现成「只有两边都改过才算冲突」。常规情况是等价的（用户没碰 → 全吃新版）。若产品想字面照打「正则正文无条件 next」，改一行即可（`mergeRegexes` 的 userF 分支删掉）。
3. **base 依赖镜像 tag**：构建号 ≤113 的历史版本没有 `mirror/` 文件（mirror 是 v0.90-114 之后才有的），那些老用户不会走到合并（直接进退化模式：全差异裁决）；不用为旧 tag 补镜像。
4. **性能**：base/theirs/next 都是全量 JSON 克隆（~2.5 MB × 3），手机上一次性内存峰值可接受；没有做增量。冲突清单上限也没做 (弹窗里的滚动区实测 OK)。
5. **裁决 UI 的可滚动性**：清单长时面板正文自己滚（兜底皮肤的 .kami-scroll 已带 overflow）——真机上几十条待裁决的长列表体验是推算、没在真机滚过（浏览器的滚动探针没跑这项）；后续若用户报「裁决页滑不动」，先查皮肤的 .kami-scroll 链（交接 §三第 31 条的同一坑）。
6. **合并报告的展示口径**：目前只在日志与 toast 面板头部出现摘要；没有单独「报告文件」落盘（用户没要求，口头/toast 口径已沿用现有那句）。
7. **未做**：文档交接（`docs/` 不在本轮文件边界）、发布（没 commit/push）、真机试验。
