## 1. 一句话结论

**智绘姬 = SillyTavern 第三方扩展 st-chatu8（`manifest.json` + `index.js`，作者"从前跟你一样"，v2.3.4 起改名智绘姬）。它主要靠扫渲染后的 DOM 找插图标签：先 `document.getElementsByClassName("mes_text")`，再遍历所有 `iframe` 读 `contentDocument`，把可见文本拼成一条字符串跑正则匹配 `image###…###`，然后就地删掉标签、就地插一个「生成图片」按钮——按钮是建在标签所在文档里的，正文在 iframe 里就插进 iframe。**

补充一句：它**完全不碰 `srcdoc`**（全文件 0 次命中），所以实测踩到的"`innerHTML` 字符串替换打在 srcdoc 属性值上"那个坑，它天然绕开了。

### 问题 7：它跟 `<image_Tag>` / `<image>` / `<MakeImage>` 有没有关系？

- **`<image>`：是核心链路，强相关。** 它是插件自用的 XML 外壳，也是它写回聊天原文的落盘标记。全文件 `<image>` 相关命中 62 处。
- **`<image_Tag>`：0 命中。`<MakeImage>`：0 命中。**
  - 唯一相近的是设置键 `ch-history_keep_image_tag`（L24109、L109217），那是"历史消息里保留 `<image>` 标签"的开关，不是标签名。
- **所以：预设里那条屏蔽 `<image_Tag>` / `<MakeImage>` 的正则，跟智绘姬不是同一条链路。这两个标签它根本不认。**
- **但要注意**：如果预设里还有一条**屏蔽 `<image>` 的正则**，那跟智绘姬就是同一条链路了——因为它自己也会建一条同样作用的 `st-chatu8-不发送image标签`。两条同时存在不会互相冲突（都是删成空串），但**都很容易顺手把插件写回原文的 `<image>` 标记一起删掉**，结果是按钮不出现、或图片挂不上。

## 4. 对我们最关键的三句

**① 它扫的是 DOM，不是原文。**
`.mes_text` 的可见文本 + 每个 iframe 的 `contentDocument`，用 TreeWalker 拼成一条 `logicalText` 再跑正则（L53476、L53452、L53798）。聊天数组 `chat[mesId].mes` 只用来落盘和回填，`getChatMessages` 一次都没用（0 命中）。**所以它跟我们"正文活在 iframe 里"这件事天生兼容，我们不需要为它做任何适配。**

**② 它插按钮是"就地替换"，文档跟着标签走。**
`range.deleteContents()` 删掉标签文本，再 `range.insertNode()` 把 `button.image-tag-button.st-chatu8-image-button`（文案「生成图片」）和 `span.st-chatu8-image-span` 插在同一位置（L53601、L53177、L53220–L53235）。元素建在 `rootElement.ownerDocument` 里（L53453），**正文在 iframe 里时按钮就活在 iframe 里**。

**③ 它有一套现成的"影子文本"迂回方案，还有可用的全局 API。**
`insertOriginalText` 模式会把 `<image>提示词</image>` 写回 `chat[mesId].mes`（L17162–L17165），`saveChatConditional()` 存盘，再 `renderMessage(mesId)` 重渲染（L17183–L17184），让前端卡重新渲染出 DOM 后又被扫到——**这就是"绕过 iframe 隔离"的现成答案**。可用扩展点：`window.regexAIBridge`、`window.showChatuSettingsPanel`、`window.loadSilterTavernChatu8Settings`、`window.zidongdianji`；可监听事件 `st_chatu8_auto_click_complete`；可用版本探针 `window.chatu8LocalVersion`。
