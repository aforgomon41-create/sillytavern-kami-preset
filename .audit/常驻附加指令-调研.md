### 2.2 「能不能在消息发出去之前拿到并改写」——四个事件的成品结论

**MESSAGE_SENDING：不存在。** 三处独立验证全部为 0 命中：

  ```js

        let message = chatItem.mes;
  ```

  → **最后一条消息 depth = 0**。跳过条件的实现见 `public\scripts\extensions\regex\engine.js:361-370`：
  ```js

            if (!isNaN(script.minDepth) && script.minDepth !== null && script.minDepth >= -1 && depth < script.minDepth) {
  ```

**对本次设计的直接含义（好消息）**：只要把 `<god>…</god>` 追加在**最后一条 user 消息**上，这条正则**不会**把它剪掉。而因为我们在提示词层追加、不写回聊天记录，下一轮它根本不存在于历史里，也就永远不会被这条正则碰到。

**但如果是「改聊天记录」方案就完蛋**：写进 `chat[].mes` 的那一楼，下一轮变成 depth ≥ 1，被这条正则整段删掉 ⇒ 用户会看到「聊天记录里有、模型却收不到」的鬼影。

## 7. 风险清单（逐条带证据）

### R1 · 顺带注入了别的请求 —— 压缩脚本的摘要请求会被污染 ⚠️ 最需要防的一条

`60-压缩.js` 的摘要是用**酒馆助手的 `generateRaw`** 发的（`60-压缩.js:1357, 1394-1400`），不是酒馆自己的生成。而酒馆助手 `generateRaw` 会派发同一个事件：

`JS-Slash-Runner\src\function\generate\generateRaw.ts:543-545`
```ts
  const prompt = chatCompletion.getChat();
  eventSource.emit(event_types.CHAT_COMPLETION_PROMPT_READY, { chat: prompt, dryRun: false });
  return { prompt };
```
> **⇒ 只要监听 CHAT_COMPLETION_PROMPT_READY，摘要请求也会被追加一次 `<god>`。** 摘要请求的最后一条是 `{role:'system', content: OUTPUT_CONTRACT}`（`60-压缩.js:1350-1356`），所以加一条「**最后一条必须是 user**」的守卫就能挡住它。这一条**必须写**，不是可选优化。

对照：`generateRaw` **不派发** `GENERATION_AFTER_COMMANDS`、**也不派发** `GENERATE_AFTER_DATA`（在 `generateRaw.ts` 全文搜这两个名字 → 各 0 命中）。所以**改用 GENERATE_AFTER_DATA 能天然躲开压缩脚本**，代价是它不覆盖纯文本补全接口（那时 `generate_data.prompt` 是字符串）。两条路各有取舍，见 §8。

### R2 · 「重生成 / swipe」会再追加一次

- `type === 'swipe'` 时酒馆会先弹掉最后一条（`script.js:4438-4440`：`if (type === 'swipe') { coreChat.pop(); }`），于是最后一条又变回 user 消息 → 我们的追加逻辑**自然再次生效**（这是想要的）。
- 但同一个回合内 `CHAT_COMPLETION_PROMPT_READY` 会触发**多次**（数 token 的 dryRun 一趟、真正发送一趟；`35-角色名包裹.js:134-135` 的注释就记了这件事）。
- ⇒ 追加逻辑必须**幂等**：写之前先判断「这条 user 消息末尾是不是已经有我们那一段」，有就跳过。否则 dryRun 之后再发就会叠两遍。

### R3 · token 成本

每次生成都多背一段。因为它**不写回聊天记录**（见 §2.2 / §3.1），所以它**不随上下文深度累加**，每轮只算一次，代价是「指令字数 × 轮数」。真正会失控的是「改聊天记录」方案 —— 那一版会把标签塞进历史，每轮都随上下文重发一次，越聊越贵，而且老楼层还会被 §4.1 的正则删掉（变成「花钱存了却发不出去」）。

### R4 · 用户自己在输入框写了同名 `<god>…</god>`

- 用户手打的那一条**在发送时会原样存进聊天记录**：`script.js:5816` 的 `getRegexedString(messageText, regex_placement.USER_INPUT)` **没有传 depth**，而 `engine.js:362` 的深度检查要求 `typeof depth === 'number'`，所以**深度限制在发送这一刻不生效**；同时 `promptOnly:true` 的脚本在这一次调用里也被 `engine.js:352` 的 `(script.promptOnly && isPrompt)` 挡住（此处没传 `isPrompt`）。⇒ **用户自己写的 `<god>` 会进聊天记录。**
- 到下一轮，那条消息变成 depth ≥ 1，就被 §4.1 的正则从提示词里删掉。所以**用户手打的 `<god>` 只在当轮有效**，这与「常驻」的语义正好互补，不打架。
- **要防的是重复**：如果用户本轮已经自己写了 `<god>…</god>`，我们的自动追加就应当**让位**（用户显式输入优先于面板默认值），否则一轮里会出现两段 `<god>`，模型的仲裁优先级表述（`<god>` 指令 > …）没有定义「两段谁赢」。建议：检测到已有 `<god>` 就跳过，并给一条 toast 说明。

### R5 · 群聊 / 多角色

- 群聊里每个成员各生成一次（`GROUP_MEMBER_DRAFTED`，见 `@types\iframe\event.d.ts:324`），所以**每个成员那一轮都会各追加一次** —— 这是符合预期的（每个成员都该遵守常驻指令）。
- 但要注意 `script.js:4478`：`const isOtherGroupMember = selected_group && coreChat[i].name !== name2;` —— 群聊里**别人**的楼层不参与本轮的 reasoning 注入，说明同一份 chat 数组在群聊下会被复用多次。追加逻辑只认「最后一条 + role === user」，不受影响。

### R6 · 与 35-角色名包裹 同时运行

两个脚本都监听 `CHAT_COMPLETION_PROMPT_READY`、都能拿到同一个 `data.chat` 数组：
- `35-角色名包裹.js:152` 做的是 `m.content = applyMode(m.content, mode, counter)`（**原地赋值**）。
- 新脚本只要也**原地赋值**（`last.content = last.content + 追加段`），两者互不覆盖 —— 一个换 `<n>` 标记，一个在末尾加 `<god>`。
- ⚠️ **绝对不要在新脚本里写 `data.chat = [...]` 或重建数组**：在 ST 1.18 的主链路里 `openai.js:1614` 返回的是闭包里的 `chat` 而不是 `eventData.chat`（见 §2.2），整体替换会**静默失效**，而且可能让 35 号的改动一起丢掉。**这就是本任务的头号实现陷阱。**

### R7 · 与 20-反截断 同时运行

`20-反截断.js` 走的是**请求体层**的 fetch 补丁，在提示词组装**之后**（`20-反截断.js:174-208` 的 `planRequest` / `placeControl`）：
```js

    patched.messages = placeControl(messages, instructionFor(tool));
```
它只会**新增**一条 system/user 控制消息（`placeControl` 在 `anchor` 模式下插在最后一条 user **之前**，否则追加到末尾），**不改 user 消息正文** ⇒ 不会冲掉我们的 `<god>`。
> 副作用（可接受）：`anchor` 模式下 反截断 把控制消息插在最后一条 user 消息**之前**，所以我们的 `<god>` 仍在**最后**，位置反而更好。

### R8 · `dryRun` 该不该改

`35-角色名包裹.js:134-135` 明确选择「照改」：「dryRun（酒馆自己数 token 的那一趟）也照改，改的是当趟的临时数组，无副作用。」**建议跟随**：不改的话，面板上显示的 token 数会少算这段指令，用户会以为还没超限。代价是必须做 R2 的幂等守卫。

### R9 · 编辑重发 / 消息被改

监听的若是 `MESSAGE_EDITED` / `MESSAGE_UPDATED` 一类的记录层事件，会牵扯存盘。**提示词层方案完全不需要挂这些事件** —— 用户编辑完旧消息再重新生成时，`prepareOpenAIMessages` 会重新组装，我们的守卫照常生效。这是选提示词层的又一好处。

### R10 · 拿不到 `eventOn` / 事件名时不静默

照 `35-角色名包裹.js:166-171` 与 `40-预设设置.js:3239-3243` 的既有约定：**拿不到就 log 一行 + 面板上给提示，绝不假装成功**。

## 10. 一句话总结

`<god>` 这套语法、语义、优先级、以及「老楼层自动清理」的正则，预设里**全都已经存在**；缺的只是「每次发送自动往最后一条用户消息尾巴上贴一段」这一个动作。而这个动作在 `CHAT_COMPLETION_PROMPT_READY` 里改一个字符串就能做到，聊天记录一个字都不用动 —— 现成先例是 `src\scripts\35-角色名包裹.js`。唯一必须记住的坑：**原地改 `content`，不要替换整个数组。**
