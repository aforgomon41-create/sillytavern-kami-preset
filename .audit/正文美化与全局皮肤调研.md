## 〇、结论速览（先看这段就够）

1. **正文美化推荐走「脚本层包裹」，不要走第三条正则。** 正则那条路会把两个既有前端和 HTML 美化一起吞掉，插件按钮的「按句子锚点插入」也会失效；而且每个楼层要多背一份约 50KB 的兜底皮肤。
2. **开启后 HTML 美化与插件按钮不会坏**，前提是守住了「让位清单」：`div.TH-render` / `pre` / `iframe` / `button` / `input` / `select` / `textarea` / `details` / 带 class 的元素 / 带行内 style 的元素，一律不包。这条已在探针里实测通过。
3. **整个酒馆能被皮肤化，但只该做「增量」**：把令牌上提到 `<html>`，再加一份**脚本内置、所有皮肤共用**的酒馆 UI 覆盖规则。第一步只做「顶栏/抽屉 + 聊天外壳 + 输入框」的底色、描边、圆角、字体四类。
4. **两件事的工作量**：正文美化约 1 个文件 + 契约 2 小节，风险中低；全局皮肤约 1 个新文件 + 契约 4 小节 + 15 套皮肤的令牌块改写，风险中高，且必然和用户自己那套 25KB 自定义 CSS 打架。

### 1.4 「HTML 美化条目」到底是什么、落在哪

预设里 `🎥 HTML美化` 条目（`src/preset.base.json:3008`，条目名在 3016 行）指示模型：

- 触发时**中断纯文本**，插入 `<medium>…HTML…</medium>`；
- **紧跟其后**输出纯文本副本 `<medium_content>…</medium_content>`；
- HTML **严禁** `<html>` / `<body>` / `<script>`，**必须用行内样式**，容器默认 `margin:10px auto; max-width:90%/400px`，要求高对比度。

两条正则把它切开（`list.json`）：

- `隐藏|HTML美化留档文字`（90-106 行，`markdownOnly`）把 `<medium_content>` 从**显示路径**删掉 → 用户看不到重复的纯文本。
- `屏蔽|HTML美化代码`（107-123 行，`promptOnly`）把 `<medium>` 从**提示词路径**删掉 → 模型下一轮看不到自己上次吐的 HTML。

**真机取样**（同上聊天文件 mesid=2，偏移 2828 起）：

```html
<medium>
<div style="max-width: 350px; margin: 12px auto; padding: 16px; background: #20242a; border-radius: 16px; box-shadow: 0 8px 24px rgba(0,0,0,0.4); font-family: -apple-system, ...; color: #e6edf3;">
  <div style="display: flex; ..."><span style="width:10px;height:10px;background:#2ea043;border-radius:50%;..."></span>
  <span style="font-size:14px;font-weight:600;color:#f0f6fc;">柚香 (妹妹)</span></div>
  <span style="font-size:11px;color:#8b949e;">23:42</span>
  ...
```

**结论：HTML 美化 = 带行内样式的裸 HTML 片段，是 `.mes_text` 的直接子元素。它没有 class、没有事件、不依赖任何我们的代码。** 它唯一的结构特征就是「有 `style` 属性」——这就是后面让位规则的判据。

## 二、任务 A：正文美化前端的方案调研与设计

### 2.1 机制选型对比

#### (a) 第三条正则载荷：匹配整条消息正文 → 替换成 iframe/srcdoc

**结论：不可行。** 四条硬伤，逐条有据：

1. **会把两个既有前端吞掉。** 正则列表是**按顺序**跑的（`engine.js:347` 的 `allRegex.forEach`）。新正则若排在两个前端之后，它匹配到的「整条正文」里已经含两段被围栏包住的前端文档 → 整段被塞进我们 iframe 的载荷里 → 酒馆助手在外层只看到一个 `<pre>`，里层那段变成转义文本，两个前端**彻底消失**。若排在它们之前，`<nyaruko_think>` / `<options>` 会被一起吞掉，永远等不到替换 → 同样消失。**两条路都是死路。**
2. **HTML 美化会被降级。** `<medium>` 的 HTML 会变成我们载荷里的字符串，要么被当纯文本显示，要么被我们自己的 markdown 引擎重新渲染一遍——多一次 DOMPurify 往返，且 `<medium_content>` 的隐藏正则与新正则的先后顺序又会打架。
3. **插件按钮的「按句子锚点插入」会失效。** 智能生图触发器把卡片插到正文里靠的是在容器里搜文本节点（`收到的文件/smart-draw-trigger.js:10695-10725` 的 `insertByDirectTextSearch`，容器来自 `RBQ-Draw-index.js` 的 `getMessageTextContainer` → `.mes[mesid=N]` 下的 `.mes_text, …, .mes_block`）。正则替换发生在**渲染之前**，那时候插件按钮还不存在；等插件运行时，正文文本已经在 iframe 里了，它在 `.mes_text` 里搜不到锚点 → 全部退化成「追加到正文末尾」（`smart-draw-trigger.js:10947-10969` 的 `mountFallbackFragment`）。**功能没坏，但「图插在对应句子旁边」这个核心体验没了。**
4. **每个楼层多背一份 50KB。** 走正则就意味着 `expandForRegex()` 会把 `base.css` 再内联一份（`build/kami-doc.mjs:68`）。契约 §9.6 已经用「showdown 不内联」论证过这个代价，正文前端只会在更多楼层上触发（几乎每条 AI 消息都有正文，思维链不一定有）。

**「先把嵌在正文里的东西请出来 / 占位托管」可行吗？** 理论上可以让新正则只匹配「围栏之间的纯文本段」，但酒馆引擎只认 `$n` 与 `$<name>`（`engine.js:422`）、且 `verify-frontends.mjs:82-91` 强制「模板里 `$1` 只能有一个」，多片段重拼几乎没法写；再看第 3 条——**插件按钮在正则时代还不存在，任何「请出来」的方案都救不了它**。所以这条路整体否掉。

#### (b) 脚本层包裹：渲染后接管，只包纯文本段，遇到既有元素就绕开

**结论：推荐。** 逐条回应你提的三个担心：

**① 酒馆什么时候重建消息 DOM（= 我们的包裹会不会被反复套娃）**

| 场景 | 酒馆代码 | 对我们的影响 |
|---|---|---|
| 新楼层 | `script.js:2522` `updateMessageElement()` 建新元素 | 新 `.mes`，包一次 |
| 切聊天 / 往上翻 | `script.js:1497-1530` `redisplayChat()`：`.nextAll('.mes').addBack().remove()` 后重建 | 整批 `.mes` 重建，全部重包 |
| 往上加载更多 | `script.js:1431-1464` `showMoreMessages()` | 新插入的批次重包 |
| swipe 切分支 | `script.js:2513-2520`：复用同一个 `.mes` 元素但重新 `updateMessageElement()` | `.mes_text.innerHTML` 被整体替换 → 旧包裹被销毁 → 重包 |
| swipe 并重新生成 | `script.js:10221` `.mes_text.html('...')` | 同上 |
| 编辑消息 | `script.js:8202-8216` `.mes_text.empty()` 后只放一个 `textarea#curEditTextarea` | 包裹被清空；此时 `.mes_text` 里只有一个 textarea，**包不出东西来**（探针实测 0 个包裹层） |
| 翻译 / 叙述 | `script.js:1978` `.mes_text.html(messageFormatting(...))` | 重包 |
| 流式打字机 | **不动 `#chat` 里的 `.mes_text`** | 见下 |

**套娃问题不存在**，原因有两条：

- 酒馆是**整体替换 `.mes_text` 的 innerHTML**，不是往里插节点。我们的包裹每次都是被销毁后重建，不会嵌套。
- 包裹层自己带 `class="kami-root"`，而「有 class 的元素」本来就在让位清单里 → 第二次扫描时它被当成保护元素跳过。**探针实测：连点三次「跑一遍包裹」，第二、三次都是「0 个连续段」，包裹层数量恒为 2。**

**② 会不会破坏酒馆自己的功能**

- **复制**：`script.js:8081-8083` 取 `mesBlock.find('.mes_text').text()`。jQuery `.text()` 拼接所有后代的 `textContent`，我们的包裹不增删文字 → 复制内容不变。（注意：因此**包裹层里不要用 `::before` 之类的生成内容塞字**，虽然 `.text()` 读不到，但读屏软件会念出来。）
- **编辑**：见上表，编辑态下包不出东西；且 `textarea` 在让位清单里，双保险。
- **swipe**：`.mes` 元素被复用、`last_mes` class 由 `script.js:2536-2537` 重新指派，都与包裹无关。
- **媒体内联**：`.mes_text.inline_media:not(:has(.edit_textarea)){display:none}`（`style.css:1535`）把整段正文藏掉。我们的包裹在它里面，一起被藏，**行为不变**。
- **推理块显隐**：酒馆用 `.mes:has(.mes_reasoning:empty)`、`#chat:not([data-show-hidden-reasoning="true"]) …` 等结构选择器（`style.css:469, 485-505, 1219`）控制推理块。这些选择器爬的是 `.mes_block` 的子孙，`details` 只要还是 `.mes_text` 的**兄弟**就不受影响；把 `details` 放进让位清单是双保险。
- **`.mes_text:empty`**：`style.css:1219` 用 `.last_mes:has(.mes_text:empty)`。所以**纯空白文本节点和注释节点一律不能进包裹**（否则「只有推理、没有正文」的楼层会被我们造出内容，那条规则失效）。这条是本轮实测踩到的：探针第一版把注释节点当成可包内容，每个保护元素前多出一个空 wrapper。
- **流式打字机**：ST 1.18 **不在 `#chat` 里做逐字渲染**。流式进度走一个独立浮窗（`public/scripts/streaming-display.js`），它自己造一个 `div` 并**也加 `mes_text` 类**（`streaming-display.js:182`），每个 chunk 整块重写 `innerHTML`（`:281`），挂在最上层 `dialog[open]` 里（`:190-191`）。
  → **所以包裹逻辑的选择器必须限定在 `#chat` 里面**（建议 `#chat .mes .mes_text` 或 `#chat > .mes .mes_text`），否则会去包流式浮窗，每个 chunk 重包一次，直接卡死。
- **酒馆助手的前端渲染**：`render$mes()` 靠 `$pre.parent('div.TH-render')` 认亲（`src/panel/render/use_collapse_code_block.ts:11,26-28`；`src/util/is_frontend.ts:7` 也按 `TH-render` 认）。**只要不在 `.mes_text` 与 `div.TH-render` 之间插任何一层，它就一切正常。** 这就是「保护清单」存在的主要理由。

#### (c) 混合：正则只做「标记」，脚本做实际包裹

**结论：不必要。** 一条只插隐形标记的正则，信息量不如脚本自己看 DOM（脚本能直接数 `.mes_text` 的直接子节点）；代价却是多一条逐楼层正则、多一个必须和另外 11 条排序协调的条目。唯一说得上的好处是「开关能顺着酒馆自己的正则开关走」，但那反而把开关藏到了用户找不到的正则面板里——而用户明确要求开关放在皮肤管理面板。

### 2.2 兼容性规则清单（硬要求）

#### A. 必须让位（永不包裹，保持 `.mes_text` 的直接子元素）

| 对象 | 判据 | 包错了会怎样 |
|---|---|---|
| 两个既有前端的宿主 | 标签 `div.TH-render`，及其中一切 | `use_collapse_code_block.ts:26` 的 `$pre.parent('div.TH-render')` 落空 → 再包一个 `.TH-render` → **同一楼层出现两个 iframe**；且 `Iframe.vue:66-71` 会把「非 iframe 的兄弟节点」加 `hidden!`，我们包进去的正文会被一起藏掉 |
| 任何 iframe | 标签 `iframe` | 第三方前端被连坐同上 |
| 任何 `<pre>` | 标签 `pre` | 普通代码块若含 `html>` 字样会被酒馆助手当前端；包一层就触发上面的双 iframe |
| 插件插进正文的按钮 | 标签 `button` / `input` / `select` / `textarea` / `label` | ① `base.css:172-173` 的 `.kami-root button,input{font:inherit;color:inherit}` 加皮肤按钮规则 → 插件按钮字号/配色/尺寸全变；② 皮肤可能给 `.kami-root` 或其祖先加 `position:relative` / `overflow:hidden` → 插件按钮里的绝对定位浮层包含块改变、或直接被裁掉；③ 点击热区被我们的规则（如 `pointer-events`）吃掉 |
| 酒馆自己的推理块 | `details` / `summary`，及 `.mes_reasoning*` | `style.css:469/485-505` 的 `:has(.mes_reasoning:empty)` 等结构判据失效 → 推理块该藏不藏、该显不显 |
| HTML 美化条目产出的 HTML | **有 `style` 属性**（预设强制要求，`preset.base.json:3008`） | 卡片的 `margin:12px auto` 居中、`max-width`、自带配色会被 `.kami-root` 的 `text-align` / 继承字体干扰；更糟的是皮肤一给 `.kami-root` 上背景，就变成「卡片套卡片」 |
| 插件插入的卡片容器 | **有 `class` 属性**且不是 kami 前缀 | 例如 `.rbq-sdt-card`（`smart-draw-trigger.js:17`）。它自带一整套 `!important` 行内样式与自己的 `<style>`，包起来只会和它的规则打架 |
| 酒馆的其余结构容器 | `.mes_buttons` / `.mes_edit_buttons` / `.mes_media_wrapper` / `.mes_file_wrapper` / `.mes_bias` | 酒馆按这些类名查找与显隐，包起来会让查找落空 |
| 样式与元数据元素 | `style` / `script` / `link` / `custom-style` | 酒馆的 `decodeStyleTags()`（`script.js:1907-1909`）会给 `custom-style` 的内容加 `.mes_text ` 前缀，动它没有收益只有风险 |

> **「有 class 就让位」+「有行内 style 就让位」这两条，是整套规则里最省事的判据**：它同时放过了 HTML 美化（行内样式）和插件卡片（自带 class），也不需要维护一份「谁家的 class」黑名单。

#### B. 可以包裹

`.mes_text` 的直接子节点里，**没有 class、没有 style、不在上面的标签表里**的元素，加上夹在中间的纯文本节点：

- markdown 产物：`p` / `h1`–`h6` / `ul` / `ol` / `li` / `blockquote` / `table` / `hr` / `br` / `strong` / `em` / `a` / `img`
- 模型直接吐的裸文本节点
- 未来的、classless 的新排版元素

**包裹单位是「连续段」**：从一段开头到遇见第一个让位对象为止，合成一个包裹层；让位对象不动。这样 `[正文][思维链 iframe][正文]` 会变成两个包裹层夹一个 iframe，顺序与内容都不变。

#### C. 包裹层长什么样

```html
<div class="kami-root" data-kami-comp="body" data-kami-ready="1">
  <div class="kami-body kami-md">…这一段的原文…</div>
</div>
```

三个设计决定，各有理由：

1. **用 `.kami-root` + 新的 `data-kami-comp="body"`**：这样 15 套皮肤里**现成的** `.kami-md` 规则（`base.css:433-484`：`p` / `h1-h3` / `code` / `pre` / `blockquote` / `ul,ol` / `li` / `strong` / `a` / `hr` / `img` / `table` / `th,td`）和 `.kami-root` 的排版规则（`base.css:157-168`：字体、字号、行高、字距、颜色、`word-break`）**一行皮肤都不用改就能吃到**。这是本次设计里性价比最高的一步。
2. **不加 `.kami-shell` / `.kami-surface`**：外壳带边框、背景、圆角、阴影（`base.css:183-191`），把每段正文变成一张卡片，视觉上很吵，也会和 HTML 美化卡片互相打断。要卡片让皮肤自己加。
3. **不新增令牌、不新增类名**：全部复用契约 §4.1 / §4.2 已登记的 `.kami-root` / `.kami-body` / `.kami-md`。要登记的只有 `data-kami-comp` 的第 5 个取值。

#### D. 探针实测结果（`.audit/正文美化-包裹规则探针.html`）

用一段「仿真 `.mes_text`」跑完整规则，输入包含：酒馆推理块、两段正文、`div.TH-render`+`pre`+iframe、插件卡片（内含 `button.menu_button`）、HTML 美化卡片（行内样式）、正文、`blockquote`、`ul`、`hr`、普通 `pre`。结果：

- **幂等**：连点三次，第二、三次报「0 个连续段」，包裹层数量恒为 2 → **不会套娃**。

### 2.4 不默认开启

- **默认值**：`false`（`DEFAULT_STATE.bodyText` + `meta.json`）。升级到新预设的老用户读到的是 `false`，**行为与现在完全一致**。
- **开启后的性能**：
  - 酒馆**没有虚拟滚动**：`#chat` 里就是全部 `.mes`，条数由 `power_user.chat_truncation` 限制，**默认 100**（`public/scripts/power-user.js:133`）。`style.css:1178-1180` 只有一个 `.auto_hide{content-visibility:auto}`，用不用取决于消息有没有那个类。
  - 一次包裹 = 遍历一条 `.mes_text` 的直接子节点 + 每个连续段一次 `insertBefore`。100 条 × 平均 10 个可包节点 ≈ 毫秒级，只在**首次加载 / 切聊天 / swipe / 翻译**时发生。
  - **不新增按楼层的载荷**：这是相对正则路线最大的性能优势。正则路线等于每条有正文的楼层都多一份 50KB 的 `base.css` 要多解析一次；脚本路线是酒馆页面上一份逻辑，零重复。
  - 触发点复用 30 号现有的三条（`MESSAGE_IFRAME_RENDER_ENDED` / 300ms 防抖 MutationObserver / 8 秒 sweep，第 1296-1329 行），**不新增观察者**（契约 §9.5 的纪律：不许自己再挂一份）。
  - **唯一要注意的**：现有 MutationObserver 观察的是 `#chat` 的 `subtree:true`，突变频繁。包裹逻辑要做成「先做一次 O(直接子节点) 的廉价检查，发现没有可包节点就立刻返回」。建议再加一条保险：**单次 sweep 最多包 N 条（比如 20），剩下的留给下一个 sweep**，防止用户把 `chat_truncation` 调到几千时首次加载卡一下。

### 3.2 三条可选路线对比

#### (a) 令牌提升成全局层 + 一份我们自己的「酒馆 UI 覆盖规则」

做法：把 `--kami-*` 令牌的定义范围从「只在 `.kami-root` 上」扩到「同时在 `html[data-kami-skin="<id>"]` 上」，然后新增一份**不属于任何皮肤包**的规则文件（例如 `src/skin/tavern.css`），由 30 号脚本注入到酒馆页面，选择器形如 `html[data-kami-skin="x"] #top-bar { … }`，全部只读令牌。

- **代价**：令牌范围是契约 §3 的核心约定（「皮肤必须给全，缺失报错」），改了就要 15 套皮肤同步。可以写一个幂等的 `build/` 脚本自动把令牌块的选择器从 `html[data-kami-skin="x"] .kami-root` 扩成 `html[data-kami-skin="x"], html[data-kami-skin="x"] .kami-root`——`lint-skins.mjs` 的「前缀原样开头」规则（契约 §7 新增规则 0）对这种写法是放行的，所以不违反现有校验。
- **风险**：① 与酒馆升级——id / 类名变了规则静默失效，正是本项目最熟悉的「选择器少一个空格」类事故（交接 §五第 22 条）；② 与用户自定义 CSS 打架——`power-user.js:1147-1158` 是**运行时**把 `#custom-style` 追加到 `document.head`，如果它跑在我们 `putStyle` 之后，**同特异性下用户的自定义 CSS 赢**；要压过只能抬特异性或上 `!important`，而 `!important` 对 `!important` 就是纯粹的运气。
- **收益**：一份规则、15 套皮肤共用；换皮肤零额外成本。

#### (b) 直接改写酒馆自身类名上的样式（每套皮肤各自写）

做法：允许皮肤包里直接写 `#chat` / `.mes_text` / `.drawer` 等规则。

- **代价**：表面上不用改令牌，实际上要把「酒馆 UI 长什么样」的决定权交给 15 套皮肤 → 每套皮肤都要补一套 UI 规则，**新增第 16 套皮肤时工作量翻倍以上**，而且立刻违反契约 §2.1（选择器必须含 `kami`、绝不裸选酒馆 UI）和 §2.2（皮肤必须 CSS-only、不得引用外部资源——酒馆 UI 规则会大量用到酒馆自己的 `--SmartTheme*` 变量，形成跨体系耦合）。
- **风险**：最高。15 份规则互相不一致、和用户主题三方混战、升级即崩。
- **结论：否掉。**

#### (c) 增量路线：只做一小块，规则由脚本内置、所有皮肤共用

做法：同 (a) 的令牌上提，但**规则文件只有一份、由 30 号脚本维护**（不是皮肤包的一部分），并且**分阶段放量**：

- 第一步：`#top-settings-holder` / `.drawer` / `.drawer-content` + `#sheld` / `#chat` / `.mes` + `#form_sheld` / `#send_form` 的**底色、描边、圆角、字体**四类。
- 之后再谈 `.mes_text` 内部排版（那是任务 A 的地盘）、原生弹窗、消息操作按钮。

- **代价**：令牌上提照做；规则一份，写完就一直复用。
- **风险**：与 (a) 相同，但**爆炸半径小得多**——只碰 3 个区域，坏了用户能明确说「就是顶栏不对劲」，回滚也只要删一段 CSS。
- **与 15 套皮肤共存的方式**：**不需要每套皮肤补一套 UI 规则**。UI 规则只读令牌，令牌每套皮肤都已经给全了（契约 §3 + `lint-skins.mjs` 强制）。所以第 16 套皮肤上线时，UI 规则自动跟着变色——**这是 (c) 相对 (b) 的核心优势，也是它唯一值得做的理由。**

### 3.3 明确回答

**能不能做？** 能。技术上没有拦路虎：CSS 本来就注入在酒馆页面上，缺的只是「选择器范围」和「一份规则」。

**做到什么程度是安全的？**

- **安全**：聊天区外壳（`#chat` / `.mes` 的背景与圆角）、顶栏与抽屉的底色/描边/图标色、输入框的底色/描边/圆角/字体。这些是「换皮不换骨」，不涉及布局与交互。
- **要非常小心**：任何改**尺寸、定位、z-index、pointer-events、overflow** 的规则。酒馆的 `#sheld` / `#form_sheld` / `.drawer-content` 的高度全是 `calc(100dvh - var(--topBarBlockSize) - …)` 算出来的（`style.css:769, 858-859, 877-881`），而 `<html>` 上有 `transform/perspective`（`style.css:143-148`）已经让 `position:fixed` 的包含块变成 `<html>` 盒子——本项目已经在这上面栽过一次（契约 §9.2：窄屏下 ✕ 被推出屏幕）。**再动几何等于二次踩坑。**
- **明确不该碰**：
  1. **`.mes_text` 内部的排版**——归任务 A，且里面混着 HTML 美化与插件元素，从外层改必然误伤。
  2. **酒馆功能性控件的可用性**：`input[type=checkbox]` / `input[type=range]` / `select` 的尺寸与焦点态。用户的自定义 CSS 已经给它们上了 `!important` 深漆，本项目已经为此付出过两轮真机返工（交接 §三第 18 条）。再改一次对比度，是第三次。
  3. **`#chat` / `.mes` 的布局几何**：`display:flex` / `flex-direction` / `padding` / `width` 一动，头像列、swipe 箭头、`swipes-counter` 全歪。
  4. **`.qr--buttons` 的排布**：那是 10 号脚本按钮中转站的绘图空间，动它会把我们自己人挤掉。
  5. **原生弹窗的定位与尺寸**：`/popup` 斜杠命令的高度兜底写在 `.popup{max-height:calc(100dvh - 2em)}`（交接 §五第 30 条），动它会让「立即更新」弹窗在手机上显示不全。
  6. **任何带 `!important` 的用户自定义 CSS 已经覆盖了的属性**：除非我们同时上 `!important` 并且接受「谁后注入谁赢」的掷硬币。`applyCustomCSS()` 在每次设置变更时都会重跑（`power-user.js:1147-1158`），顺序并不由我们决定。

**第一步最小可行增量是什么？**

一条 `src/skin/tavern.css`（或 30 号里的 `TAVERN_CSS` 常量），只做四类、只覆盖三个区域，并且**默认跟随皮肤、不额外加开关**（它本身就是皮肤的一部分）：

```css
/* 示意，实际取值全部来自 --kami-* 令牌 */
html[data-kami-skin="x"] #chat          { background-color: var(--kami-card-2); }
html[data-kami-skin="x"] .mes           { background-color: transparent; }
html[data-kami-skin="x"] #top-settings-holder { box-shadow: 0 1px 0 var(--kami-line); }
html[data-kami-skin="x"] .drawer        { background-color: var(--kami-bg-soft); color: var(--kami-fg); }
html[data-kami-skin="x"] .drawer-content{ background-color: var(--kami-bg); }
html[data-kami-skin="x"] #send_form     { background-color: var(--kami-bg-soft); }
html[data-kami-skin="x"] #send_textarea { background-color: var(--kami-card); color: var(--kami-fg);
                                          border:1px solid var(--kami-line); border-radius: var(--kami-r-sm); }
```

**验收方式**：真机（`localhost:11451`）逐区域读 `getComputedStyle`，确认 ① 底色确实是令牌值而不是用户主题值；② `#chat` / `.mes` 的 `display`/`flex-direction`/`padding`/`width` 与改动前逐属性一致；③ 窄屏（375px）下面板与抽屉没有变形；④ 切 15 套皮肤每一套都不出现「底翻了字没翻」（交接 §五第 28 条那个坑）。

**如果发现「整站皮肤化」会牵动皮肤契约，要改哪几节：**

| 契约节 | 要改什么 |
|---|---|
| **§1 生效与兜底** | 新增第三种作用域：**全局层** `html[data-kami-skin="<id>"]`（不带 `.kami-root`），只作用于酒馆自身 UI，由脚本内置规则消费，**不属于任何皮肤包**。要写清它与 `.kami-root` 层的优先级关系（全局层在后，靠文档顺序或特异性胜出）。 |
| **§2.1 选择器必须含 kami** | 需要为全局层开一个明确的口子并写清边界：全局层规则的选择器形如 `html[data-kami-skin="x"] #top-bar`，字面上含 `kami`（在属性里），但**意图**是碰酒馆 UI。要么把 §2.1 改成「皮肤包仍严禁裸选酒馆 UI；全局层是平台规则，由脚本维护，不受本节约束」，要么把全局层规则移出皮肤校验范围（`lint-skins.mjs` 不检查它）。**建议后者，更干净。** |
| **§3 令牌** | 增加约定：令牌块**同时**定义在 `html[data-kami-skin="<id>"]` 与 `html[data-kami-skin="<id>"] .kami-root` 上（否则全局层读不到）。这是唯一需要 15 套皮肤同步的点，必须配一个幂等的 `build/` 改写脚本 + 一次 `lint-skins.mjs` 全量 PASS 作为验收。 |
| **§4.1 `data-kami-comp`** | 任务 A 用：新增第 5 个取值 **`body`**，写明谁写、在哪、皮肤怎么消费（复用 `.kami-md` / `.kami-body` 规则）。 |
| **§4.2 组件类名** | 补一行「正文包裹层的骨架」（`.kami-root[data-kami-comp="body"] > .kami-body.kami-md`），并明确它**不**带 `.kami-shell` / `.kami-surface`。 |
| **§9 例外清单** | 正文包裹层需要登记几条结构性例外（例如它必须能清掉继承来的 `margin`、必须 `display:block`、不得加 `pointer-events` 限制）。 |
| **§7 构建期校验** | 若走任务 A 的脚本方案，`verify-frontends.mjs` 的 `targets` **不用加**（没有新正则）；若要加令牌上提的机械检查，在 `lint-skins.mjs` 里加一条「令牌块必须同时覆盖 `<html>` 作用域」。 |

## 六、给派活方的三句话

1. **正文美化走脚本层包裹**，落点只有 `30-皮肤管理.js` 一个文件；开关用现成的 `flagRow` 放在「皮肤」页的全局档位卡片里，状态存 `kami-skin.bodyText`，默认关。
2. **兼容性靠一张让位清单**：`div.TH-render`/`pre`/`iframe`/交互标签/`details`/带 class 的/带行内 style 的，一律不包；这条已在探针里实测通过，连点三次不套娃，编辑态不干扰。
3. **全局皮肤做增量**：令牌上提 + 一份脚本内置的酒馆 UI 规则，先只碰顶栏/抽屉、聊天外壳、输入框四类属性；**不要**让 15 套皮肤各自补 UI 规则；`.mes_text` 内部、控件几何、弹窗定位明确不碰。
